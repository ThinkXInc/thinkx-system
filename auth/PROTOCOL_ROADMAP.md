# Auth Protocol Roadmap — 次段階の計画

PROTOCOL.md v1 (現段階) の次に来る2つの段階の設計方針。
前提: 我々は AI アルゴリズムの企業であり、**レコメンド API の他社提供が早期にありうる**。

## 最重要の区別 — レコメンド API 提供は2種類あり、必要な仕組みが全く違う

他社に API を出すと言ったとき、実際には2つの異なる事業形態がありうる。
どちらなのかで、作るものが一段階ぶん違う。

**形態A: 相手企業が自社のデータで使う。**
相手企業が自社の商品カタログ・自社ユーザーの行動データを送り、レコメンド結果を受け取る。
ThinkX のエンドユーザーは登場しない。これは機械同士 (サーバ間) の契約であり、
必要なのは API キーと課金メーターだけ。**署名トークンも同意画面も refresh_token も不要。**
→ 第2段階。早期に来る可能性が高いのはこちら。

**形態B: 相手企業のサイトで、ThinkX ユーザー本人のデータを使う。**
例:「あなたの ThinkX 上の履歴に基づくおすすめを、提携サイトでも表示する」。
ThinkX ユーザー本人の同意が必要になり、初めて「信用できない他人 + ユーザーの同意」という
Google と同じ構図が成立する。→ 第3段階 (= PROTOCOL.md §7 の引き金 (a))。

営業上は同じ「API 提供」に見えるが、技術上はこの2つの間に段差がある。
**商談が来たら最初に確認すべき問いは「相手は誰のデータでレコメンドを受けたいのか」。**

## 第2段階: B2B API 提供 (形態A) — v1 への追加で対応する

### 設計方針

- auth を「人間の身元 (セッション)」に加えて「機械の身元 (API キー)」も発行する
  唯一の場所に拡張する。身元と課金の真実を一箇所に置く現行の設計をそのまま延長する。
- UserInfo (PROTOCOL.md §3) は**一切変更しない**。protocol_version は 1 のまま。
  追加されるのは新しいエンドポイントだけであり、§6 のルール上、既存サイトに影響しない。
- レート制限は nginx-root 層で行う (アプリに入る前に落とす)。
  使用量の計測はレコメンド API 側が記録し、課金 (Stripe) は auth が既に持つ経路に乗せる。

### 追加されるもの

| もの | 置き場所 | 内容 |
|---|---|---|
| パートナー登録 | auth | 社名・連絡先・契約プラン・発行済みキー。当初は手動登録でよい (管理画面は不要。config 登録の延長) |
| `api_key` 発行 | auth | パートナーごとの不透明文字列。Redis + Mongo に保存。無効化は即時 (削除するだけ) |
| キー検証口 | auth | `POST /v1/api_keys/verify` (バックチャネル、サーバ間)。レコメンド API がキーの有効性・プラン・レート上限を照会する。結果は短時間キャッシュ可 |
| 使用量記録 | レコメンド API | リクエスト数・処理量を記録し、auth の課金へ集計 |

### 手続き (形態A の API 呼び出し)

1. 【一度だけ】パートナー企業と契約し、auth にパートナーとして登録、`api_key` を発行して渡す。
2. パートナーのサーバがレコメンド API を呼ぶ:
   `POST https://api.thinkx.com/v1/recommend` に `Authorization: Bearer {api_key}` と入力データ。
3. nginx-root がレート制限を通す。レコメンド API は受け取ったキーを
   auth の `/v1/api_keys/verify` で検証する (直近の検証結果があればキャッシュを使う)。
4. レコメンド API が結果を返し、使用量を記録する。
5. 月次で使用量を集計し、auth の Stripe 経路で請求する。

### 今から先回りしてよい安い準備 (これだけ)

- auth のサービス登録 (SSO_CLIENTS 相当) を設計する際、登録主体に
  「身内サイト / 外部パートナー」の**種別フラグを持てる形**にしておく。
  config の構造の話であり、プロトコルの凍結対象ではないのでコストゼロ。
- レコメンド API のレスポンス外形を最初から libcommon の3型 (成功 / 単体エラー /
  errors 配列) に合わせておく。他社に見せる API こそ、外形の一貫性が価値になる。

署名トークン・SDK 配布・開発者ポータルは第2段階では作らない。
パートナー数が少ないうちは、API キー + ドキュメント1枚で成立する。

## 第3段階: ユーザー委任アクセス (形態B) — protocol_version 2

### 発動条件

PROTOCOL.md §7 の (a): 他社アプリが ThinkX ユーザー本人のデータへ、本人の同意の下で
アクセスする事業判断が確定した時点。(b)(c)(d) が先に成立した場合も、署名部分のみ先行する。

### 追加されるもの (この段階で初めて作る理由も併記)

| もの | 今作らない理由 |
|---|---|
| 同意画面 (「アプリXがあなたの履歴へのアクセスを要求しています」) | 同意の境界は他人が現れて初めて存在する |
| scope (アクセス範囲の宣言: 例 `recommend:read`, `profile:read`) | 何を切り売りするかは商材が決まってから決まる |
| refresh_token (ユーザー不在の継続アクセスの同意証明) | 身内は §2 手順7 の `GET /v1/users/{user_id}` で足りている |
| 署名付きトークン (JWT) + 公開鍵配布 (JWKS) + 鍵ローテーション | 鍵運用は使われて初めて鍛えられる。先に作ると未使用のまま契約に凍結される |
| PKCE (モバイル/SPA などの秘密を持てないクライアント対応) | 対象クライアントが現れてから、その時点の標準で入れる |
| 開発者登録・ドキュメント・ToS | 第3段階の作業総量の大半はこれ。プロトコル変更はごく一部 |

### 移行が既存を壊さないこと (§6 の適用)

- 身内サイト (vendoring 済みの auth_client) は protocol_version 1 のまま無変更で動き続ける。
  v2 は「リクエストで 2 を明示した相手」にだけ返る。
- 第2段階の API キー (形態A のパートナー) も無変更。形態B は別の credential 体系。
- つまり第3段階は、既存の2系統の上に**足す**だけで、置き換えではない。

## 段階と事業判断の対応 (一枚まとめ)

| 事業判断 | 発動する段階 | 作る主なもの |
|---|---|---|
| (現在) 自社サイト群に共通ログインと課金 | 第1段階 (PROTOCOL.md v1) | authorize / exchange / userinfo、UserInfo v1 |
| 他社が自社データでレコメンド API を使う | 第2段階 | api_key 発行・検証・使用量課金 |
| 他社サイトで ThinkX ユーザーのデータを使う | 第3段階 (v2) | 同意画面・scope・refresh_token・署名トークン |
| SPA/モバイルが直接 auth と話す、リージョン分離 | 第3段階のうち署名部分のみ | JWT + JWKS |
