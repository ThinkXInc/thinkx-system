# API設計原則(原本)

この文書は、設計判断の根拠となった方針の**発言原文を保存する**もの。「」内は原文のまま。
規約や実装で判断に迷ったとき、解釈(PROTOCOL.md 等)ではなくここへ戻る。

## 命名

- 「原則としてキーを見て中身が完全にわかる命名であることが必要」
- 「命名はやはり人間から見てわかりやすいことが重要だから user_id でいいだろう」
- client_id への疑義:「client_id とは? サービス名? だとしたら service とか直接わかるように原則は同じ」
  → service_id / service_secret 採用の根拠。
- 派生した境界規則: 外部(Google 等)と話す境界では相手の名前(sub, aud 等)で読み書きし、
  内部プロトコルでは上の原則で命名する。

## 参照設計の選び方

- 「json の型はすでにうまくいっている Google の形式などを参考にするのが確実だろう」
- 「まず Google の形式を見せて それをもとに議論を構築すべき」
- 「Google が3段階にしているのは理由があるだろう 我々もいずれそうなるのなら最初から
  そうしておくべきだろう そのためのコストはそれほど大きいとも思えない」
  → 議論の結果: 借りる前に「その理由が我々にも当てはまるか」を検証する。
  当てはまらない装置(署名付きトークン・refresh_token)は先回りせず、
  protocol_version と昇格条件(PROTOCOL.md §7)を保険として後置する。

## バージョン

- レスポンスにプロトコルのバージョン番号を入れる方針:「それはやるべき」

## 事業方針(プロトコル設計に直結するもの)

- 「我々は AI アルゴリズムから構築する技術企業であり特にレコメンド API の他社提供は
  早い段階で行う可能性がある」
  → PROTOCOL_ROADMAP.md 第2段階の根拠。他社提供には2形態あり
  (相手企業のデータで使う / ThinkX ユーザーのデータで使う)、必要な仕組みが一段違う。
- 「Google アカウントのように全サービス共通のアカウントシステムを用意したい」
- 「auth サービスはあくまで apps のひとつとする」

## 全体の設計思想(コーディングガイドから、プロトコルに効く部分)

- 「ツールを多用するのでなくミニマルなモジュールでロバストな大規模化しても破綻しにくく
  AI 駆動開発で長期に生産性を保てる詰まりにくい設計になっていること」
