## 1. 用語の是正（「交換」「AuthorizationState」とRedisの帰属）

**kaz:**

> まず、交換するという表現が意味不明だ。交換というのは何かと何かを交換するので、それが書かれていないなら、多分それは交換じゃないんだろう。 取得なのか、それとも送信するのか、それとも何かと何かを交換するのか。多分交換という表現が間違っている。次に、AuthorizationStateというのは何らかの状態を意味するはずだが、これは状態というよりも、とりあえず認証を開始したよという印か何かを保存しているんだろう。 というか、それをブラウザーと照合するためのIDじゃないのか。だとしたらIDと呼ぶのが正しいだろう。さっきまでIDと呼んでなかったか。そして、最初に読んで最も意味不明だったのは、AuthのセッションクラスとQuantのセッションクラスが別々に存在し、そしてそれらがそれぞれRedisに何らかの値を保存するとして、それらが全く別々のものなのか。RedisのデータベースはAuthとQuantサービスがどちらもそれぞれ持つのか何なのか。 オーナーは最後の説明に納得がいっていない。議論をすべて踏まえて、オーナーの主張をすべて汲み取った上で、オーナーが求める完全な認証フローの手続きの説明を作ってくれ。

指摘は3点ともに正当で、いずれも名前が実態を隠していた。

**「交換」→「引き換え」。** quantz が使い捨ての券（auth_code）を渡し、その券と user_id を引き換える一方向の操作。対等な交換ではない。英語 exchange の直訳が混乱の元。

**「AuthorizationState」→照合用の一時ID。** これは「状態」ではなく、「quantz がログイン開始時に発行し、auth から戻った callback が同一ブラウザ発かを照合するためのID」。名前は照合目的を表すべき。後にこれは OAuth 予約語 `state`（wire名）と内部名の使い分けの話へ発展する。

**セッションクラスは1つ、Redisは別。** `Session` クラスの実装は auth と quantz で共有し、接続先 Redis だけが違う。「別々のクラスが存在するのか」への答えは「クラスは同じ、保存先 Redis が別」。この分離が後の中央Session/ローカルSessionの区別の起点になる。

## 2. 完全な認証フローの構築（自作版）

（この論点は論点1と同じ kaz 発言を起点に、Claude が最初の完全フローを提示した部分。以下は Claude 側の要点。）

authorization code 方式の全手続きを、リクエスト単位で提示。要点は「秘密をブラウザのURLに載せず、使い捨ての番号（auth_code）だけを載せる」こと。

- **リクエスト1（quantz `/auth/signin`）**: `callback_verify_id` を生成し Session に保存、auth の `/authorize` へリダイレクト。
- **リクエスト2（auth `/authorize`）**: service_id 登録確認、redirect_uri 検証、auth 中央 Session で user_id 確認。
- **リクエスト3（auth signin）**: auth **だけ**が password を受け取り Argon2id 検証、auth 中央 Session を開始。
- **auth_code 発行**: Redis に TTL 60秒。Session（継続状態）と auth_code（使い捨ての券）は役割が違う。
- **リクエスト4（quantz `/auth/callback`）**: `callback_verify_id` 照合 → auth_code を user_id に引き換え → quantz ローカル Session 開始。

核心は「中央Session＝authで本人確認済み」「ローカルSession＝このサービスにログイン済み」の二層構造。変わるのは `Session.start(user_id)` 直前の本人確認方法だけで、成立後の通常処理は従来通り。

## 3. インフラ配置 — Redisをどこに置くか、`state`の名前、標準性

**kaz:**

> ようやく全体がつかめた。少し疑問がある。
> この場合、オースサーバーとサービスのクォンズサーバーはそれぞれ別のセッション用のDB、RedisDBを必要としているということは分かった。そして、このRedisのDBは結局どこに置かれるべきなんだろうか。
> 今、ステージングはすべて一つのサーバーにまとめて、プロダクションはMongoDBとセッション用のレジスDBを分けようとしていたが、このセッション用のDBの単にDBナンバーを分けて、オース用とサービス用にすればいいだろうか。またもう一つの論点は、ステートという変数というか名前が本当に適切なのかだ。あなたがチェックなんとかIDというふうに最初に言った通り、ステートじゃなくて別の名前を使った方がいいなら、そうした方がいいのではないだろうか。また、この設計は極めて標準的な設計と言えるのか。そして、もはやこれがスタンダードと言っていい設計なら、単にそれに従えばいいだろう。
> いくらかの名前の変更などはしてもいいと思うが、設計自体は極めて標準的と言っていいだろうか。

**Redisの配置。** 論理分離（用途）はDB番号でよいが、所有境界（authとquantz）はインスタンスで分ける。同一サービス内の Session/SSO はDB番号、別サービス間はコンテナ/インスタンス。「DB番号だけで全部分ける」は所有権の違う二者を1物理DBに相乗りさせるので不可。staging は auth用コンテナ・quantz用コンテナを別に、production は別サーバーなので自動的に分かれる。Redis はバックアップ対象外（消えても再ログインで回復）。

**`state` の名前。** 内部名は実態に合わせ `login_nonce`（後に `callback_verify_id`→最終的に `authorization_transaction_id`）に。ただし **wire名は `state` のまま**。理由は `state` が OAuth 2.0（RFC 6749）の予約語で、標準ライブラリ・ツールがその名前で認識するから。境界で一度読み替える。「自分で決められる名前は実態に、外部プロトコルが固定する名前はそれに従う」。

**標準性。** これは OAuth 2.0 / OIDC の Authorization Code Flow そのもの。第一原理で詰めた部品（照合ID・使い捨てコード・サーバー間の秘密での引き換え・中央/ローカルSession分離）が全部 OAuth 標準構成要素と一対一で対応する。ただし auth 側（Authorization Server）を自作する点が多くのプロジェクトと違う。PKCE の採否は実装時の判断として残る。

## 4. 設計の標準性の調査 — 既存OSSとの比較（Authlib vs 完成品IdP）

**kaz:**

> callback_verify_id が直感的でいい
>
> callback_verify_id -> stateにurl上は書くのはそれでいいだろう
>
> そこが重要な論点だ。完全に標準と一致しているのであれば、既成のオープンソースなどを使って単にそれを使えばいいのではないだろうか。
> つまり、今私たちが到達した仕様にほぼ完全に一致するようなオープンソースがあるのなら、それを使えばいい。わざわざ自作する必要がない。
> 少し調査をしてほしい。どうだろう。もし、つまり最も似ているオープンソースを見つけ出し、そして違いを比較してほしい。

既製品を2種に分けて評価。

**完成品IdP（Keycloak / Authentik / Ory Hydra）は不適合。** PostgreSQL 必須（MongoDBを正本とする方針にDBが増える）、リソース過大（Keycloak単体で1-2GB）、ブラックボックス（「ソースコードを契約の正本にする」方針と衝突）、既存資産（User/Session/simplicity/SES）を捨てることになる。「認証を丸ごと外注したい」チーム向けで、既存 Flask+Mongo 資産の上に最小構成で作りたいケースには過剰。

**Authlib は到達点とほぼ一致。** 保存層を強制せず、`query_client`/`save_token`/`save_authorization_code` を MongoDB/Redis で書ける。第一原理で導いた部品が Authlib の API と一対一対応。PKCE・redirect検証・code再利用防止など「自分でバグらせたくない微妙な部分」を標準準拠で肩代わりする。ただし `callback_verify_id` の照合と `Session.revoke_all` は OAuth 仕様の外で、Authlib を使っても自作のまま残る。

## 5. Authlib版フローの提示と、自作との比較

**kaz:**

> 完全なログインフロー
>
> 上記の選択で言えば、OAuthlibを使う可能性はありだと思う。ただ、まだ実装イメージが湧かない。
> つまり、我々はなるべく外部ライブラリに依存せずに、外注をなるべくしないようにしている。それは見えない部分を減らすためであるし、余計なインターフェースを覚えるよりも自作で書いた方が一貫性を持てるなら、その方が見通しが良いからだ。
> あなたの書いた完全なログインフローを、もう一度このOAuthを使ったバージョンで書いてほしい。そうすれば、一体実装がどのように変化するのかがわかるだろう。もしインフラのDBとかインフラの構成が変わるなら、それについても書いてほしい。

Authlib版フローを提示。結論の枠：**Authlibが肩代わりするのは auth の `/authorize` と token endpoint の内部だけ**。quantz側の signin/callback、callback_verify_id照合、Session、revoke_all、UIは自作フローから一切変わらない。

**インフラは変化なし。** Authlib は保存層を持たず、`query_client`/`save_token` の中身を自分で書くので PostgreSQL は増えない。MongoDB 1 + Redis 2 のまま。

差分が出るのは、auth `/authorize`（`get_consent_grant`+`create_authorization_response`）、token endpoint（`create_token_response`）、`require_oauth` デコレータの3箇所。access_token を token endpoint で返し、UserInfo を別 `/userinfo` にする点が「引き換えでUserInfo同梱」案と分かれる。自作を貫く論拠（ライブラリ固有の語彙とライフサイクルを覚える必要、結局 save系を自分で書くなら実装量の差は劇的でない）と、Authlibを使う論拠（危険な処理は"見えにくい"コードなので標準準拠に委ねる方が哲学と両立）を両論提示。この時点の推奨は「骨格は自作確定、token endpoint内部だけ初版自作→将来必要ならAuthlib」。

## 6. `server`とは何か・MongoEngine Userのアダプタ問題（自作確定へ）

**kaz:**

> grant = server.get_consent_grant(end_user=user)
>
> ここで急にサーバーというものが出てきているが、これはオースリブのインスタンスなのか、それとも文字通り何らかのオースリブを動かすサーバーを想定しているのか。
> そしてこのユーザーというのは、我々はMongoDBのユーザー、もっと言えばMongoエンジンベースのユーザーインスタンスを我々は使用しているが、それをそのままここに引数として取っても動くのか、それとも互換性のあるように調整しなければいけないのか。

> つまり、O3部のインターフェースに合わせるのに、むしろそこでバグったり見通しが悪くなるぐらいだったら、それほど難しくない処理だったら、全部見通しよく一貫した書き方で書いてしまった方が、むしろ枠が少なくなるとも言えるし、人間が見た時に見通しがいいとも言える。
>
> `/authorize`（リクエスト2）の `create_authorization_response` が、Authlibの手でこのリダイレクトを組み立てる：
>
> この部分についても、一体オースリブがどこでどうやるのかがよくわからない。これもオースサーバーの中で行われるのか。
> その中でオースリブインスタンスが何らかの関数によってリダイレクトURLとかステートを生成するということなのか。だとしたら、それを自分で書くのと何が違うのかがよくわからない。
>
> つまり、もう少し完成されたコードに近いようなコードを書いてくれ。その際に、実際に我々の実装しようとしているAuthの実装、つまり我々のセッションクラスなど、またユーザークラスなどを使ったと想定した実装で書いてくれ。もしその元のソースコードが参照しなければわからないとしたら、クォンツウェブまたはlibcommonのレポジトリをパブリックにしてあるからそれを見ればわかるだろう。
>
> https://github.com/ThinkXInc/libcommon
>
> 実際の使用
> https://github.com/ThinkXInc/quantz-web

疑問への直接の答えと、それが自作確定を導いた。

**`server` はAuthlibの `AuthorizationServer` インスタンス。** 別プロセスのサーバーではなく、アプリ起動時に一度作るPythonオブジェクト。新プロセスもポートもコンテナも増えない。

**MongoEngine User はそのままでは動かない。** Authlib は `user` に `get_user_id()` 等を期待し、`query_client` の戻り値は `ClientMixin`（`check_redirect_uri`等十数個）を満たす必要がある。つまり Authlib を使う実際の作業は「OAuthの手続きを書く」ことではなく「既存 User/Service/Session/Redis を Authlib の期待するインターフェース（Mixin）に翻訳するアダプタ層を書く」ことになる。kaz の直感（合わせるところでバグる・見通しが悪くなる）は的確。

**危険な処理を手で書いてもミスる余地は小さい。** auth_code の一回消費（`getdel`で原子的）、redirect_uri検証（完全一致の`in`）、client_secret検証（`compare_digest`）、callback_verify_id照合。4つ合わせて十数行で、使う道具は既知のものだけ。「`getdel`を使う」「完全一致にする」「`compare_digest`を使う」の3定石を外さなければレビューで目視確認できる。

→ **前回の推奨を修正し、初版はAuthlibを入れず全部自作すると確定。** アダプタ層のコストが肩代わり分を上回り、ブラックボックス化が「ソースコードを契約の正本にする」方針を崩すため。PKCE・複数プロバイダ・OIDC discovery が本当に必要になった段階で再検討。

## 7. 自作版・完全フローの提示（実コードベースに即して）

**kaz:**

> 続けてくれ

auth側の心臓部（authorize / token_exchange / userinfo / SSOStore）を、既存の `MongoModel`・`RedisBase`・libcommon `Session` に載せた実コードで提示。

- **`AuthService`**: client_id/secret_hash/registered_redirect_uris。secret も平文でなくハッシュ保存、判定はモデルに閉じ込める。
- **`SSOStore`**: `issue_auth_code`（TTL60秒）、`redeem_auth_code`（`getdel`で一回消費、service/redirect_uri のすり替え防止）、access_token 発行。危険な処理が一クラスに可視化。
- **`/authorize`**: `Session.user_id()`（既存メソッドそのまま）でログイン判定。Authlib版で必要だった翻訳層がゼロ。
- **token endpoint**: `@required_fields_check` 等でハンドラを読めば契約が全部見える。
- **quantz callback**: 前回の自作フローから不変、`auth_code`→`code` の名前だけ。

判断の再確認：初版はAuthlib不使用で全自作。既存資産に素直に載り、危険処理は3定石に収束。初版必須は「redirect_uri完全一致」と「auth_codeの`getdel`一回消費」で、これだけは契約テストで固める。

## 8. OIDCの各概念の解説（何を守るために各値があるか）

**kaz:**

> 全体的に前のバージョンよりかなりシンプルで見通しが良いように見える。ただし、それぞれの個々のセキュリティ上というか認証上の概念がよくわからない。
> これは多分OIDCの仕組みそのものだと思う。もう一度説明してくれ。

各値を「攻撃者の視点で、何を防ぐか」で説明。全体は「auth だけがパスワードを扱い、認証結果を盗難・すり替え・偽造に耐える形で渡す」という一要件から導かれる。

- **authorization code** = 秘密を載せない使い捨て番号（履歴・ログ・Refererに残っても無害）。
- **state** = login CSRF（なりすましログインの強要）を防ぐ。ブラウザと認証フローを結ぶ。
- **PKCE**（challenge/verifier）= 盗まれた code の悪用を防ぐ。code の発行と引き換えを結ぶ。verifier はサーバー内に留まりURL経路に出ない。
- **client_secret** = サービスのなりすましを防ぐ。ブラウザに渡さずサーバー間のみ。
- **redirect_uri 完全一致** = code を攻撃者サーバーへ送らせない。
- **ID Token** = 認証結果の偽造を防ぐ。auth が秘密鍵で署名、サービスが公開鍵で検証。鍵の非対称性が「サービスがauthを信頼できる」根拠。
- **iss/aud/exp/sub** = それぞれ発行元固定・宛先固定・期限・不変の背番号。
- **nonce** = ID Token のリプレイを防ぐ。ログイン開始と ID Token を結ぶ。

3つの照合値（state=ブラウザ / PKCE=code / nonce=ID Token）は同じ乱数だが守る対象が3層に分かれる。ID Token（誰か）と access_token（アクセス権）の2トークンも役割が別。

## 9. OIDC準拠の採否 — コストは何か、JWTの延長で済むか

**kaz:**

> OIDCに準拠するかはかなり大きな問題である。基本的にはAPIのプロバイダーにならない限りは、準拠するコストを支払う必要がないはずである。
> しかし同時に、プラットフォーマーとして大きなサービスを目指しているなら、いずれは必須となる可能性があるし、認証のAPIを開放できるというのは、サービスのビジネス的な設計に幅を持たせることができる。だから、これを検討することは価値があるし、我々は大きなプラットフォーマーを目指しているのだから、無視できない。
> 問題はそのコストである。特にインフラ上に大きなコストが追加されないのであれば、つまり単にソースコード上の運用の問題であれば、検討に十分反対する。もしそれによってかなり複雑化したりバグが多くなったりする管理コスト、ソフトウェアのメンテナンスコストが増えるのであれば、慎重にならなければならない。一体どれだけソースコードが増大したり、一体どれだけ手続きが複雑になるんだろうか。
> 今現在、QuantsというサービスではJWTを使ったトークンを発行しているので、これは私の知見の中にブラウザ署名という概念はすでにあるし、すでにサービスとしてもJWTでの認証自体は行ったことがあるので、その延長で済むのであれば、それほど私の認知コストは増えない。
> 実際にどのような行動になるのか、さっきあなたが書いてくれたフローの説明は非常に直感的で分かりやすかったので、もしOIDCの基準に沿った場合のプランでいくと、どのような実装になってくるのかをフローとして説明してくれないか。

**結論：インフラは1バイトも増えない。** OIDC完全準拠が opaque 案に追加するのは署名鍵ペア1組だけ。DB・サーバー・プロセスは増えない。JWTは既にQuantzで使用済みなので依存も知見もある。新しい認知負荷は実質 nonce・sub・JWKS の3概念だけ。

opaque案との差分は、ログイン開始時に nonce を1つ追加、token endpoint が `id_token`（署名JWT）を1つ多く返す、quantz が ID Token を検証する数行。opaque案で必要だった `/userinfo` 往復が ID Token に情報が入るぶん減るので、コード量はほぼ相殺。

唯一の新要素は公開鍵配布（JWKS）だが、初版は各サービス設定に公開鍵を直書きで足り、JWKSエンドポイントは他社開放時に足せばいい（それもGET1本でDB・インフラ増えず）。

→ **プラットフォーマー志向と「インフラが増えないなら検討に値する」の判断軸の両方から、OIDC準拠を採るべき。** 唯一の設計規律は「sub は issuer内で一意・永久に再割当てされない」を初版から守ること（MongoのObjectId、後に独立subject_idへ）。

## 10. OIDC準拠版フローの完全な提示

**kaz:**

> では、OIDCでのバージョンでの差分ではなく、完全なフローをもう一度書いてくれ。なるべく実際のコードがイメージできるように書いてくれ。

OIDC準拠版の全フローを、既存資産に即した実コードで頭から提示。前提を固定：既存 `Session`（start/user_id/id/get/set/revoke_all）、`MongoModel`、`RedisBase` はそのまま使い、新規ライブラリはJWTのみ、**アダプタは書かない**（自作なので翻訳層が不要）。

9ステップ（①signin→②authorize→③signin画面/password→④authorize再訪→⑤code発行→⑥callback→⑦token交換→⑧ID Token検証→⑨通常ページ）を、誰が誰に送るかを明記して提示。新規クラスは `SSOStore`/`IDTokenIssuer`/`AuthService`/`ServicePrincipal`/`AuthClient`/`IDTokenVerifier`。

> 新規のみ、移行不要

> （さらに追指示）

**判断A（JWKS）**：初版から `/oauth/jwks` と `/.well-known/openid-configuration` を公開。鍵ローテーションは決定論的スクリプト＋スケジューラで自動化（生成→JWKS追加→待機→active切替→待機→retired）。判断を要する分岐がないので完全自動化可能。「運用が増える」の実体は「スクリプト1本を書く」。Claude Codeのような対話エージェントは、決定論的処理には短所なので使わない。

**ステージングのClaude Code論点**：本番の署名鍵・client_secret・ユーザーデータをステージングと共有しない（無条件確定）。これを守れば、ステージングにアクセスできても漏れるのは捨ててよいステージング用の秘密だけ。auth は変更頻度が低いので常駐エージェントを置かず、ローカル修正→デプロイ→テスト一発の構成にする。

**その構成の成立条件**：テストを2層（論理層の単体テスト＋HTTPクライアントによる最小E2E疎通）に分け、seedコマンドでステージング初期化。実ブラウザ自動化は不要（リダイレクト・cookie・POSTだけなのでrequestsのSessionで足りる）。

**判断B**：subject_id を ObjectId と分離（一度公開したsubは不変、pairwise余地）。**判断C**：新規のみ・移行不要。**判断D**：logout はservice/auth/globalの3種、デフォルト=global logout、個別も残すが目立たせない。

## 到達点

議論の出発点は「用語が実態を隠している」という違和感だった。そこから第一原理で認証フローを組み立て直した結果、たどり着いたのは OAuth 2.0 / OpenID Connect の Authorization Code Flow + PKCE そのものだった。独自発明ではなく標準に収束したことが、設計の正しさの傍証になっている。

確定した骨格：auth だけがパスワードを扱い、認証結果を盗難・すり替え・偽造に耐える形で各サービスへ渡す。中央Session（authにログイン済み）とローカルSession（サービスにログイン済み）を分離し、OIDC完全準拠（ID Token=RS256 JWT、JWKS公開）を採るが、インフラは MongoDB 1 + Redis 2 ＋署名鍵1組から増やさない。Authlib等のフレームワークは使わず全自作し、ソースコードと契約テストを契約の正本とする。2度の第三者レビューで見落とし（PKCE・複数タブ・GETDEL順序・失効の実装・billing順序転倒ほか）を修正した。

正本は `auth-spec/`（5ファイル）と DECISIONS D-38〜D-46。本文書はその背後の思考の経緯である。
