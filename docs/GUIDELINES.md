### 2 への追記(2026-07-18): 圧縮禁止の再発と適用範囲の明確化
- **原文**: 「もう少し丁寧に簡略化せずに説明してくれ　文脈をすべて覚えていないことがあるから思い出しながら読むのに時間がかかる　過度にコンパクトに文章を圧縮しようとするな　普通に説明してくれ」+「これは一般的な話であり そこまで展開しろと言っていない あなたの説明の傾向を言っている またはどこか私の書いた指示書にその原因があるならそれを特定したい」

### 追記(2026-08-07): 後始末まで含めて完結させる

- **原文**: 「なんでこの操作が add ip .sh に入ってないんだよ　コマンド全部完結させるだろ」
- **解釈**: スクリプト化の範囲は「目的の操作」だけでなく、**その操作の後に必ず要る後始末**まで。
  人間に手打ちを残した時点でスクリプト化は未完了である。特に、スクリプト自身が末尾で
  検証している事柄については、その検証を通すために要る操作を外に出してはならない。
- **文脈**: `add_current_office_ip.sh` が SG に IP を足した後、4台へ ssh して到達確認するが、
  インスタンスを作り直すとホスト鍵が変わるため古い `known_hosts` で検証が NG になる。
  実行者はこれを「別途 `ssh-keygen -R` を打ってください」とチャットで案内していた。
  スクリプト自身の検証を人間の手打ちに依存させており、しかも失敗の原因が SG に見える。
  対処: `reach_host()` を追加し、鍵の不一致に当たったときだけ古い鍵を捨てて張り直す
  (毎回捨てると成りすましも黙って通るため、不一致時のみ・警告を出す)。

## 結論だけを先置きせず、結論に至る理由を続けて説明する(2026-07-20)

- **原文**: 「前から言ってるが、お前の説明にはなぜがないので、いきなり結論が来たり、いきなり事実だけ列挙されてるから、論理を追いづらいんだよ。なぜそうなる？私が書いた何らかの指示が影響しているのか、それともお前の単なる本来的な傾向なのか。とにかくこの私の指示はガイドラインに書き込んで以降反映しろ。」
- **解釈**: 「結論を先に書く」は、理由を省略した結論を単独で置いたり、その後に事実だけを列挙したりしてよいという意味ではない。結論を述べた直後に、どの前提・観測事実から、どの因果関係を経てその結論になったかを普通の散文で説明し、読者が判断過程を順に追えるようにする。事実の一覧は理由の代わりにしない。
- **文脈**: auth の実装範囲と構成案への回答で、「複数の認証領域として展開できる構造が最善」「SMS と payment は初版から分離」と先に結論を書いたが、なぜ固定ドメイン・固定DBでは要求を満たせないのか、なぜSMSとpaymentを分けるのかを結論の直後に説明せず、その後に事実と提案を節ごとに列挙した。そのため論理の接続が読者側の補完に委ねられた。
- **原因**: Codex の「結論から書く」と既存 GUIDELINES の「結論→散文の理由」のうち、実行者が前半だけを過剰適用したこと。オーナー指示が理由の省略を求めたのではなく、実行者が「先に結論」と「因果を説明する」を誤って切り離した。
- **運用**: 回答冒頭は必要なら結論から始めるが、次の段落で必ず根拠と因果を接続する。「結論→関連事実の箇条書き」だけで終わらせない。複数案から一案を推奨するときは、要求、制約、各案の帰結、推奨理由が順に読める文章にする。

## サイトを変更したら反映(再起動)まで込みでやる(オーナー指示 2026-08-07)

- **原文**: 「変更したら再起動はルーチンとして覚えて」
- **解釈**: サイトのファイルを変更したら、そこで終わりにせず**反映まで**を1セットで行う。
  編集 → 該当サービスの再起動 → **URL を curl して変更後の値が返ることを確認** →
  オーナーへ「どの URL で確認できるか」を提示する。オーナーが見ている画面が変わらない
  ことを自分より先にオーナーに気づかせない。再起動は `infra/run/restart_<site>.sh`
  (中身は `sudo systemctl restart uwsgi_<site>.service`)。sudo が対話パスワードを
  要求して Claude 側から叩けない場合は、その事実とオーナーに叩いてもらうコマンドを
