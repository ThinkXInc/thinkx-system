## 1. ツールはシステム依存にせずプロジェクト内に持つ

- **原文**: 「その辺のツールをどこから取って使うかは一般規則として記載しておこう　システムに依存しないように　毎回使うツールはプロジェクト内にビルドを持っておこう」＋「ARM実行はCLAUDE GENERALに書いてなかった？」＋「正しいVENVを使っているの？必ずプロジェクト内の専用の環境で実行する決まりのはずだよ」
- **解釈**: 実行バイナリも PATH 任せにせず、ARM64 ネイティブをプロジェクト内 BIN/ に持ち、専用 VENV で動かす。
- **文脈**: HOMEBREW の X86 PANDOC が ROSETTA 実行でハングし組版が止まった事故。
- **解決**: 一般規則化 → **CLAUDE_GENERAL.MD 項7** が正本（ENV→`<PROJECT>/BIN/`→PATH の解決順、ARM64 必須、導入手順を TRACKED に）。

## 2. チャット応答は「結論→散文の理由→表は補助」で書く（形式化・過剰圧縮の禁止）

- **原文**: 「こういう返答スタイルというか記述が仕事がしやすかった　今は形式的すぎるし情報が過度に折りたたまれすぎて意味不明　あとはどこを直せば戻る？」
- **解釈**: 見本として示されたのは SSM Session Manager の説明返答（2026-07-15）。その構造 = ①結論を一文で先に ②理由を散文で説明（機構が読めば分かる）③表は散文の補助（表を読まなくても本文で意味が通る）④判断を求めるときはトレードオフを文章で述べてから。逆に、規約引用が結論より先に来る・情報を表のセルに短句で圧縮する・会話を A-1/B 等の整理番号で管理する、は「形式的すぎ・折りたたみすぎ」で仕事がしにくい。
- **文脈**: CLAUDE_GENERAL.md 導入直後、実行者（Claude）が規約12（当時）の許可求め形式と文書向け規約（14/15/17）をチャット応答にまで誤適用し、返答が承認申請書のようになった。規約12 はオーナーが取り消し線で無効化。
- **解決**: 実行者が項19として条文化を試みたがオーナーが「全然そういうことじゃない」と却下・削除（規約11以降も削除）。条文化はせず、この記録の原文と見本（SSM 返答）を直接の規範として運用で従う。

## 3. 手順書は「上から何も考えずに実行するだけ」・分岐を置かない

- **原文**: 「そういう手順書は、とにかく何も考えずに実行したいから、いちいち読む前提で書くなよ。」「もっと上から何も考えずにただ実行するだけにしてくれ。何か分岐があるんだったら、分岐があることを明確にしてくれ。基本的に分岐はないと思う。」(2026-07-17)
- **解釈**: 手順書の説明文はほぼゼロ、全ステップをコードフェンス(コピーボタン)、環境差は冒頭変数のみ、本文は共通コマンド、分岐は作らない(環境ごとに別ファイル)。やむを得ない分岐は明示。
- **文脈**: infra/docs/prod構築手順.md の初稿に説明文と「どちらか1ブロック」分岐を入れて差し戻された。
- **解決**: 詳細は infra/docs/GUIDELINES.md「手順書(構築 runbook)の書き方」。DOC_STYLE_GUIDES.md への恒久反映は人間判断。

### 2 への追記(2026-07-18): 圧縮禁止の再発と適用範囲の明確化
- **原文**: 「もう少し丁寧に簡略化せずに説明してくれ　文脈をすべて覚えていないことがあるから思い出しながら読むのに時間がかかる　過度にコンパクトに文章を圧縮しようとするな　普通に説明してくれ」+「これは一般的な話であり そこまで展開しろと言っていない あなたの説明の傾向を言っている またはどこか私の書いた指示書にその原因があるならそれを特定したい」
- **原因の特定**: 手順書向けの「説明を削れ」系指示(GUIDELINES 3 / infra 手順書ルール)を、実行者がチャット説明にまで過剰適用した。逆方向の混同(文書の形式主義をチャットへ)も過去にあり、**文書ルールと会話ルールの境界管理が弱い**のが構造要因。
- **運用**: 削るのは実行用文書(手順書・スクリプト出力)。**チャットの説明は、読者が文脈を全部保持していない前提で、普通の文章で、固有名詞には短い思い出しの手がかりを添えて書く**。圧縮(矢印連結・括弧詰め込み・名詞羅列)をしない。ただし「圧縮するな」は「長大に展開しろ」ではない — 聞かれたことに普通の分量で答える。

## コマンドの束はスクリプトに落とす・対象環境は必ず引数(2026-07-19)

- **原文**: 「基本的なことだが、これは一般規則にするに値するが、基本的にコマンドの束はまとめて一つのスクリプトにしておくべきである。ここでは、Terraformのチェンジディレクトリなど、いちいちそんなコマンドを覚えていられないというものがたくさん入っている。これらは一つのスクリプトにおいて、定型処理としてバッシュに落とし込むべきだ。(中略)一つのスクリプトで引数を必ずステージングかプロダクションか取るようにして、引数がなければ引数を入れてくださいと注意を出す、黄色で注意を出すようにするのが最も安全で、かついちいち個別のコマンドを覚えたりする必要がないし、書き留めておく必要もないだろう。一般規則にするためには、もっと汎用的なルールとして読み換えて、規則として書くべきである。」
- **解釈(汎用規則)**: ①人間に貼らせる定型コマンド束(2行以上・オプション持ち・覚えられない類)は名前のついたスクリプト1本に落とす ②対象(環境・ホスト等)は必ず引数で受け、無ければ黄色の注意と使い方を表示して何もしない ③ツール固有の切替(terraform workspace 等の「間違えると混在事故になる」選択)はスクリプト内部で引数から機械的に決め、人間に選ばせない
- **文脈**: staging 再構築の手順1で terraform の workspace select + chdir + var 指定を人間に貼らせていた。適用例: infra/scripts/terraform_apply.sh / terraform_output.sh / terraform_destroy.sh
