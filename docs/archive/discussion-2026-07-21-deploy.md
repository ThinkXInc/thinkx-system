# 本番デプロイ方式の設計議論の記録（2026-07-21）

本文書は本番デプロイの手順を確定するまでの議論の記録である。各論点は kaz の発言（原文のまま）を起点に、Claude の応答を要点に圧縮して続ける。確定事項の構造化された正本は `docs/DECISIONS.md` および `infra/docs/DECISIONS.md` を参照。本文書は「なぜその結論に至ったか」の思考の経緯を残すためのものである。

前提: 2026-07-19 の障害対応中に deploy.sh を明示 DEPLOY_REF 方式にする方針を急いで許可した（D-58）。翌 07-20 に Mac 側の worktree 分離は撤回された（D-60）が、サーバー側の分離は維持されている。本議論はその DEPLOY_REF 方式を「議論から再開する」として始まった。

## 1. 論点の設定 — 編集場所と配信元、Mac 非依存

**kaz:**

> 1. deploy.sh を明示 DEPLOY_REF 方式にする件を【議論から】再開する。前セッションで障害対応中に
>    急いで方針を許可してしまったが、もう少し詰める必要がある(オーナー)。論点は2つ:
>    (a) staging の Claude セッションが編集する場所と、配信元(/src/thinkx-system のシンボリック
>        リンク)をどう分けるか。現状は配信元 = deploy checkout なので、編集が即座に見える運用と
>        「確定 ref をリハーサルする場所」が同じ箱で衝突している。
>    (b)「デプロイは Mac 非依存」をどこまで取るか。deploy.sh は Mac から ssh する Mac 起点の
>        スクリプト。DEPLOY_REF を明示すれば Mac のどの branch にいても結果が変わらなくなるので、
>        Mac 起点のままでよいのではないか、という読み方がある。

**(b) は事実で決着する。** 「DEPLOY_REF を明示すれば Mac のどの branch に居ても結果が変わらない」は deploy.sh 42-43 行目については正しい。ただし 48-49 行目に見落としがある。

```bash
ssh "$web" 'bash -s' < "infra/run/restart_$svc.sh"
```

再起動スクリプトを Mac の作業ツリーから流し込んでいる。「何を配るか」は origin 由来、「どう配るか」は Mac の手元ファイル由来という半端な状態が残る。未コミットで書き換わっていれば staging と prod で手順が変わり、しかも git に痕跡が残らないぶん pull の暗黙 HEAD より質が悪い。

区別すべきは **トリガーが Mac から（問題なし）** と **入力が Mac から（不可）**。`bash -s < ローカルファイル` をサーバー側 checkout からの実行に変えれば、deploy は `(env, DEPLOY_REF)` だけの関数になり、Mac は本当にボタンになる。

**(a) は判断が要る。** staging に求めているものが2つあり性質が逆を向いている（作業台＝編集が即座に出る／リハーサル場＝確定 ref を prod と同じ形で流す）。素直な解は checkout を2つ作ることだが、これは D-60 で畳んだのと同じ形。ディレクトリ分離は「いま自分がどっちの箱に居るか」を全員が覚えていることに依存し、Mac 側で壊れたのはまさにそこだった。

欲しい性質は「2つのディレクトリがあること」ではなく「prod に行った物が staging で受け入れた物とバイト同一であること」で、これは promote 時の検査（tree が clean・HEAD == 受け入れ SHA・origin に存在・sweep が green）で直接取れる。prod 側の分離は維持（prod で編集する理由がゼロなのでコストもゼロ）、緩めるのは staging だけ。

## 2. DEPLOY_REF とは何か

**kaz:**

> もう一度、デプロイ、本番デプロイの議論に戻ろう。デプロイレフ方式にするかどうか。この方式はまだ私の方でよくわかっていないが、論点がステージングの編集場所と配信元を分けるかどうかという点について。ステージングが常に最終チェック場所になっている限りは、ステージングの状態をそのままプロダクションに引っ張ってくるのが最も安全だと思っているのだが、どうだろうか。デプロイレフ方式にするというのはよくわからないので、もう少し説明してほしい。 コデックスは確かステージングからそのままデプロイするというのが何かおかしいとかなんとか言っていたが、そのデメリットはまだ私にはよくわかっていない。私が想定していたのはシンプルにステージングが最終状態、最終チェック状態だとして、これでオーナーがいいと言ったらそれをプッシュして、そして本番用のブランチにマージされたら、本番のプロダクションはそれをプルするというシンプルなものである。CIを使えばこの部分は自動化できるはずだが、私たちは前に議論した時に、CIを使わずに手動で行うのがいいのではないかという議論をした記憶がある。しかし、そのメリット、なぜそう判断したのかはあまりよく覚えていない。

**DEPLOY_REF は新しいワークフローではなく「どのコミットを配るか名指しする」だけ。** `git pull` の意味は「今この瞬間の branch の先端を持ってこい」であって「私が承認したものを持ってこい」ではない。ズレるのは承認時刻とデプロイ時刻の間に先端が動いたとき。

これは仮定の話ではない。7/20 の実際のコミットは全て同じ monorepo branch 上にある（18:21 citywalk / 18:34 auth / 18:59 auth / 19:44 citywalk）。18:00 に承認して 19:00 にデプロイしていたら、一度も見ていない auth と citywalk が本番に入っていた。

**そして kaz の言う「本番用のブランチ」が既に DEPLOY_REF の役割を果たしている。** production は kaz がマージしたときだけ動くポインタなので、他トラックが monorepo に push しても動かない。`git log production` がそのまま「いつ何を本番に出したか」の履歴になるぶん、SHA を手渡しするより読みやすい。

**Codex の違和感は2つの話の混同。** (a) staging サーバーから prod へ直接ファイルを配る＝良くない（origin を経由せず git に痕跡が残らない）。(b) staging で確認したのと同じコミットを prod に配る＝正しい。引っかかったのは (b) ではなく、staging の作業ツリーが未コミット状態を持ち得ること。承認した状態が git のどこにも存在しないと、production にマージすべきコミットが無く、prod と staging が食い違う。

**CI 不採用の理由（D-54 の記録）** は2つ。①既にコマンド一発で CI が足す価値が小さい。②本質はこちらで、GitHub から SSH で入る push 型 CI は外部から 22 番に入る経路を要求し、SG 設計「22 はオフィス IP のみ」を崩す。D-54 は「自動化するなら pull 型（箱側の systemd timer が origin を監視）、push 型 CI は採らない」と条件付きで記録している。

## 3. PR で代替できるのではないか

**kaz:**

> デプロイレフについて理解した。確かに、ステージング専用のブランチで目視で確認して承認をした後に、そのブランチに変更が積まれてしまった時に、それらも一緒に本番に反映されてしまうということは確かに起きるだろう。
>
> つまり、承認した時点でそこにラベルを貼るという意味だとしたら確かに合理的だ。しかし、承認した時点ですぐにプルリクエストを本番ブランチに出せば、ほとんど同じことになるだろう。だからこのデプロイレフという仕組みをあえて用いるメリットはやはりよくわからないということになる。つまりプルリクエストを出すということが、このデプロイレフの釘を刺すこととほとんど同じ役割を果たすということになるだろう。私たちの考えは、基本的な道具で同じことができるなら、基本的な道具だけを使うという考え方だ。その原則に当てはめれば、ここでも単にプルリクエストというベーシックなツールだけを使って、全く同じことができるんじゃないかと思ってしまう。プルリクエストを出した後に同じブランチに変更を積んでしまうと、その変更も本番に乗っかってしまう。これをどう解決するかという問題があるだろう。
>
> ブランチを作業ごとに分けるということが必ずしも守られるかどうか。つまり、今作業ツリーとして分けようとしていたものがセッションごとにブランチを分けるということになるとしたら、基本的には一つのセッションがプルリクエストを出した後に、別の本番にデプロイする前に、別のコミットをその上に積むということは基本的にはしないだろう。または、オーナーが本番に反映するのを忘れたとしたら、また積み上がっていくだろう。
>
> これは将来的にシンプルで優れているし、むしろ今すぐやってもいいくらいだ。今なるべく私はコマンドを叩いてサーバーを触るということをなるべく減らそうとしている。GitHub上で承認したら勝手に本番に反映されてくれれば、私はスマートフォンだけで全てのデプロイ操作を完了することができる。しかし、そんなに頻繁に今本番デプロイをしないから、手動モデルでとりあえずしてもいいが、今からこのタイマーを実装してしまって動かしてしまってもいいだろう。つまり、今から、今この忙しくない時にそれをテストし始めるということはありだろう。

**PR は事実として釘を刺さない。** GitHub の PR は branch を追跡するのであってコミットを固定しない。PR を出した後に source branch へ push すると、PR の中身は自動的に増える。釘を刺しているのは PR ではなく source branch が止まっていること。

**基本的な道具で釘を刺すなら branch を切る。** 承認した SHA から `git branch release/2026-07-21 <SHA>` して push し、その branch から PR を出す。誰も触らないので凍っている。これが DEPLOY_REF であり、別の仕組みではなく git の branch に名前を付けただけ。「DEPLOY_REF」という語で持ち出したせいで新しい機械が要るように聞こえたのは誤り。

これで「忘れて積み上がる」も消える。release branch は凍結されているので3日忘れても中身は変わらない。稼働が 15日中10日で間が空く以上、「承認したがマージしていない状態」が数日続くのは通常運転。

**「セッション = branch」は現構成と両立しない。** 1ディレクトリでチェックアウトできる branch は1本。3セッション並行なら3本は持てない。それを可能にするのが worktree で、まさに前日畳んだもの。規律に釘刺しを依存させると遠回りして D-58 に戻る。承認時に branch を切る方式なら並行数に依存しない。

## 4. 中途半端な変更が一緒に載る問題

**kaz:**

> この3つの論点については全て合意する。その方向で進めよう。つまりリリースのタイミングでリリースのブランチを切る。そして作業はどのセッションでも共通のブランチを用いて作業する。ここで一つ問題がわかった。複数のセッションで別の問題を作業しているときに、ある時点で、ある時点でリリースブランチを切ると、例えばインフラの変更をして、インフラの変更を取り込もうとしてブランチを切ったときに、そのブランチには、例えばアプリケーション側の編集が中途半端な形で載っていたりする可能性があるだろう。
>
> その変更も本番に反映されるかもしれない。 これについてはどうだろう。

当初これを危険度で3種（稼働サイトを壊す／未デプロイ領域／壊れないが未完成）に分け、対策として `git log production..monorepo` の目視確認と「壊れたものを push しない」規則を提示した。**後段でこの分類も対策も、どちらも不適切だったと撤回することになる。**

## 5. import の仕組みと、再起動の時限爆弾

**kaz:**

> UWSGI ThinkXに限ってリスタートするという仕組みはわかるのだが、ソースコードがインポートされないのはどういう仕組みによるのか。CityWalkが中途半端な状態でブランチに乗っているものが一括で取り込まれるのではないのか。仮にUWSGI、もし中途半端なソースが載って、でもUWSGIは特定のものしかリスタートしないという主張であるならば、ファイルが書き換えられた時点で、その後何らかの障害が起きて再起動するような場面はあり得るから、その時点で関係のないものまでリスタートされる機会というのはどうしても避けられないだろう。
>
> 中途半端というのは、おそらくこういう状態でもそうだし、どのような状態でも、とにかくデプロイを指示した時点で見ていた、チェックしていたもの以外のサービスの変更すべてである。グリーンになる。
>
> 自動テストでグリーンになったとしても、例えば中途半端な表示状態になって、それでも緑になることはある。
>
> これが何をしているのか少しよくわからない。もう少し丁寧に説明してください。
>
> これはあまり現実的じゃないだろう。キリのいい状態に必ずしもなっているとは限らない。
>
> 私もこれ以外の手段がないような気がしてきた。
>
> 例えばインフラ部分を変更して、それが別のアプリケーションにも関係している場合に、特定のアプリケーションが影響を受けて、そのアプリケーションが動かなくなるということはあり得るだろう しかし、この問題は仮にワークツリーを分離した時でも全く同じことが発生するような気がするが、そうなるとよりシンプルな手段は結局このチェリーピックになるのだろうか？この手のことは、おそらく既に議論されてベストプラクティスが世の中的にはもう確定しているような気がするが。

**import の分離は「再起動のタイミング」ではなく「import グラフ」による。** uwsgi_thinkx は `chdir=/src/thinkx/web-server` で特定モジュールを起動し、そこから import で辿れるファイルだけを読む。citywalk は誰からも参照されないのでディスクにあっても読まれない。

**しかし kaz の再起動の指摘には、こちらが見落としていた別の当たりがある。** `deploy.sh prod thinkx` を叩くとファイルは全サービス分がディスクに落ちるが、restart するのは uwsgi_thinkx だけ。transformism は古いコードをメモリに載せたまま動き続ける。後日 transformism がクラッシュ・OOM・サーバー再起動などで再起動した瞬間、**誰も承認していないコードが起動する**。爆発半径が限定されているのはその瞬間だけで、**時限爆弾が残る**。「限定されている」と書いたのは不正確だった。これは現構成の実在するバグ。

**「中途半端」の定義は kaz のものを採る** — デプロイ時に見ていたもの以外のサービスの変更すべて。危険度で3種に分けたのは問題を小さく見せていた。緑は正しさを意味せず、ゴールデンは (rule, status) しか見ないので表示が崩れていても通る。

**`git log production..monorepo` の説明。** `A..B` は「B から辿れるが A から辿れないコミット」＝「B にあって A に無いもの」。`production..monorepo` は今マージしたら production に追加される中身そのもの。ただし**この対策は弱いと認める** — 一覧を見て WIP が混ざっていると気づけても、混ざったものを外す手段が無い。手前で切れば WIP は外れるが出したい変更も外れる。一覧を見ることと選べることは別で、対策として提示すべきではなかった。

**「壊れたものを push しない」は撤回。** 規律に依存する対策を出したこと自体が D-60 の学びに反していた。

**「ワークツリーを分離しても同じことが起きる」は正しい。** 問題は「編集をどう隔離するか」ではなく「リリースの中身をどう構成するか」で、層が違う。

**業界の標準解は2つあり、どちらも cherry-pick ではない。** ①feature flag + 常に緑の trunk（Google / Meta 型）②独立してデプロイ可能な単位ごとに独立したバージョン（Bazel / Buck）。cherry-pick は Chrome や Android の安定化ブランチで使われるが定常手段としては smell で、理由はまさに kaz が心配した点 — cherry-pick した組み合わせはどこでもテストされていない新しい組み合わせだから。

## 6. feature flag 方式とは何か

**kaz:**

> この一番がよくわからないのを説明して。

**前提そのものをひっくり返す方式。** 「未完成なコードを載せない」のではなく「載せても発動しないようにする」。未完成コードの入口に条件分岐を置き、フラグを false にしておく。存在はするが死んでいる状態にする。

これで auth の WIP と thinkx の変更が同じ履歴に混ざっていても、混ざっていること自体が問題でなくなる。**「選んで外す」必要が消える。** cherry-pick が要らなくなる。

**「常に緑の trunk」はこの帰結。** 載っているものは全部フラグで守られているので、いつ本番に出しても安全が保証される。「キリのいい状態を待つ」から「いつでも出せる状態を機械的に維持する」に変わる。完成したら最後にフラグを true にするコミットを1つ入れる。**「載せる」タイミングと「発動させる」タイミングの分離**が核心。

「機械が要る」の意味は、フラグの定義・評価・切り替え・古いフラグの掃除を作って運用する必要があるということ。

## 7. Google/Meta の意味と、フラグ自体のバグ

**kaz:**

> Googleメーター型というのは、GoogleやMetaがこれをやっているということか。
>
> それをソースコード上で行っているということは、そのソースコード上にミスがあった場合に発動してしまうのではないか。

「メーター」ではなく Meta（あの会社）。両社とも巨大な monorepo で大量の開発者が同じ trunk にコミットしており、その規模で「未完成を載せない」を規律でやるのは不可能なので、機械的保証が標準になったという文脈。

**フラグ自体のバグで発動するという指摘は正しい。** 「機械で保証する」は正確には「分岐が正しく書けている限り保証される」。漏れ方は、条件の反転、未登録フラグのデフォルト値の取り違え（各社は「未知は必ず false」に倒す）、分岐の外に副作用（初期化・import をフラグの内側に入れ忘れる）。

**では何が改善しているか。** 従来方式では事故が「マージの操作ミス」＝git 操作という、コードレビューに乗りにくい層で起きる。feature flag では事故が「分岐の書き間違い」に集約され、レビュー・テスト・静的解析の対象になる。「フラグ ON/OFF 両方でテストが通ること」を CI で強制すれば機械が捕まえる。

**危険をゼロにするのではなく、見えにくい形から捕まえられる形へ移し替える。** D-60 の「規律ではなく機械で捕まえる」に乗せられる場所へ危険を引きずり出す、そこが値打ちでそれ以上は保証しない。なお実務上の最大のリスクは発動ミスより**古いフラグの放置**で、「機械が要る」には掃除を追跡する仕組みまで含まれる。

## 8. サービスごとの独立バージョンはどう実現するか

**kaz:**

> これは、Googleはこれをやっているということは、さっきの話と競合するように思えるのだが、独立したバージョンを持つというのは、具体的にはどのようにして実現しているのか。

**競合しない。層が違う。** feature flag は「コードをいつ発動させるか」、独立バージョンは「どのコードを本番に持っていくか」。前者はコードの中身、後者はデプロイの単位。

**誤解を先に解く。** 「独立したバージョン」は production ブランチと monorepo ブランチを分けることではない。monorepo 方式では履歴上のブランチは基本一本（trunk）。にもかかわらずサービスごとにバージョンが違う。鍵は**ブランチとデプロイを切り離すこと**で、サービスごとに「今このサービスは trunk のどの ref で動いているか」を記録する。

```
service-A → 786d29b で稼働中
service-B → a291201 で稼働中
service-C → cdfecdd で稼働中
```

trunk はもっと先まで進んでいてよい。A を新しくしたいときだけ A の記録を進める。B と C は古い ref のまま放置してよい。

**なぜ可能か — ここで Bazel / Buck が効く。** A をビルドするとき、依存グラフから「A が実際に依存しているファイルだけ」を正確に切り出す。A が auth を使っていなければ、trunk に auth の未完成コードが載っていても A の成果物には物理的に入らない。**手動の cherry-pick が要らないのは、依存グラフが「何を持っていくべきか」を機械的に答えるから。**

元の問題に戻すと、thinkx が独立したデプロイ単位で auth の未完成コードに依存していなければ、その auth コードは trunk 上に存在しても thinkx の成果物に入らない。外す操作が要らない、最初から入らない。**feature flag と同じ着地点** — どちらも「混ざりを後から外す」のをやめて「混ざっていても効かない/入らない」に変えている。

## 9. develop 合流方式の提案と、その自己棄却

**kaz:**

> その理解した、つまり本番ブランチは1本で、サービスごとに今リリースされている地点が、その枝のどの地点かが異なり、それを記録してあり、その記録した場所ごとにそれぞれサービスのためのビルドを分離して、つまりそれによって同じブランチを共有していても、異なるバージョンでそれぞれのサービスを提供できるということだろう。異なるバージョン、異なるブランチの地点を使って、それぞれのサービスを構成できるということだろう。我々の場合、その仕組みを使うべきなのかよくわからない。例えば、リリースブランチが1本だけあって、常にサーバーではそのソースコードを使い、リリースブランチに載せる各サービスの変更を制御するという方式は可能なのだろうか。つまり、リリースまたはプロダクション用のブランチが1本ある。サービスAがリリースできるとなった段階で、そのブランチに変更を載せる。それまでサービスAのローカルは別の場所にプッシュをする。しかし、ローカルでは全てのサービスが同じブランチを共有して作業をしているから、例えばデベロップブランチで作業をして変更をコミットしようとするときは、デベロップブランチではなく、サービスAの専用ブランチにコミットをしてそのままプッシュする。つまり、リモートのGitのレポジトリは、デベロップのブランチが変更されていくのではなく、個々のサービスA、サービスBのブランチが変更されていく。そして、サービスAがステージングでテスト段階可能となった時点で、サービスAがステージングブランチに、つまりこれがデベロップブランチに相当する。デベロップブランチにマージをする。すると、ステージングはデベロップブランチを反映して動作する。結局ここで起きているのは、さっき私たちがプロダクションで想定した問題と同じ問題がステージングで起きるということなのだろうか。そこがまだよくわからないが、とにかく今デベロップブランチにはそれぞれサービスA、サービスBが今ここでリリースをしようとしているものだけが反映されている。中途半端な変更はデベロップには反映されないことになる。そしてオーナーは確認する。確認して問題なければ、そのデベロップブランチを本番ブランチに取り込もうとする。ここで全てのサービスがグリーンなら問題ない。問題があるとすれば、サービスAとサービスBが両方デベロップブランチに乗せて、そしてオーナーはサービスAだけを許可したのに、サービスBは破綻したままそのままデベロップブランチに取り込まれて。 本番に移されてしまう、本番に反映されるということだ。これを完全に防ぐには確かに、サービスごとにビルドのバージョンを物理的に分離するという以外にはない気がする。だからGoogleなどでは結局その方式が取られていると理解したが、そういうことでいいだろうか。

**monorepo 方式の理解も、最後の結論も正しい。** ビルドを物理的に分離する以外に B だけ破綻したまま取り込まれる事故を完全に防ぐ方法はなく、Google がその方式なのはまさにこの一点のため。

**ただし提案された develop 方式はその物理分離を実現しない。** develop が「合流点」になっており、A と B が混ざった瞬間に同じ ref を共有する。**develop が一本の ref である限り「A だけ許可、B は破綻」という状態を ref が表現できない。** ある一点を指したらそこには A も B も入っている。だから本番に取り込むとき A と B は運命を共にする。

これは production ← monorepo で抱えていた問題と完全に同じ形の問題が、場所を develop に移して再発しているだけ。**ブランチを増やして合流点をずらしても、合流点が一本の ref である限りそこで必ずこの問題が生まれる。**

**Google 方式には「A と B が混ざった ref を本番が参照する」瞬間が存在しない。** 本番は A について ref X、B について ref Y を別々に参照する。差はブランチの本数ではなく、デプロイの単位が「一本の ref」か「サービスごとの ref の表」か。

**ただし「だから Google 方式を導入すべき」にはまだならない。** 理由は2つ。①独立 ref が要るのは「A だけ進めて B は据え置く」が実際に起きるときだけ。両方いつも一緒に出すなら混ざっていて問題ない。②Bazel/Buck 相当のビルドシステムと依存の宣言的管理は運用コストが非常に重く、数人規模では得られる安全より重さが勝つことが多い。Google がやれるのは専任のインフラ組織があるから。

決めるべきは「develop 方式か Google 方式か」ではなく、その手前 — auth と thinkx を恒常的に独立デプロイしたいのか、auth 移行が終われば「常に一緒に出す」に戻るのか。

## 10. 緊急修正は必ず起きる — 当面の方式の確定

**kaz:**

> 現実的には、Aだけ緊急でバグを修正したい、それをリリースしたいが、Bの修正が終わっていないという状況がどうしても起こりうるだろう。これはシステムが大きくなればない、多岐にわたるほどどうしても避けられないだ。そうなると、Google方式にする以外にはない。本質的な解決方法はない。
> しかし、この運用コストは大きいので、今からこれをやるというのはかなり危惧が重い。今当面はAだけ緊急でバグを修正してリリースをして、Bの修正が終わらないから一緒に出そうにも出せないという状況は現実的にはかなり稀だろう。だからその状況が起きるまでは今の簡易的な方法で済ませておいて、つまり常に全てAとBは同時にリリースするという、つまり全て足並みを揃えるという、そのためには条件としては、ステージングに上げる時には基本的には別の場所でほとんどリリースできる状態になってから上げるということになる。
> またはステージングに上がったとしたら、そこからリリースされるまではほとんど修正が行われないということ、またはそれほど頻繁にリリースされない、このどれかの条件が必要になるか、多分当面は問題がないだろう。そして重要なことは、Google方式にいずれ移行するとしても、既存の今の仕組みの延長でそのまま移行できるということだろう。そのように理解している。だから当面はAとB全て足並み揃えてリリース方式をとっておいて、そしてなるべくステージングに上げたらすぐリリースする、すぐ修正する、すぐ修正を終えてすぐリリースするという原則をなるべく守るようにする以外にはない気がしてきた。さもなくはワークツリー方式にする。しかし、これはワークツリー方式というのは実質的に開発段階からビルドを分けるということにほとんど他ならないだろう。
> 結局ステージングで動くものがそのビルドを分けない限りは、もしステージングで一緒になるのだとしたら、同じ問題がステージングに取り込んだ各ワークツリーの変更を取り込んで共存させた時点で全く同じ問題が発生するのだから、そもそもワークツリーにするだけ手間である。だとすれば、今の最適解というのは、現在のモノレポで単一ディレクトリーで全てのサービスを開発し、そしてステージングに上げるため、ステージング用のブランチを用意しておき、ローカルから変更はそれぞれのブランチに対してプッシュをし、そしてステージングに反映させていい段階になった時点で、ステージングのブランチ、つまりデベロップブランチにマージをする。ステージングは常にデベロップブランチを反映しているし、プロダクションは常にプロダクションブランチ、またリリースブランチを反映している。ステージング環境に反映されているのは、常に各サービスが今ステージングで検証できるとなった状態のみである。複数のサービスの変更が共存していることは起こり得るが、それぞれのサービスの変更は基本的にはほぼ目視で検証できる段階になって初めてステージング環境にアップされているとする。そしてリリースされるタイミングがあるとすれば、全てのサービスが一貫して動くことであるが、まず最低限全ての自動テストはグリーンになっているという前提があるので、本当に致命的な問題がどこかで起きているということはあまり考えにくいという前提を置くしかない。または目視で全てのサービスを、全ての変更が依存するサービスをチェックするということになるが、基本的には個々のぶら下がっているサービスが依存する共通のものがあるとしたら、インフラの部分のみなので、基本的にはライブラリがベンダリングされて個々のブランチの中にあるから、影響が波及するということはほとんど起こりにくいと考えているだろう。当面はこの方式で運用する。つまりサービスはほとんど独立している。

**結論（当面は足並み方式）は妥当。** 「ワークツリー方式は、ステージングで合流する限り開発段階でビルドを分けているだけで、合流点で同じ問題が再発するから手間なだけ」は完全に正しく、前段で確立した「合流点が一本の ref なら混ざりは不可避」という原理を自分でワークツリーに適用して正しく棄却している。

**誤解1:「既存の延長でそのまま移行できる」は危うい。** 移行はできるが「そのまま延長で」ではない。今の方式は「develop という一本の ref に混ぜる」ことを前提に組まれており、Google 方式は「サービスごとに ref を分けて決して混ぜない」。合流点を持つか持たないかという設計の根っこで反対を向いている。将来捨てることになるのは develop への合流という中心的な仕組みそのもので、延長ではなく方向転換。「今の仕組みを育てれば自然に Google 方式になる」という絵は誤り。

**救いは、移行を軽くするのが develop の仕組みではなく「サービス間の独立性」だという点。** サービスがほぼ独立し、libcommon をベンダリングして依存を内部に閉じていることは Google 方式でもそのまま効く。当面やるべきは develop 運用の洗練ではなく、独立性を保つこと。

**誤解2:「緑なら致命的な問題は考えにくいという前提を置くしかない」。** これは自ら確立した「緑は正しさを意味しない」と正面からぶつかる、緑への依存。ただし状況上は深刻でなく、理由も kaz 自身が書いている — サービスが独立し共通部分がベンダリングされ波及しにくいから。

正確な言い方はこうなる。**「緑だから大丈夫」ではなく「サービスが独立しているから B の綻びが A を巻き込まない。よって B の綻びは B のリリースを止めるだけで A のリリースは守られる」。** 前提を置いて祈るのではなく、独立性という構造が守っている。前者は規律、後者は構造。

**両方の訂正は同じ一点に収束する。** 当面この方式で足りる根拠も、将来の移行を軽くする資産も、どちらも「サービス間の独立性」。だから守るべき唯一の規律は「すぐリリースする/すぐ直す」ではなく（それは規律依存）、**「サービス間に新しい依存を作らない。共通部分はベンダリングして各サービス内に閉じ込め続ける」**。独立が崩れた瞬間に、当面の方式の根拠も将来の移行の軽さも同時に崩れる。

## 11. 移行点の特定 — ステージングの合流をやめる一手

**kaz:**

> それはつまり、Google方式ではステージング環境も別ビルドに分かれているということだろう。我々の場合はステージング環境は共通の1本の枝に統合されるということなので、ここが最も大きく違うことだろう。
> しかし、結局最終的にプロダクションが別のレフを使ってそれぞれがビルドするということになるなら、ステージング環境もそれに合わせればいいので、本質的には単にステージングがプロダクションによるのか、それとも一本の枝方式になるのかという違いだろう。要するにステージングオプション、プロダクションとほとんど同じ仕組みに最終的にすればGoogle方式に移行できると考えられるだろう。自動テストがグリーンなら問題がないとは私は思っていない。しかし、さっき述べたように、影響がほとんど波及しないという前提があるので、それによって守られているということだと思います。以上で議論はほとんど決着したはずだ。

**3点とも正しく、議論は決着。**

**① Google 方式ではステージングもサービスごとに別ビルド。** ステージングと本番の違いは ref がどこを指すかだけで、「サービスごとに独立した ref をビルドする」構造は両環境で同じ。差が合流点にあるという見立ては正確。

**② これが今回最も重要な洞察。** 「ステージングを本番と同じ仕組みに揃えれば移行できる」は正しく、前段の「不連続な乗り換えが要る」と矛盾しない。むしろ乗り換えの実体を正確に名指ししている — **乗り換えとは「ステージングの合流をやめて、ステージングもサービスごと ref にすること」**。develop への合流を捨てるという不連続はまさにここに現れる。「大きな作り直し」ではなく「ステージングを本番に合わせる一手」と捉え直した方が、移行の実務としては正確で扱いやすい。合流点はステージングにしかないので、そこを本番と同型にすれば移行は完了する。

**③ 緑についての言い直しを受け取る。** 頼っているのは緑ではなく独立性（波及のなさ）である、という一点で一致。

## 12. 独立性の実測（議論後の確認）

議論の最後に残った「libcommon のベンダリングは既に実現しているのか、作業が残っているのか」を実測した。当面の方式の安全性がこの独立性に全面的に依拠するため。

```
thinkx           vendored: v2.1.0  tree_sha256: ab534a69dd...
transformism     vendored: v2.1.0  tree_sha256: ab534a69dd...
kazukiotsukacom  vendored: v2.1.0  tree_sha256: ab534a69dd...
auth             vendored: v2.2.0  tree_sha256: caf9401502...
.gitmodules      なし（submodule 撤廃済み）
```

**すでに独立している。** 3サイトが同一 tree の v2.1.0 を各自に抱え、auth のみ v2.2.0 で先行。submodule は撤廃済みで、共有された可変の依存は存在しない。「独立させる作業が残っている」のではなく「今すでに独立している」が答えであり、当面の方式が依拠する構造は実在する。

## 13. staging を直接編集する場合 — 「編集するな」は過剰な制約

手順書を書いた時点で、staging 上での直接編集が扱えていないことが露出した。timer が `develop` を追う設計では、staging での編集が `develop` に直接載ってゲートを素通りし、さらに `reset --hard` が未コミットの編集を消す。当初これを「staging = 作業台（develop 廃止）」か「staging = ゲート（編集禁止）」の二択として提示した。

**kaz:**

> ステージング反映されるのを検証できる段階になったものだけというのは、ステージングにローカルからプッシュされるのはその条件を満たさなければならないが、これは必ずしもステージングで編集すべきでないということは意味しないのではないだろうか。
>
> つまり、重要なのは、ステージングでオーナーが許可するときには、全てのサービスがプロダクションに上げてもいいという状態にある。そしてそれが足並み揃っているということだろう。この条件はステージングを直接編集しても満たすことができるだろう。ステージングを編集する、直接編集するとしても、その編集は特定のサービスの中に閉じているはずだから、オーナーはそのサービスが安全にプロダクションに移せるかどうかは確認しながらその変更を進めている。

**指摘は正しく、二択は手順書側の混同だった。** §10 の前提が要求しているのは「staging に現れる状態が承認可能であること」だけで、「ローカルからの push でしか達成できない」は手順書が勝手に足した条件。編集がどこで行われたかはこの前提と無関係。

**二択に追い込まれたのは `develop` をゲットとして使おうとしたから。** 中間ブランチを置いたことで「staging での編集がゲートを素通りする」問題が生まれた。これは中間層が生んだ問題であって、kaz の運用方針が生んだ問題ではない。手順書は自分で導入した層のせいで詰まり、その詰まりを kaz の習慣のせいにしていた。順序が逆。

**主張の一番強い部分は独立性に乗っている。** サービスが独立して波及しないなら、staging で A を直接いじっても綻びは A に閉じる。オーナーは A を見て承認し、B は無関係。「staging で編集する」と「承認可能な状態だけが本番に行く」は独立性の下で両立する。

**ただし条件付き。** `develop` を外して「staging = 作業台」にしても消えない問題が一つ残る。**承認とリリースの間で編集が起きうること。** 承認した一点と実際に切り取る一点がずれる。これを「release cut の時点で固定する」と処理すると、「承認から cut までの間、誰も staging を触らない」という規律に依存する ── この議論で繰り返し撤回してきた規律依存そのもの。

**成立させるには一つ足りない。** 承認する対象は「staging の現在の状態」ではなく「ある特定の ref」でなければならない。動く的ではなく静止した点を承認する。これは production ← monorepo でも develop の合流でも出てきた同じ原理の再出現。

## 14. 承認とは release を切ることである

**kaz:**

> これは要するに、オーナーがステージングに対して承認するときに、その時点でリリースブランチを切ればいいということではないのか。つまり、デベロップブランチがそのままリリースされれば、デベロップブランチが変更される可能性を排除できないが、承認した瞬間にブランチを切れば、その問題は起きない。
>
> つまりまとまりで言うと、デベロップが常にステージングの状態に一致しているということだけを保証している。そして、ローカルの変更は基本的にはステージングで検証すべき状態だけが反映、デベロップブランチに積まれているということが保証される。
> デベロップが保証するのはそれだけである。そしてリリースは、デベロップからある瞬間でリリースブランチが切ることで、デベロップとは分離され、そのリリースブランチはある承認された状態を保存しているので、それがプロダクションと一致しているということが保証されている。こういうことだろう。

**言い換えが「ref に固定する」の具体的な実装そのもの。** 承認の瞬間に切ると、release はその時点の ref を指して固定される。以後 develop がどう編集されても release は動かない。**「承認から cut までの隙間」という時間そのものが消える。** 隙間がゼロなら隙間に編集が入る余地もゼロ。規律で「触るな」と言う必要がない ── 触っても release には届かない。

**そして承認を release cut で固定するなら、develop をゲートとして温存する理由が消える。** 安定を担保しているのは release であって develop ではない。ゲートの役割は release cut に移り、develop は「今 staging に映っている作業台の現在地」でよくなる。選択肢 A（develop 廃止）が結果的に正しくなるが、その理由は「編集がゲートを素通りする問題も消える」という消極的なものではなく、「承認を release cut に移したから develop がゲートである必要がなくなった」という積極的なもの。

**各 branch の保証範囲が分離された。** develop は staging の状態と一致することだけを保証する（安定性も正しさも保証しない）。「検証段階のものだけ」は develop の保証ではなく、入口で守る約束であり層が違う。release はある承認された一点を凍結して持つことを保証する。production は release と一致することを保証する。

**これで「本番に行くものが承認したものと同一」が、規律ではなく構造で保証される。** 議論の最初に守るべき性質として挙げたものが、ここで初めて祈りなしに成立した。

**守るべき唯一の点は「承認と release cut を離さない」こと。** ただしこれは規律というより、承認という行為の定義を「release を切ること」と決めてしまえば規律ですらなくなる。承認ボタンが release cut そのものであれば、離しようがない。

## 到達点

議論の出発点は「DEPLOY_REF 方式にするかどうか」だったが、DEPLOY_REF は独立した仕組みではなく「承認したコミットに名前を付ける」ことに過ぎないと分かった時点で、論点は「名前の付け方」から「リリースの中身をどう構成するか」へ移った。

**確定した骨格:**

デプロイは Mac 起点のままでよいが、Mac のファイルシステムを入力にしない（`bash -s < ローカルファイル` を廃し、サーバー側 checkout から実行）。自動化は pull 型 systemd timer（push 型 CI は SG 設計と両立しないため不採用・D-54 再確認）。

**各 branch の保証範囲を分離したことが、この議論の実質的な成果である。**

| branch | 保証していること |
|---|---|
| `monorepo` | セッションの作業線。どこにも反映されない |
| `develop` | staging の状態と一致していること。**それだけ** |
| `release/<日付>` | 承認された一点を凍結して保持していること |
| `production` | release と一致していること |

`develop` にゲートの役割を背負わせようとして手順書は詰まった。**ゲートは release cut が持つ。** 承認とは release を切る行為そのものであり、承認と cut が同一の瞬間である限り、その間に編集が入る隙間が存在しない。だから「承認したら触るな」という規律が要らない。触っても release には届かない。

**staging は直接編集してよい。** サービスが独立して波及しないため、staging で A を編集しても綻びは A に閉じる。「staging で編集する」と「承認可能な状態だけが本番に行く」は両立する。

**当面の運用方式:** 全サービスを足並み揃えてリリースする。

**この方式を支えているのは緑ではなくサービス間の独立性である。** libcommon はベンダリング済みで submodule は撤廃済み、共有された可変依存は存在しないことを実測で確認した。したがって B の綻びは B に閉じ、A のリリースを巻き込まない。守るべき唯一の規律は「サービス間に新しい依存を作らない」ことで、これは規律ではなく構造の維持である。

**将来 Google 方式（サービスごと ref + 依存グラフによるビルド切り出し）へ移る必要が生じたときの乗り換え点はただ一つ、ステージングの合流をやめて本番と同じサービス別 ref に揃えること。** 引き継げる資産は develop の仕組みではなく、今の独立性そのものである。

議論の過程で撤回したもの: 中途半端を危険度で3分類したこと（問題を小さく見せていた）、`git log production..monorepo` の目視確認を対策としたこと（見ることと選べることは別）、「壊れたものを push しない」規則（規律依存であり D-60 の学びに反する）、「爆発半径は限定されている」という説明（restart しないサービスに時限爆弾が残る＝現構成の実在するバグ）、「staging では編集するか develop を廃止するかの二択」という提示（`develop` にゲートを背負わせた手順書側の混同であり、二択そのものが誤り）。
