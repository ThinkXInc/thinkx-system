## 1. 論点の設定 — 編集場所と配信元、Mac 非依存

**kaz:**

> 1. deploy.sh を明示 DEPLOY_REF 方式にする件を【議論から】再開する。前セッションで障害対応中に
>    急いで方針を許可してしまったが、もう少し詰める必要がある(オーナー)。論点は2つ:
>    (a) staging の Claude セッションが編集する場所と、配信元(/src/thinkx-system のシンボリック
>        リンク)をどう分けるか。現状は配信元 = deploy checkout なので、編集が即座に見える運用と
>        「確定 ref をリハーサルする場所」が同じ箱で衝突している。
>    (b)「デプロイは Mac 非依存」をどこまで取るか。deploy.sh は Mac から ssh する Mac 起点の
>        スクリプト。DEPLOY_REF を明示すれば Mac のどの branch にいても結果が変わらなくなるので、
>        Mac 起点のままでよいのではないか、という読み方がある。

オーナーの論点:

- staging の編集場所と配信元が同じ箱で衝突している。分けるべきか。
- DEPLOY_REF を明示すれば Mac のどの branch にいても結果が同じになるので、Mac 起点のままでよいのではないか。
- 障害対応中に急いで許可した方針なので、議論から詰め直したい。

**(b) は事実で決着する。** deploy.sh 42-43 行目については読みの通り。ただし 48-49 行目に見落としがある。

```bash
ssh "$web" 'bash -s' < "infra/run/restart_$svc.sh"
```

再起動スクリプトを Mac の作業ツリーから流し込んでいる。「何を配るか」は origin 由来、「どう配るか」は Mac の手元ファイル由来という半端な状態が残る。未コミットで書き換わっていれば staging と prod で手順が変わり、しかも git に痕跡が残らないぶん pull の暗黙 HEAD より質が悪い。区別すべきは **トリガーが Mac から（問題なし）** と **入力が Mac から（不可）**。

**(a) は判断が要る。** staging に求めているものが2つあり性質が逆を向いている（作業台＝編集が即座に出る／リハーサル場＝確定 ref を prod と同じ形で流す）。素直な解は checkout を2つ作ることだが、これは D-60 で畳んだのと同じ形。欲しい性質は「2つのディレクトリがあること」ではなく「prod に行った物が staging で受け入れた物とバイト同一であること」で、これは promote 時の検査で直接取れる。

Claudeの回答要点:

- (b) は正しいが、`bash -s < ローカルファイル` という別の Mac 依存が残っている。トリガーが Mac からは可、入力が Mac からは不可。
- (a) は checkout を2つ作る解を採らない。D-60 で畳んだのと同じ形（規律依存）だから。
- 欲しい性質は「バイト同一」であり、ディレクトリ分離ではなく promote 時の検査で取れる。prod 側の分離は維持、緩めるのは staging だけ。

## 2. DEPLOY_REF とは何か

**kaz:**

> もう一度、デプロイ、本番デプロイの議論に戻ろう。デプロイレフ方式にするかどうか。この方式はまだ私の方でよくわかっていないが、論点がステージングの編集場所と配信元を分けるかどうかという点について。ステージングが常に最終チェック場所になっている限りは、ステージングの状態をそのままプロダクションに引っ張ってくるのが最も安全だと思っているのだが、どうだろうか。デプロイレフ方式にするというのはよくわからないので、もう少し説明してほしい。 コデックスは確かステージングからそのままデプロイするというのが何かおかしいとかなんとか言っていたが、そのデメリットはまだ私にはよくわかっていない。私が想定していたのはシンプルにステージングが最終状態、最終チェック状態だとして、これでオーナーがいいと言ったらそれをプッシュして、そして本番用のブランチにマージされたら、本番のプロダクションはそれをプルするというシンプルなものである。CIを使えばこの部分は自動化できるはずだが、私たちは前に議論した時に、CIを使わずに手動で行うのがいいのではないかという議論をした記憶がある。しかし、そのメリット、なぜそう判断したのかはあまりよく覚えていない。

オーナーの論点:

- DEPLOY_REF 方式がまだ理解できていない。説明してほしい。
- staging が最終チェック場所である限り、その状態をそのまま本番に引くのが最も安全ではないか。
- 想定しているのは「承認 → push → 本番ブランチにマージ → prod が pull」というシンプルなもの。
- CI を使わず手動と決めた記憶があるが、その理由を覚えていない。

**DEPLOY_REF は新しいワークフローではなく「どのコミットを配るか名指しする」だけ。** `git pull` の意味は「今この瞬間の branch の先端を持ってこい」であって「私が承認したものを持ってこい」ではない。ズレるのは承認時刻とデプロイ時刻の間に先端が動いたとき。

これは仮定の話ではない。7/20 の実際のコミットは全て同じ monorepo branch 上にある（18:21 citywalk / 18:34 auth / 18:59 auth / 19:44 citywalk）。18:00 に承認して 19:00 にデプロイしていたら、一度も見ていない auth と citywalk が本番に入っていた。

**そして kaz の言う「本番用のブランチ」が既に DEPLOY_REF の役割を果たしている。** production は kaz がマージしたときだけ動くポインタなので、他トラックが monorepo に push しても動かない。`git log production` がそのまま履歴になるぶん、SHA を手渡しするより読みやすい。

**Codex の違和感は2つの話の混同。** (a) staging サーバーから prod へ直接ファイルを配る＝良くない。(b) staging で確認したのと同じコミットを prod に配る＝正しい。引っかかったのは (b) ではなく、staging の作業ツリーが未コミット状態を持ち得ること。承認した状態が git のどこにも存在しないと、マージすべきコミットが無い。

**CI 不採用の理由（D-54 の記録）** は2つ。①既にコマンド一発で CI が足す価値が小さい。②本質はこちらで、GitHub から SSH で入る push 型 CI は外部から 22 番に入る経路を要求し、SG 設計「22 はオフィス IP のみ」を崩す。

Claudeの回答要点:

- DEPLOY_REF は別建ての仕組みではなく「承認したコミットを名指しする」だけ。`git pull` は「今の先端」であって「承認したもの」ではない。
- 7/20 の実履歴で、承認と反映の間に3トラックが push しており、見ていない変更が本番に入る事故は実在の危険。
- kaz の言う「本番用ブランチ」が既に DEPLOY_REF そのもの。しかも `git log production` が履歴になるぶん読みやすい。
- Codex の違和感の実体は「staging の未コミット状態は git で名指しできない」こと。
- CI 不採用の本当の理由は SG 設計（22 はオフィス IP のみ）との衝突。pull 型なら両立する（D-54）。

## 3. PR で代替できるのではないか

**kaz:**

> デプロイレフについて理解した。確かに、ステージング専用のブランチで目視で確認して承認をした後に、そのブランチに変更が積まれてしまった時に、それらも一緒に本番に反映されてしまうということは確かに起きるだろう。
>
> つまり、承認した時点でそこにラベルを貼るという意味だとしたら確かに合理的だ。しかし、承認した時点ですぐにプルリクエストを本番ブランチに出せば、ほとんど同じことになるだろう。だからこのデプロイレフという仕組みをあえて用いるメリットはやはりよくわからないということになる。つまりプルリクエストを出すということが、このデプロイレフの釘を刺すこととほとんど同じ役割を果たすということになるだろう。私たちの考えは、基本的な道具で同じことができるなら、基本的な道具だけを使うという考え方だ。その原則に当てはめれば、ここでも単にプルリクエストというベーシックなツールだけを使って、全く同じことができるんじゃないかと思ってしまう。プルリクエストを出した後に同じブランチに変更を積んでしまうと、その変更も本番に乗っかってしまう。これをどう解決するかという問題があるだろう。
>
> ブランチを作業ごとに分けるということが必ずしも守られるかどうか。つまり、今作業ツリーとして分けようとしていたものがセッションごとにブランチを分けるということになるとしたら、基本的には一つのセッションがプルリクエストを出した後に、別の本番にデプロイする前に、別のコミットをその上に積むということは基本的にはしないだろう。または、オーナーが本番に反映するのを忘れたとしたら、また積み上がっていくだろう。
>
> これは将来的にシンプルで優れているし、むしろ今すぐやってもいいくらいだ。今なるべく私はコマンドを叩いてサーバーを触るということをなるべく減らそうとしている。GitHub上で承認したら勝手に本番に反映されてくれれば、私はスマートフォンだけで全てのデプロイ操作を完了することができる。しかし、そんなに頻繁に今本番デプロイをしないから、手動モデルでとりあえずしてもいいが、今からこのタイマーを実装してしまって動かしてしまってもいいだろう。つまり、今から、今この忙しくない時にそれをテストし始めるということはありだろう。

オーナーの論点:

- 承認時点でラベルを貼るという趣旨は理解した。ただ、承認時点で PR を出せばほぼ同じではないか。
- 基本的な道具で同じことができるなら基本的な道具だけを使う、が原則。PR で足りるなら DEPLOY_REF は要らない。
- ただし PR を出した後に同じブランチに積まれたらどうするか、という問題は残る。
- pull 型 timer は将来的に優れているし今すぐやってもいい。GitHub で承認すればスマホだけでデプロイが完結する。忙しくない今テストを始めるのはあり。

**PR は事実として釘を刺さない。** GitHub の PR は branch を追跡するのであってコミットを固定しない。PR を出した後に source branch へ push すると、PR の中身は自動的に増える。釘を刺しているのは PR ではなく source branch が止まっていること。

**基本的な道具で釘を刺すなら branch を切る。** 承認した SHA から `git branch release/2026-07-21 <SHA>` して push し、その branch から PR を出す。誰も触らないので凍っている。これが DEPLOY_REF であり、git の branch に名前を付けただけ。

これで「忘れて積み上がる」も消える。release branch は凍結されているので3日忘れても中身は変わらない。稼働が 15日中10日で間が空く以上、「承認したがマージしていない状態」が数日続くのは通常運転。

**「セッション = branch」は現構成と両立しない。** 1ディレクトリでチェックアウトできる branch は1本。3セッション並行なら3本は持てない。それを可能にするのが worktree で、まさに前日畳んだもの。

Claudeの回答要点:

- PR は branch を追跡するのでコミットを固定しない。出した後に push されれば PR の中身が増える。釘を刺すのは source branch が止まっていること。
- 基本的な道具での実現は「承認した SHA から branch を切る」。これが DEPLOY_REF の実体で、新しい機械は要らない。
- 凍結されるので「忘れて積み上がる」問題も消える。数日空く稼働パターンと相性がよい。
- 「セッション = branch」は単一ディレクトリと両立しない（worktree が要る）。この時点では規律依存として退けた。

## 4. 中途半端な変更が一緒に載る問題

**kaz:**

> この3つの論点については全て合意する。その方向で進めよう。つまりリリースのタイミングでリリースのブランチを切る。そして作業はどのセッションでも共通のブランチを用いて作業する。ここで一つ問題がわかった。複数のセッションで別の問題を作業しているときに、ある時点で、ある時点でリリースブランチを切ると、例えばインフラの変更をして、インフラの変更を取り込もうとしてブランチを切ったときに、そのブランチには、例えばアプリケーション側の編集が中途半端な形で載っていたりする可能性があるだろう。

## 5. import の仕組みと、再起動の時限爆弾

**kaz:**

> UWSGI ThinkXに限ってリスタートするという仕組みはわかるのだが、ソースコードがインポートされないのはどういう仕組みによるのか。CityWalkが中途半端な状態でブランチに乗っているものが一括で取り込まれるのではないのか。仮にUWSGI、もし中途半端なソースが載って、でもUWSGIは特定のものしかリスタートしないという主張であるならば、ファイルが書き換えられた時点で、その後何らかの障害が起きて再起動するような場面はあり得るから、その時点で関係のないものまでリスタートされる機会というのはどうしても避けられないだろう。
>
> 中途半端というのは、おそらくこういう状態でもそうだし、どのような状態でも、とにかくデプロイを指示した時点で見ていた、チェックしていたもの以外のサービスの変更すべてである。グリーンになる。
>
> 自動テストでグリーンになったとしても、例えば中途半端な表示状態になって、それでも緑になることはある。
>
> これが何をしているのか少しよくわからない。もう少し丁寧に説明してください。
>
> これはあまり現実的じゃないだろう。キリのいい状態に必ずしもなっているとは限らない。
>
> 私もこれ以外の手段がないような気がしてきた。
>
> 例えばインフラ部分を変更して、それが別のアプリケーションにも関係している場合に、特定のアプリケーションが影響を受けて、そのアプリケーションが動かなくなるということはあり得るだろう しかし、この問題は仮にワークツリーを分離した時でも全く同じことが発生するような気がするが、そうなるとよりシンプルな手段は結局このチェリーピックになるのだろうか？この手のことは、おそらく既に議論されてベストプラクティスが世の中的にはもう確定しているような気がするが。

オーナーの論点:

- import されない仕組みが分からない。ファイルが書き換わっている以上、後で何かの障害で再起動すれば関係ないものまで起動するのではないか。
- 「中途半端」の定義は、デプロイ時に見ていたもの以外のサービスの変更すべて。緑でも表示が崩れていることはある。
- `git log production..monorepo` が何をしているのか分からない。
- 「壊れたものを push しない」は非現実的。キリのいい状態とは限らない。
- ワークツリーを分離しても同じ問題が起きる気がする。結局 cherry-pick か。ベストプラクティスは既に確定しているのでは。

**import の分離は「再起動のタイミング」ではなく「import グラフ」による。** uwsgi_thinkx は特定モジュールから import で辿れるファイルだけを読む。citywalk は誰からも参照されないのでディスクにあっても読まれない。

**しかし kaz の再起動の指摘には、こちらが見落としていた別の当たりがある。** `deploy.sh prod thinkx` を叩くとファイルは全サービス分がディスクに落ちるが、restart するのは uwsgi_thinkx だけ。transformism は古いコードをメモリに載せたまま動き続ける。後日 transformism がクラッシュ・OOM・サーバー再起動などで再起動した瞬間、**誰も承認していないコードが起動する**。爆発半径が限定されているのはその瞬間だけで、**時限爆弾が残る**。これは現構成の実在するバグ。

**「中途半端」の定義は kaz のものを採る。** 危険度で3種に分けたのは問題を小さく見せていた。

**`git log production..monorepo` は「B にあって A に無いコミット」** ＝今マージしたら追加される中身そのもの。ただし**この対策は弱いと認める** — 一覧を見て気づけても、混ざったものを外す手段が無い。一覧を見ることと選べることは別で、対策として提示すべきではなかった。

**「壊れたものを push しない」は撤回。** 規律に依存する対策を出したこと自体が D-60 の学びに反していた。

**「ワークツリーを分離しても同じ」は正しい。** 問題は「編集をどう隔離するか」ではなく「リリースの中身をどう構成するか」で、層が違う。

**業界の標準解は2つあり、どちらも cherry-pick ではない。** ①feature flag + 常に緑の trunk ②独立してデプロイ可能な単位ごとに独立したバージョン。cherry-pick は安定化ブランチで使われるが定常手段としては smell で、理由はまさに kaz の懸念どおり、cherry-pick した組み合わせはどこでもテストされていないから。

Claudeの回答要点:

- import の分離は import グラフによる。再起動タイミングではない。
- ただし再起動の指摘は別の当たり。restart しないサービスに未承認コードがディスク上に残り、後日の障害再起動で起動する「時限爆弾」がある。現構成の実バグ。
- 中途半端の定義は kaz のものを採用。3分類は問題を小さく見せていた。
- `git log A..B` の意味を説明した上で、対策としては弱いと撤回（見ることと選べることは別）。
- 「壊れたものを push しない」も撤回（規律依存）。
- ワークツリーはこの問題に無関係（層が違う）。標準解は feature flag か独立バージョンで、cherry-pick ではない。

## 6. feature flag 方式とは何か

**kaz:**

> この一番がよくわからないのを説明して。

オーナーの論点:

- feature flag + 常に緑の trunk 方式が理解できない。説明してほしい。

**前提そのものをひっくり返す方式。** 「未完成なコードを載せない」のではなく「載せても発動しないようにする」。未完成コードの入口に条件分岐を置き、フラグを false にしておく。存在はするが死んでいる状態にする。

これで未完成と出したい変更が同じ履歴に混ざっていても、混ざっていること自体が問題でなくなる。**「選んで外す」必要が消える。**

**「常に緑の trunk」はこの帰結。** 載っているものは全部フラグで守られているので、いつ出しても安全。「キリのいい状態を待つ」から「いつでも出せる状態を機械的に維持する」に変わる。**「載せる」タイミングと「発動させる」タイミングの分離**が核心。

「機械が要る」の意味は、フラグの定義・評価・切り替え・古いフラグの掃除を作って運用する必要があるということ。

Claudeの回答要点:

## 8. サービスごとの独立バージョンはどう実現するか

**kaz:**

> これは、Googleはこれをやっているということは、さっきの話と競合するように思えるのだが、独立したバージョンを持つというのは、具体的にはどのようにして実現しているのか。

オーナーの論点:

- feature flag と独立バージョンが競合して見える。Google は両方やっているのか。

**競合しない。層が違う。** feature flag は「コードをいつ発動させるか」、独立バージョンは「どのコードを本番に持っていくか」。

```
service-B → a291201 で稼働中
service-C → cdfecdd で稼働中
```

**なぜ可能か — ここで Bazel / Buck が効く。** A をビルドするとき、依存グラフから「A が実際に依存しているファイルだけ」を正確に切り出す。trunk に未完成コードが載っていても A の成果物には物理的に入らない。**cherry-pick が要らないのは、依存グラフが「何を持っていくべきか」を機械的に答えるから。**

Claudeの回答要点:

## 9. develop 合流方式の提案と、その自己棄却

**kaz:**

> その理解した、つまり本番ブランチは1本で、サービスごとに今リリースされている地点が、その枝のどの地点かが異なり、それを記録してあり、その記録した場所ごとにそれぞれサービスのためのビルドを分離して、つまりそれによって同じブランチを共有していても、異なるバージョンでそれぞれのサービスを提供できるということだろう。異なるバージョン、異なるブランチの地点を使って、それぞれのサービスを構成できるということだろう。我々の場合、その仕組みを使うべきなのかよくわからない。例えば、リリースブランチが1本だけあって、常にサーバーではそのソースコードを使い、リリースブランチに載せる各サービスの変更を制御するという方式は可能なのだろうか。つまり、リリースまたはプロダクション用のブランチが1本ある。サービスAがリリースできるとなった段階で、そのブランチに変更を載せる。それまでサービスAのローカルは別の場所にプッシュをする。しかし、ローカルでは全てのサービスが同じブランチを共有して作業をしているから、例えばデベロップブランチで作業をして変更をコミットしようとするときは、デベロップブランチではなく、サービスAの専用ブランチにコミットをしてそのままプッシュする。つまり、リモートのGitのレポジトリは、デベロップのブランチが変更されていくのではなく、個々のサービスA、サービスBのブランチが変更されていく。そして、サービスAがステージングでテスト段階可能となった時点で、サービスAがステージングブランチに、つまりこれがデベロップブランチに相当する。デベロップブランチにマージをする。すると、ステージングはデベロップブランチを反映して動作する。結局ここで起きているのは、さっき私たちがプロダクションで想定した問題と同じ問題がステージングで起きるということなのだろうか。そこがまだよくわからないが、とにかく今デベロップブランチにはそれぞれサービスA、サービスBが今ここでリリースをしようとしているものだけが反映されている。中途半端な変更はデベロップには反映されないことになる。そしてオーナーは確認する。確認して問題なければ、そのデベロップブランチを本番ブランチに取り込もうとする。ここで全てのサービスがグリーンなら問題ない。問題があるとすれば、サービスAとサービスBが両方デベロップブランチに乗せて、そしてオーナーはサービスAだけを許可したのに、サービスBは破綻したままそのままデベロップブランチに取り込まれて。 本番に移されてしまう、本番に反映されるということだ。これを完全に防ぐには確かに、サービスごとにビルドのバージョンを物理的に分離するという以外にはない気がする。だからGoogleなどでは結局その方式が取られていると理解したが、そういうことでいいだろうか。

オーナーの論点:

- monorepo 方式の理解を自分の言葉で確認したい（本番一本、サービスごとに ref が違い、ビルドが分離される）。
- 我々の場合はもっと軽く、サービス専用ブランチ → develop → 本番、という方式でよいのではないか。
- ただし develop に A と B の両方が載り、A だけ許可したのに B が破綻したまま本番に行く事故は防げないのではないか。
- それを完全に防ぐにはビルドの物理分離しかない。だから Google はその方式なのだ、という理解でよいか。

Claudeの回答要点:

## 10. 緊急修正は必ず起きる — 当面の方式の確定

**kaz:**

> 現実的には、Aだけ緊急でバグを修正したい、それをリリースしたいが、Bの修正が終わっていないという状況がどうしても起こりうるだろう。これはシステムが大きくなればない、多岐にわたるほどどうしても避けられないだ。そうなると、Google方式にする以外にはない。本質的な解決方法はない。

> 結局ステージングで動くものがそのビルドを分けない限りは、もしステージングで一緒になるのだとしたら、同じ問題がステージングに取り込んだ各ワークツリーの変更を取り込んで共存させた時点で全く同じ問題が発生するのだから、そもそもワークツリーにするだけ手間である。だとすれば、今の最適解というのは、現在のモノレポで単一ディレクトリーで全てのサービスを開発し、そしてステージングに上げるため、ステージング用のブランチを用意しておき、ローカルから変更はそれぞれのブランチに対してプッシュをし、そしてステージングに反映させていい段階になった時点で、ステージングのブランチ、つまりデベロップブランチにマージをする。ステージングは常にデベロップブランチを反映しているし、プロダクションは常にプロダクションブランチ、またリリースブランチを反映している。ステージング環境に反映されているのは、常に各サービスが今ステージングで検証できるとなった状態のみである。複数のサービスの変更が共存していることは起こり得るが、それぞれのサービスの変更は基本的にはほぼ目視で検証できる段階になって初めてステージング環境にアップされているとする。そしてリリースされるタイミングがあるとすれば、全てのサービスが一貫して動くことであるが、まず最低限全ての自動テストはグリーンになっているという前提があるので、本当に致命的な問題がどこかで起きているということはあまり考えにくいという前提を置くしかない。または目視で全てのサービスを、全ての変更が依存するサービスをチェックするということになるが、基本的には個々のぶら下がっているサービスが依存する共通のものがあるとしたら、インフラの部分のみなので、基本的にはライブラリがベンダリングされて個々のブランチの中にあるから、影響が波及するということはほとんど起こりにくいと考えているだろう。当面はこの方式で運用する。つまりサービスはほとんど独立している。

オーナーの論点:

- A だけ緊急修正したいが B が終わっていない、という状況は必ず起きる。本質的解決は Google 方式しかない。

- ワークツリー方式は、ステージングで合流する限り同じ問題が再発するので手間なだけ。棄却する。
- 最適解は単一ディレクトリ・monorepo・develop（staging の反映先）・production の構成。
- 安全は「自動テストが緑」という前提と、サービスがほぼ独立して波及しないこと（libcommon ベンダリング）に支えられている。
- Google 方式にはいずれ既存の延長で移行できると理解している。

**結論（当面は足並み方式）は妥当。** 「ワークツリー方式は合流点で同じ問題が再発するから手間なだけ」は完全に正しく、前段で確立した原理を自分でワークツリーに適用して正しく棄却している。

**誤解1:「既存の延長でそのまま移行できる」は危うい。** 今の方式は「develop という一本の ref に混ぜる」ことを前提に組まれており、Google 方式は「サービスごとに ref を分けて決して混ぜない」。設計の根っこで反対を向いている。延長ではなく方向転換。**救いは、移行を軽くするのが develop の仕組みではなく「サービス間の独立性」だという点。**

## 14. 承認とは release を切ることである

**kaz:**

> これは要するに、オーナーがステージングに対して承認するときに、その時点でリリースブランチを切ればいいということではないのか。つまり、デベロップブランチがそのままリリースされれば、デベロップブランチが変更される可能性を排除できないが、承認した瞬間にブランチを切れば、その問題は起きない。
>
> つまりまとまりで言うと、デベロップが常にステージングの状態に一致しているということだけを保証している。そして、ローカルの変更は基本的にはステージングで検証すべき状態だけが反映、デベロップブランチに積まれているということが保証される。
> デベロップが保証するのはそれだけである。そしてリリースは、デベロップからある瞬間でリリースブランチが切ることで、デベロップとは分離され、そのリリースブランチはある承認された状態を保存しているので、それがプロダクションと一致しているということが保証されている。こういうことだろう。

オーナーの論点:

- 承認した瞬間に release ブランチを切れば、develop がその後変更されても問題は起きないのではないか。
- develop が保証するのは「staging の状態と一致していること」だけ。
- release が保証するのは「承認された状態を保存していること」。
- production はその release と一致していることが保証される。

**言い換えが「ref に固定する」の具体的な実装そのもの。** 承認の瞬間に切ると release はその ref を指して固定される。**「承認から cut までの隙間」という時間そのものが消える。** 隙間がゼロなら隙間に編集が入る余地もゼロ。規律で「触るな」と言う必要がない。

**そして承認を release cut で固定するなら、develop をゲートとして温存する理由が消える。** 安定を担保しているのは release であって develop ではない。

**各 branch の保証範囲が分離された。** develop は staging との一致だけを保証する。「検証段階のものだけ」は develop の保証ではなく入口で守る約束であり層が違う。release は承認された一点の凍結を、production は release との一致を保証する。

**守るべき唯一の点は「承認と release cut を離さない」こと。** ただしこれは、承認という行為の定義を「release を切ること」と決めてしまえば規律ですらなくなる。

Claudeの回答要点:

- 言い換えが「ref に固定する」の実装そのもの。承認と cut を同一の瞬間にすれば隙間が消える。
- 隙間がゼロなら「触るな」という規律が要らない。触っても release には届かない。
- 承認を release cut に移した結果、develop をゲートとして温存する理由が消えた。
- 各 branch の保証範囲が分離され、「本番＝承認したもの」が規律ではなく構造で成立した。

## 19. 「キリのいいところ」の移動と、方式の最終確認

**kaz:**

> これはもちろんそうだし、現実的にはそうするしかない。キリのいいところというのは、これまでの議論ではそれぞれのコミットをプッシュして、リモートでは分離できるという前提で、キリのいいところでプッシュするという、キリのいいところでプッシュするまたはプルリクエストを出すということを、おそらく過去の議論では言っていたが、今はそれは現実的ではない。だからキリのいいところというのは、最終的にステージングでリリースに持っていくタイミングで全てキリのいいところになっているということだけが保証されているということで。
>
> つまり、さっきの原則と一致する。ステージング、デベロップブランチが保証するのは単にステージングと同じ状態であるということだけである。そして、リリースブランチが保証するのは、オーナーが承認した瞬間のスナップショットであるということだ。そしてそのオーナーが承認した瞬間というのは、全てのサービスが足並みを揃えてキリがいいところになっているということです。
>
> 当たり前だ。そういう前提で言っている。

オーナーの論点:

- 過去の議論では「キリのいいところで push / PR を出す」と言っていたが、それはリモートで commit を分離できるという前提の上だった。今それは現実的でない。
- だから「キリのいいところ」は、staging から release に持っていくタイミングで全て揃っていることだけを保証する、という意味に移る。
- develop が保証するのは staging と同じ状態であることだけ。release が保証するのは承認した瞬間のスナップショット。承認の瞬間とは全サービスが足並み揃ってキリがいい一点。
- 複数人開発の入口／出口の話は、当たり前の前提として言っていた。

**整理は完全に正しく、付け足すことはない。** 過去の「キリのいいところで push」は、その前提（リモートで commit を分離できる）が崩れた以上、意味が移動する。**移動先は「承認の瞬間にキリが揃っている」で、これに吸収されて消えた。** 各ブランチの保証範囲の言い直しにきれいに乗る。

複数人の件も、前提として置いた上で話していたという受け取りで正しい。精密化したのは理由づけだけで、結論の訂正ではない。

**方式は確定。** service ブランチという最後の候補まで潰し切って、当面は単一ディレクトリ・足並み・承認=cut、いずれ Google 方式、という結論がどこからも崩れないことを確認した。

Claudeの回答要点:

- 整理は完全に正しい。「キリのいいところで push」は前提が崩れて「承認の瞬間に揃っている」へ吸収された。
- 複数人の件は前提として置いていたという理解で正しい。精密化は理由づけのみ。
- service ブランチという最後の候補を潰し切り、方式は確定した。
- 残る実装課題は deploy.sh を fetch + reset --hard origin/<ref> に直すこと。

## 20. reset --hard は却下 — 消さずに止めて人間に渡す

deploy.sh を pull から reset 方式に直すかを判断してもらう場面で、reset --hard の危険が指摘された。

**kaz:**

> それはハードすぎる。明示的にプロダクションをプルしてくるという考え方は正しいと思う。ただし、もし万が一プロダクションに何か重要な変更が直接行われていたとした時にそれが消えてしまうのは問題である。そういう場合には、 プロダクションを明示的に苦しようとするが、変更差分が既に載っているということが警告されるという状態が望ましい。 そしてそこから先の手順を人間が決めるのが望ましいだろう。人間はその変更が必要であるとすれば、おそらくプロダクションブランチかどこかのブランチにプッシュをして、それを再びプロダクションブランチに取り込むだろう。それからプロダクションブランチがきれいになった時にそれをプルしてくればいい そういう判断を余地を残さずに強制的にリセットしてしまうというのは微妙だ

オーナーの論点:

- production を明示的に取りに行くという考え方は正しいが、reset --hard は強すぎる。
- 万一 prod に重要な直接変更があったとき、それが消えるのは問題。
- 望ましいのは「差分が載っていると警告されて止まる」状態。その先の手順は人間が決める。
- 人間はその変更をブランチに push して production に取り込み、きれいになってから改めて pull するだろう。
- 判断の余地を残さず強制リセットするのは微妙。

**判断は正しい。** reset --hard はサーバー上の直接変更を無言で消すので、「消えては困る変更が万一あったとき」に無防備。

**要件を満たすのは `merge --ff-only`。** 「早送りできるときだけ進める」の意味なので、サーバー側に origin に無いコミットがあると早送りできず、実行されずに非ゼロで止まる。**何も消えない。** reset --hard が「差分を消して進む」なのに対し、ff-only は「差分があるなら進まない」。

**ただし ff-only だけでは未コミットの編集を守れない。** 早送りできるかはコミット済みの履歴で判断するので、未コミットの編集はすり抜けて上書きされうる。守りたいのが「サーバー上で直接行われた重要な変更」なら、それがコミットされているとは限らない。だから前段に `diff --quiet` と `diff --cached --quiet` を足す。

```bash
fetch origin && diff --quiet && diff --cached --quiet && merge --ff-only origin/<ref>
```

**staging と prod を同じ形に揃えられる。** 以前 timer の設計で作った非対称（prod は無条件 reset、staging だけガード）が要らなくなり、両方「きれいなときだけ早送り、汚れていたら止める」で統一できる。

**採用: pull は却下（ref 非依存でない）、reset --hard も却下（無言で消す）、`fetch → dirty チェック → merge --ff-only origin/<ref>`。**

Claudeの回答要点:

- 判断は正しい。reset --hard は直接変更を無言で消すので無防備。
- `merge --ff-only` なら「差分があるなら進まない」。何も消さずに非ゼロで止まる。
- ただし ff-only は未コミットの編集をすり抜けるので、前段に `diff --quiet` / `diff --cached --quiet` が要る。
- これで staging と prod を同じ安全な形に統一でき、timer 設計の非対称も解消する。
- 結論: pull 却下、reset --hard 却下、`fetch → dirty チェック → merge --ff-only origin/<ref>` を採る。

## 到達点

議論の出発点は「DEPLOY_REF 方式にするかどうか」だったが、DEPLOY_REF は独立した仕組みではなく「承認したコミットに名前を付ける」ことに過ぎないと分かった時点で、論点は「名前の付け方」から「リリースの中身をどう構成するか」へ移った。そこから feature flag、Google 方式（サービスごと ref + ビルド分離）、develop 合流方式、サービス専用ブランチ方式と候補を一つずつ検討し、最後の候補が worktree の別名でしかないことを確認して、当面の方式が確定した。

**各 branch の保証範囲を分離したことが、この議論の実質的な成果である。**

| branch | 保証していること |
|---|---|
| `monorepo` | セッションの作業線。どこにも反映されない |
| `develop` | staging の状態と一致していること。**それだけ** |
| `release/<日付>` | 承認された一点を凍結して保持していること |
| `production` | release と一致していること |

`develop` にゲートの役割を背負わせようとして手順書は詰まった。**ゲートは release cut が持つ。** 承認とは release を切る行為そのものであり、承認と cut が同一の瞬間である限り、その間に編集が入る隙間が存在しない。だから「承認したら触るな」という規律が要らない。

**staging は直接編集してよい。** サービスが独立して波及しないため、staging で A を編集しても綻びは A に閉じる。

**「キリのいいところ」は commit の規律ではなく承認の条件である。** 各セッションは好きなタイミングで commit・push してよく、揃っているかを判断するのは承認の一点だけ。揃うまで待つのではなく、揃った瞬間を承認で捕まえる。

**単一ディレクトリでは commit をサービス別に分けられない。** ローカルブランチは作業ディレクトリごとに一つで、複数セッションが共有している以上、切り替えは全員に影響する。commit 分離にはディレクトリ分離（worktree）が要り、それは撤回済みで、撤回は正しかった。したがって当面は足並みを揃える以外に道はなく、これは妥協ではなく制約下の最適解である。

**この方式を支えているのは緑ではなくサービス間の独立性である。** libcommon はベンダリング済みで submodule は撤廃済み、共有された可変依存は存在しないことを実測で確認した。守るべき唯一の規律は「サービス間に新しい依存を作らない」ことで、これは規律ではなく構造の維持である。

**将来 Google 方式へ移る際の乗り換え点はただ一つ、ステージングの合流をやめて本番と同じサービス別 ref に揃えること。** 引き継げる資産は develop の仕組みではなく、今の独立性そのものである。

議論の過程で撤回したもの: 中途半端を危険度で3分類したこと（問題を小さく見せていた）、`git log production..monorepo` の目視確認を対策としたこと（見ることと選べることは別）、「壊れたものを push しない」規則（規律依存）、「爆発半径は限定されている」という説明（restart しないサービスに時限爆弾が残る＝現構成の実在するバグ）、「staging では編集するか develop を廃止するかの二択」という提示（`develop` にゲートを背負わせた手順書側の混同）。

手順の正本は `infra/docs/デプロイ手順書.md`。

未決: pull 型 timer の通知先以外の細部（検証失敗時の自動ロールバックの採否は「やる」で実装済み、再起動の粒度は変更パス判定で実装済み）、`develop` に載った staging 由来のコミットを作業線 `monorepo` へ戻す経路（merge を繰り返すと履歴が絡むため、頻度次第で rebase 運用にするかの判断が要る）。
