Claude
良い着眼で、これは monorepo 化しても意図的に残している二層構造だ。役割ははっきり分かれている。

二層の役割

トップの libcommon/（と simplicity/）＝原本（マスター）。 開発・修正はここでだけ行い、タグ（v2.0.0、v2.1.0…）で版を刻む。bake.sh もここに住む。
各サイト内の thinkx/web-server/libcommon/ 等＝焼き込みスナップショット。 VERSION ファイル付きの読み取り専用コピーで、編集は禁止（settings でも deny 済み）。「そのサイトが、原本のどの版を採用しているか」の凍結された記録。
運用はあなたの推測どおり「マスターを編集し、焼き込みで適用」で、流れはこうなる：
```
1. libcommon/(原本)を修正 → 原本のテスト green
2. 新タグを打つ(例 v2.2.0)
3. 追随したい消費側にだけ bake.sh を流す(例: thinkx に v2.2.0 を焼く)
4. そのサイトのゴールデン sweep で回帰なしを確認
5. コミット — そのサイトの diff に「libcommon v2.1.0→v2.2.0 採用」が丸ごと可視化される

```

「バージョンがそれぞれ異なる」のは異常ではなく設計

これが vendoring を選んだ理由そのものだ。追随は消費側ごとの明示的な選択であり、原本を更新しても、焼き直さない限りどのサイトも1バイトも変わらない。だから auth が v2.0.0 のまま、サイト群が v2.1.0、という混在が正当に存在できる（VERSION ファイルがそれぞれの採用版を証明する）。ライブラリの変更が全消費者へ暗黙に波及する事故 — submodule 時代の問題 — を構造的に殺してある。

monorepo 化で何が変わったか

構造は変わらないが、選択肢が1つ増えた：原本の修正と全サイトへの焼き直しを1コミットで原子的にやれるようになった（polyrepo 時代は7回の push が要った — 旧 ROADMAP の「monorepo 化の引き金(a)」がまさにこれ）。つまり今は「サイトごとに時期をずらして追随する自由」と「全系一斉更新を1コミットでやる能力」の両方を持っている。使い分けは：緊急のバグ修正は一斉焼き直し1コミット、大きめの変更は1サイトずつ追随、が自然だ。
将来、焼き込み層をやめて各サイトが libcommon を直接 import する形（単一コピー・完全原子化）に畳む選択肢もあるが、それは「変更の完全可視・独立凍結」という現在の価値を捨てる取引なので、必要が実測されたら小さな計画書1本でやればいい — 今は触らないのが正しい。
この二層運用は E トラック文書に1行入れておく価値があるので、次に E を v1.0 化するとき「vendored スナップショットの編集禁止・修正は原本→bake→sweep→1コミット」の既存の禁止事項に「原本の版上げと焼き直しは通常のセッションブランチ+PR で行う（全サイト一斉も可）」を足す形にする。

まず認めるべき点：あなたの懸念シナリオは現実的だ。「サイト X で今すぐ直したいバグ、しかし原本は破壊的変更を挟んで先に進んでいて、全体を追随検証する時間がない」— 運用者が1人で時間が最も稀少な資源であるこのシステムでは、「forward 追随のほうが理論的に健全」と言われても、今夜直したいという場面で v2.0.1 を切れる能力には実際の価値がある。
そのうえで、それでも並置案より monorepo 内包＋forward 既定を推す理由は、コストの非対称性だ。
並置案が毎日払うコスト：clone が2〜3回に戻り、push 忘れ事故の口が再び開き、「原本修正＋全サイト焼き直し」の原子1コミットが不可能になる。これは backport が一度も起きなくても払い続ける。
内包案が backport 時にだけ払うコスト：旧ソースの復元が一手増える。頻度が低ければ総額は小さい。
ただし内包案の backport 手順が「今夜使える」程度に軽くなければならない。鍵は、取り込みコミットにタグを打っておくことと、git worktree だ：
1. M-2 の取り込み時、libcommon の取り込みコミットに libcommon-v2.1.0 のタグを打つ
2. 以後、原本の版上げのたびにタグを打つ — monorepo の歴史の中に版の座標が残る
3. backport が要る夜は：git worktree add /tmp/lib-v2.0.0 <旧版のタグ or 旧リポジトリ> で旧ソースを数秒で実体化 → 修正 → bake → サイト X の sweep → X のスナップショット変更だけを PR worktree を使えば「遡って焼く」が並置案とほぼ同じ手数になる。つまり並置案の唯一の利点を、内包のまま9割回収できる。

そして2点目のほうが本質的だ。「マスターのみ修正」の前提は実運用に合わない — これも正しい。サイトのバグを追うとき、現場は thinkx/web-server/libcommon/ の中だ。そこを直接いじって、動いているサイトに対して秒単位で試行するのが最速のループで、「原本を直す → bake → サイトで確認」を毎イテレーション回すのは明らかに遅い。しかも原本 HEAD がサイトの採用版より進んでいる場合、原本上ではそのサイトの状況を再現すらできない。直接編集は避けられないのではなく、それが正しい作業方法だ。
では「スナップショット編集禁止」の規則は何を守っていたのか。禁止の実体は2つの事故の防止だ：(1) 直した内容が原本に還流されず、次の bake で修正が上書き消滅する（vendoring 最古典の事故）、(2) VERSION が「v2.1.0」と言っているのに中身が v2.1.0 でなくなり、どこに何が動いているかの台帳が嘘になる。つまり守るべき不変条件は「触るな」ではなく「マージされる時点で、スナップショットは VERSION が指す版の bake 結果と一致していること」だ。手続き禁止を不変条件に置き換えれば、快適なループと台帳の健全性は両立する：
セッションブランチ内(自由):
thinkx/web-server/libcommon/ を直接編集 → サイトで即試行 → 動くまで反復
仕上げ(マージ前の義務):
1. 出来た diff を原本に適用
2. 新タグ(v2.2.1 等)→ bake で thinkx に焼き直し → 作業中のコピーと byte 一致するはず(しなければ還流漏れが機械的に発覚)
3. VERSION 更新・sweep green → PR 他サイトへの適用: 従来どおりサイトごとの明示的な追随(遅延可)

そう、「並置」はまさにあなたの図のこと — libcommon が自分の .git を持って monorepo の外に横並びする形だ。「PR が2本に割れる」の意味は：仕上げの還流で、(a) monorepo 側に「サイト修正＋焼き直しスナップショット＋VERSION 更新」の PR、(b) libcommon リポジトリ側に「還流 diff ＋新タグ」の push、という2つの別リポジトリへの書き込みが発生し、(b) を忘れても (a) は単独でマージできてしまう — 忘れた瞬間、canonical に存在しない「幽霊版」がサイトで動き、次に誰かが bake すると修正が消える。これが「口が開く」の中身だった。
だが、あなたの主張を受けて正直に再計算すると、内包論は負けている。決定打は2つ：
1. monorepo は焼き込みスナップショットの diff を通じて、本番に届く内容変更をすでに全部記録している。canonical を外に出しても、monorepo から見える情報はほぼ何も失われない — canonical は「内容の記録」ではなく版のカタログ（タグと系列の台帳）であり、カタログはカタログ専用の git を持つのが一番素直だ。版間 diff は git diff v2.0.0..v2.2.0 で一発、backport は git checkout v2.0.0 -b hotfix で自然に切れる。内包案で worktree だ遡及タグだと組み立てた迂回装置は、独立 git なら全部標準機能。
2. 移行作業がゼロになる。既存の libcommon / simplicity リポジトリは凍結せず、そのまま生き続けるだけでいい。M 計画から取り込みを外すだけ。
(b) 忘れの事故は、アーキテクチャではなく機械ガードで塞ぐのが正しい：PR ゲートで「各サイトの snapshot の tree_sha ＝ canonical の VERSION が指すタグを bake した結果の tree_sha」を照合する。タグを push し忘れていれば照合先が存在せず赤くなる。このガードは内包でも並置でも同じく必要だったので、並置のハンデにならない。
細部の訂正を1点：bake.sh は snapshot には焼かれない（dev 物は除外、S2 でも確認済み）。bake は常に canonical から：/src/libcommon/scripts/bake.sh v2.0.1 /src/monorepo/kazukiotsukacom/web-server/。「/src/libcommon が要るのは bake（と還流）のときだけ＝編集マシンのみ、サーバーには不要」という理解は正しい。
確定構成:
/src/thinkx-system(monorepo)   ← サイト群 + auth + infra + docs。snapshot を内包
/src/libcommon(独立 git・生存) ← canonical。版タグの台帳。編集マシンにのみ clone
/src/simplicity(独立 git・生存)← 同上
