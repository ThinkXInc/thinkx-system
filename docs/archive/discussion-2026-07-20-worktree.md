Claude
あなたの指摘は当たっている。ただし半分だ。間違っていたのは worktree を分けたことではなく、branch まで分けたことだ。

いま我々がやろうとしている苦役 — 3本のトラックを cherry-pick でほぐして別々の clean branch に組み直す — これは worktree を分けたから発生したのではない。「auth のコミットが citywalk のコミットの子孫になっているのは不正だ」という要件を後から立てたから発生している。そしてその要件は、よく考えると必要がない。

全トラックは最終的に origin/monorepo という同じ1本に着地する。チームで trunk に push しているのと同じ構造だ。trunk 開発で「A さんのコミットが B さんのコミットの子孫になっている」ことを問題視する人はいない。コミットメッセージに接頭辞が付いていて、触っているディレクトリも分かれているのだから、履歴は十分読める。bisect も revert も困らない。つまり混在した一直線の履歴は欠陥ではない。

一方で worktree の分離自体は無駄ではないと考える。今回あなたが 804MB のバックアップ tarball を取ったのは、ファイルが競合したからではない。「別のセッションが git reset や git clean や git stash を打ったら、citywalk の未コミット素材が消し飛ぶ」という恐怖からだ。私が起こした事故も、ファイル競合ではなかった。infra の変更を commit した瞬間、HEAD が auth 線の先端だったせいで push が拒否された。

どちらもファイルの競合ではなく、git の状態(index と HEAD と working tree)という共有された可変状態への同時書き込みだ。あなたの言う「それぞれ自分の持ち場しか触らない」は、ファイルについては完全に正しい。しかし index と HEAD は持ち場が無く、全員が同じ1個を書き換える。ここだけは自制では守れない。エージェントが5つ並行で動いていて、そのうち1つが git add -A や git checkout . を打った瞬間に他が壊れる。worktree はこれを OS のディレクトリ境界で物理的に不可能にする。それが唯一にして十分な理由だ。

結局、常にGitステータスで他のセッションが編集中かどうかをチェックしておけば、そして自分の持ち場の分だけアドすればいいということではないだろうか。

Claude
正直に言うと、あの「唯一にして十分な理由だ」は言い過ぎだった。あなたの反論の方が正確だ。順に潰していくと、こうなる。

git add <自分のパス> して commit する限り、ファイルの選択は安全だ。index への同時書き込みは index.lock があるので、衝突しても片方が「Unable to create index.lock」でうるさく失敗するだけで、壊れない。リトライすれば通る。HEAD が他人のコミットに動いていても、自分のコミットがその上に乗るだけで、これは混在履歴を許容すると決めた以上もう問題ですらない。実際、今日の唯一の事故は、「混在は不正だ」という前提があったから事故に見えただけで、trunk 方式ならただの正常な積み上がりだった。

つまり、日常的に起きる操作の範囲では、あなたの言う通り「status を見て、自分の持ち場だけ add する」で足りる。

危ないのは日常操作ではなく、git reset --hard / git checkout . / git clean / git stash / branch 切替 / rebase の6つだけだ。これらは working tree 全体を書き換えるので、他セッションの未コミット作業を音もなく消す。しかもコミット前のファイルには reflog が無いので復旧できない。頻度の問題ではなく、blast radius の問題だ。

ただしこの論点も、あなたが今提案した「編集したらその場で push」というルールを入れると、かなり弱くなる。未コミットの窓が数分しかなければ、消される対象がそもそも存在しない。だから安全性は決め手にならない、というのが正直なところだ。

それでも worktree を残す価値が残るとしたら、安全性ではなく可読性の方だと思う。共有ツリーだと git status が全トラックの作業中ファイルを混ぜて表示する。まさに今日、citywalk のツリーに .codex/GUIDELINES.md と docs/DECISIONS.md と infra/CLAUDE.md が未コミットで並んでいて、「これは誰の変更だ」という問いに答えるのに、私が diff を読んで内容から判定する必要があった。5セッション並行だとこれが常時起きる。

代わりに払うコストも正確に言っておくと、ディスクだ。このリポジトリは 4994 ファイル + LFS の動画があるので、worktree 1つで数 GB 食う。5つで無視できない量になる。
