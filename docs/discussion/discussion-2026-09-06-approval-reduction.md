> **こういうコマンドは？これはBashでやるべきことなのか？bashでやるから承認がいるのでは [python heredoc で build スクリプトを書き換え → build → curl localhost で確認]**

承認が出る原因は curl(ask)。python heredoc も build も単体では止まらない。このコマンドは 3 つの別作業が混ざっている。(1) build スクリプトの書き換え → これは Edit ツールの仕事(heredoc の s.replace は Edit の再発明で不可視)。(2) build 実行 → 無承認で通る。(3) localhost 確認 → curl が ask。curl を allow に足しても ask が勝つので効かない。localhost 確認をスクリプト(python の urllib)に畳めば可視コマンドが python3 になり承認が消える。

- **オーナーの論点**: このコマンドは Bash でやるべきか。Bash だから承認が要るのでは。
- **Claudeの回答要点**: 承認の原因は curl。編集は Edit、確認はスクリプトに畳む。curl を allow に足しても ask が勝つ。

> **汎用性のない仕組みスケールしない仕組みに労力をさかないのは原則 ただsettingsのaskを変えればいいだけなら何が問題？**

## 到達点

承認削減は「settings では表現力が不足するのが明らか」という認識から、判定(hook)と固定 wrapper を
使い分ける 3 層構成に到達した。割り当ては 3 問(settings の前置一致で書けるか / 実行時に安全に分類できるか /
頻度が高く習慣的か)で機械的に決まる。settings = git add・WebFetch ドメイン。hook 判定 = git commit・push
(settings で書けず・分類が安全・頻度が最高という唯一の交点)。固定 wrapper = curl・ssh 観測(任意コマンドの
安全分類が原理的に危ういため、構築による安全)。deny の床は全層で維持し、hook も wrapper もその上で承認を
足すだけ。v1 は最小(git 判定フック + 既存 wrapper)としてコミット/push 済み。オーナーがフックを settings に
登録済みで、次セッションで動作確認(複数行 commit で無承認 / force push は停止 / add && 外部 curl はプロンプト)
してから v2 へ拡張する。設計上の分岐(フック採用)を独断で進めた反省から、以後は選択肢と trade-off を示して
委ねる。確定した成果物の正本は `docs/approval_cases_v1.md` と `docs/DEPLOY_APPROVAL_LEVELS.md`。
