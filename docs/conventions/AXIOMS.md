## 三公理

原本(2022, wiki)の英語原文を規範の原料として保存する。

### 1. Minimalism — A small number of principles to satisfy all

物理が少数の法則で多くを説明するように。フレームワークの機能は、より多くのユーザ層を満たすため
必然的に増え、同じことをする方法も多数ある。その中から**基本的で汎用的な方法を選び、それが必要を
満たす限りそれだけを使う**。

### 2. Uniqueness — The interface is the brand

プロダクトのインターフェイスは人の顔・声・表情のようなもの。独自であることで、人の認知の中に
ブランドが蓄積する。既製品をそのまま使うことを避け、原則として自前で実装する。アニメーションは
生き物のように滑らかで自然に動かす。

### 3. Speed — Fast response is the greatest feature

コンピュータ最大の利点は、人間が同じ結果を返すより速く応答できること。遅いコンピュータは人間の脳を
劣化させ、速いコンピュータは人にまた頼みたいと思わせる。**多くの場合、速いことは何よりも優先される。**

## 記憶力より思考力に頼る

私たちは記憶力よりも思考力に頼る。**覚えることを少なくする。** 覚えていなければ使えないことを
少なくし、使う人がほとんどのことを組み込みの関数で書けるように設計する。

- 独自ラッパを覚えなければ使えないクラスは避ける。例: `addEventListener` をラップした独自関数を
  覚えないとイベント登録できない設計にはしない。標準の `addEventListener` で登録できるようにする。
- ラッパは、必要なら「その画面・その部分だけ」でその場定義・その場使用に止める。クラスに常設化する
  ことには慎重になる。

---

## 命名

**キーを見て中身が完全にわかる命名。一つの事実に一つの名前。別名・エイリアスは禁止。**

- 必要十分であること(過不足なし)。
- type/object が明確であること(例: `user_age` / `is_valid` / `dogs`(リストを示唆) / `dog`(単一))。
- 主語・述語、過去・未来が紛れないこと(例: `managed_account` / `blocking_user` / `saved_password` /
  `visiting_page`)。
- 略語は原則不可、特例のみ(`item_dsc` は不可 / `lat`・`lon` は可)。
- 英語の文のように読めること(例: `if password.is_valid`)。
- 一貫していること。役割が "to be" / "to do" / "how" / "what" のどれかを明確にすること。
- **外部(Google 等)と話す境界だけ**は相手の名前(`sub`, `aud`, `locale` 等)で読み書きする。
  内部では使わない。
- JavaScript の変数名は平均 1.5 語で短く: 1 語=良 / 2 語=普通 / 3 語=やや長い /
  4 語=どうしても必要な場合だけ。

---

## メソッドは小分けにする

1 つのメソッドに処理を詰め込まない。

- 良い例: ユーザ作成メソッドにはユーザの保存とそのバリデーションだけがある。
- 悪い例: ユーザ作成メソッドに「初回作成時の決済手段設定」まで書く。決済手段の設定は別メソッドにし、
  別のスコープで呼ぶ。

---

## 疎結合の維持

オブジェクトを別のオブジェクトの引数やメソッド内 import でそのまま使うより、**なるべくプリミティブな
型を境界で受け渡す**。スコープの外でプリミティブ型に出力してから入力に取ることで独立性を担保する。
自作/ライブラリのオブジェクトを引数に埋め込むと、そのオブジェクトの変化が波及し、最悪プロジェクト
全体のリファクタリングになる。

- 例外: HTTP エラーレスポンスの共通クラス等。API が長く不変である前提を覚悟して使う。
- View に関するクラスには**最小権限の原則**が適用される。特に HTTP 通信は View のクラスの中では
  行わない。ハンドルできないイベントはカスタムイベントを発行し、その View を配下に持つ親側で拾って
  そこで通信する。
- 細かなコンポーネント(フォーム等)にはロケールオブジェクトを持たせず、コンストラクタにテキストを
  受け取らせて出力済みのテキストをセットする(疎結合原則)。

## コメントとチャンク

**コードベースは短く保つ。コメントを書かなくてもわかるのが理想。**

- 変数名・メソッド名を必要十分につけ、込み入った処理は別スコープに閉じ込め、読むべきところを簡潔に
  保つ。API ハンドラのような表のレイヤーで込み入った処理を書かない。
- **ひとまとまりの処理は空白行で区切る(チャンク)。** 空白行で切られた塊が一目で何をしているか
  わかればコメントは不要。わからない/コメントの方が良い場合のみ、その塊の一番上にコメントを貼る。
- まず「名前の付け方」「抽象化の仕方」「空白行の使い方」を良い例で身につける。

---

## データ型の制約

ひとまとまりのデータの型を制約したいとき:

- 厳密な型チェックが要りパフォーマンスが最重要でない → **pydantic**。
- 拘束性が必要、または大量に繰り返し生成する → **namedtuple**(pydantic との速度差は 10 倍以上)。
- 上記の中間的な用途 → dataclass。

---

## 日時は UTC で保存する

日時の保存・演算は常に UTC。ユーザ表示やその地域の時刻を使うときだけ、UTC から使用場所の
タイムゾーンへ変換する。naive datetime を新規に作らない。UTC 統一により、地域をまたぐ書類処理等で
「狙った時刻に実行されない」不具合を避ける。(libcommon dateutils の aware-UTC ドクトリンと同一。
契約実装は L-5 の管轄。)

## 継承 — アプリ層で深くしない (現代化)

**アプリ層で深い継承をしない。フレームワーク基底の継承+1段の拡張は可。**

- JavaScript は基本的にスクリプト言語であり、本格的な OOP をやろうとしない。アプリのドメインクラスを
  何段にも継承しない。
- ただしフレームワーク/コンポーネント基底(例: ビューコンポーネント基底、`Page`、`TextField`)を
  継承して 1 段拡張するのは可。例: 追加のボタンやインターフェイスを足したいとき `TextField` を継承した
  専用フォームクラスを書く。継承クラスを作るかは慎重に検討する。
- (原本は「クラスの継承は基本的に行わない」と書いていた。simplicity の実態=フレームワーク基底
  起点の 1 段拡張と整合させるため精密化した。詳細は `NORMALIZATION_REPORT.md`。)

## エラー表示 — 詳細はログへ (現代化)

**エラーの詳細はログへ出す。ユーザへはエラーコード+安全なメッセージを返す。詳細を返すのは
バリデーションエラーのみ。**

- 無条件にエラーの中身をユーザへ詳しく表示することは、内部情報の漏えい経路になるため行わない。
- バリデーションエラーは、どのフィールドが何故不正かをユーザが直せる必要があるため、フィールド名・
  コード・メッセージを返す(契約上の `errors` 配列型。外形は契約層=L-7 / PROTOCOL.md の管轄)。
- (原本は「エラーの内容はなるべく詳しく細かくユーザに表示してもほとんどの場合構わない」と書いて
  いた。セキュリティの観点から上記に修正した。詳細は `NORMALIZATION_REPORT.md`。)

## テスト規律 — 機械オラクルが先行する (追加)

**機械オラクル(sha 台帳・ゴールデン・lint ベースライン等)が全変更に先行する(D-4)。**

- 挙動の正しさは、人間の目視ではなくコマンド+機械比較で判定する。挙動を保存する変更は、まず
  オラクルを構築してから着手する。
- 「一見して原因がわからないバグには、とにかく細かくログを出す」というデバッグは有効だが、
  **オラクル不在時の最終手段**に降格する。まず機械オラクルで差分を局所化することを優先する。
- (この節は原本に無い**追加**。両リファクタリング計画の項目0系・D-4 を公理層へ昇格したもの。)

## この文書の使い方

各リポジトリの `CLAUDE.md` は、冒頭でこの `AXIOMS.md` を参照し、その下にリポ固有の規約
(パス・ビルド・デバッグ・契約実装の呼び出し方)を重ねる。公理とリポ固有が食い違った場合は、
食い違いの事実を当該リポの findings に記録し、上位(計画書 → CLAUDE.md → 本書)に従う。
