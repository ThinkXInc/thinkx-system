# ThinkX でのコードの書き方

> このドキュメントは、ThinkX のコードベースを書く上での設計思想・実装指針をまとめたものである。
> スタイルの規約であると同時に、「なぜそう書くのか」という判断の根拠を含む。

---

## 原則 — 記憶力より思考力に頼る

私たちは記憶力よりも思考力に頼る。多くのことを覚えていることに依存しない。**覚えることを少なくする。**

そのためには、覚えていなければ使えないことを少なくする。使う人がほとんどのことを組み込みの関数で書けるように設計する。

例えばイベントリスナーは誰もが知っている。もし、あるクラスが `addEventListener` をラップした独自関数を持っていて、それを使わなければイベントを登録できないとしたら、そのラップ関数を覚えていなければそのクラスを使えないことになる。しかしそんな関数をいちいち覚えていられない。だから、単に標準の `addEventListener` を使ってイベントを登録できるように設計すべきである。

実際にはほとんどのことが組み込み関数で書ける。何度も繰り返す処理を避けたいときにラッパー関数を用意する場合はあるかもしれないが、そういうものは、もし必要ならその画面やサイトのある部分だけで使うために、その場で定義してその場で使うだけに止める。クラスにそういったものを実装することには慎重になる。

## Python

### アーキテクチャの前提

普通のウェブアプリケーションは、Nginx をサーバーにして uWSGI でプロセス管理し、その上に Python アプリケーションを載せる構成にする。

共通ライブラリとしては、共通ライブラリのリポジトリをルートの配下に submodule として配置する。ここにはよく使う処理が入っているので、この中の重要なものをまず読むとよい。

とりわけ重要なのは `web` ディレクトリの中にある、HTTP の返却値を定義するファイル。特にエラー（errors）とサクセス（success）の定義は重要。

次に重要なのは locale。これは多言語化のためのもので、エラーメッセージやメール本文の記述などを多言語化するのに使う。

ハンドラを書くときにさらに重要なのは、Flask ヘルパーに含まれたデコレーターである。これらはハンドラに必要な共通処理を定義している。例えばセッションからユーザを取り出す、言語情報を取り出す、バリデーションをする、といった何度も使う処理がここに書かれている。このデコレーターを使うことで、ハンドラの中は簡潔に記述できる。

### メソッドは小分けにする

1つのメソッドにたくさんの処理を詰め込まず、小分けにする。

**良い例** — ユーザを作成するメソッドには、ユーザの保存とそのバリデーションだけが書かれている。

**悪い例** — ユーザを作成するメソッドに、ユーザの保存に加えて「最初にユーザを作成したときに行う決済手段の設定」などが書かれている。決済手段の設定は別のメソッドにして、別のスコープで呼ぶ。

### エラー表示

エラーの内容は、なるべく詳しく細かくユーザに表示しても、ほとんどの場合は構わない。

### ログの色分け

ログには色をつける。区分は概ね次の通り。

- **赤** — エラー。目立たせる。
- **シアン** — 重要な、読むべきメッセージ。
- **イエロー** — 何かに成功したり接続したりしたとき、それなりに目立たせたいとき。
- **マゼンタ** — 結構目立たせたい重要な情報。例えば、どの環境にあるか、リクエストされたパラメータ、言語情報といった重要な情報。ボールドを使ってもいいし、場合によってはアンダーラインを使ってメタ的に強調してもよい。

### 日時（datetime）の保存

日時の保存は基本的に UTC で行い、ユーザに表示したりその地域での時刻を使う場合に、UTC からその使用場所のタイムゾーンに変換する。つまり保存は常に UTC。

例えば、ある国で何かの書類処理を実行したい場合、UTC 時間でないと狙った時刻に実行されない不具合が起きうる。UTC で統一すればこうした厄介な問題が起きない。

### セッション

Redis に格納されるセッションについては、独自のカスタム Redis セッションハンドラを Flask にセットする。

この独自の拡張ハンドラを使う理由は、主にセッションから「複数の端末でアクセスされている状況」をカウントするためである。その予定がない場合は必ずしも使う必要はないが、ほとんどの場合これを使えばそれでいいので、黙ってこれを使う。

このファイルにはセッションクラスも定義されている。基本的な使い方は次の通り。

セッションをスタートするには、ユーザ ID を渡す。ここでユーザは基本的に MongoDB のモデルで保存されているので、ID は ObjectId 型である。ObjectId 型はそのままでは文字列ではないので、`str(user.id)` にキャストしてユーザ ID の文字列を得る。これをセッションスタート関数に入れて呼び出せば、そのユーザのセッションが作られる。

このとき裏側で起こっていること:

1. そのユーザ ID のセッションデータが Redis に保存される。ここには期限があるので、セッションが切れる時刻を制御できる。
2. 同時にクラスが自動的に HTTP ヘッダにセッションのためのクッキーをセットして HTML を返す。これはレンダー HTML を呼ぶと自動的に実行されるので、クッキーのことを考える必要はない。

同じようにセッションクリアを呼び出すと、今作られているセッションが閉じられる。このとき裏側で起きているのは、Redis のそのユーザ ID に対応したデータが消されることである。

Redis の中にそのユーザのセッションがない状態で、セッションが必要なハンドラにアクセスすると、基本的には 403 Unauthorized が返る。この仕組みは、Flask ヘルパーの中にあるセッションハンドラのデコレーター関数をハンドラに付ければ、自動的に内部でセッションを確認し、「セッションがない」または「セッションはあるが該当するユーザが存在しない」ことをチェックして、それぞれのエラーを raise する。

`main.py` の中には、これらのエラーを検出すると呼び出される汎用ハンドラが書かれている。リクエスト URL によって、サインインにリダイレクトするか、エラーオブジェクトを返すか、どちらかの処理を行う。

#### セッション ID の転送

セッション ID はサーバーで作られると、セッションがある間（HTTP 通信をしている間）は HTTP ヘッダのクッキーセクションに格納され、サーバーとブラウザ間で自動的に転送される。これは WebSocket 通信でも同じ。

ただし、クロスオリジン通信の場合にはクッキーはセットされない。そのため、当初はウェブサーバーとストリームサーバーを別のサブドメインに設定していたが、それだとクロスオリジン通信になってしまい、ストリームサーバー側からクッキーを取得できない。そこで共通ドメインにすることに変更した。

このクッキーに含まれるセッション ID からユーザ ID を特定する必要が出てきたので、Redis のセッションには `session:userID` のキーと同時に `userID:sessionID` のキーも保存する。後者は逆引きのためである。セッションクラスにはユーザ ID を返すメソッドがあり、後者を使わずともセッション ID からユーザ ID を引き出せるが、これは Flask のコンテキスト内でしか使えない。

### デバッグ — 原因がわからないとき

一見して原因がわからないバグに遭遇した場合、まず確実に解決する方法は、とにかく細かくログを出すこと。ログをどんどん細かくしていけば、そのうち原因となる箇所がわかる。

### 疎結合の維持

クラス等のあるオブジェクトを独自に定義したとする。それを別のオブジェクトの引数に取ったり、別のオブジェクトのメソッドの中でインポートしてそのまま使ったりするよりも、なるべくプリミティブな型を引数に取るようにする。つまり、その別のクラスのメソッドのスコープの外でプリミティブ型に出力したあと、そのプリミティブ型を入力に取ることで、コードの独立性を担保できる。

逆に、引数にそのまま自作プロジェクトや何かのライブラリのオブジェクトを埋め込むと、そのオブジェクトが変化した場合、それを引数に取ったり利用しているオブジェクトも書き換えなければならない。最悪の場合、プロジェクト全体をリファクタリングすることになる。そうならないために、メソッド相互やオブジェクト同士が独立していることをなるべく維持する。

ただし例外もある。例えば HTTP エラーレスポンスの共通クラスなど。こうしたものは、基本的に API がずっと変わらない前提を覚悟して使われる。

### コメントはどの程度書くべきか

なるべくコードベースは短く保ちたいので、コメントを書かなくてもわかるのが理想的である。

そのためには、変数名やメソッド名を必要十分につけ、無駄な状況整理をなくし、なるべく込み入ったことは別のスコープに閉じ込めて、読むべきところは簡潔になっているようにする。例えば API ハンドラはかなり表のレイヤーだから、この中で込み入った処理をたくさん書くのは避けたい。そうすると可読性が下がる。

ひとまとまりの処理は空白行で区切ることで、それが1つのまとまりであることを示す。つまり、まず「名前の付け方」「抽象化の仕方」「空白行の使い方」を良い例を見てマスターする。空白行で切られた塊が、一目見て何をしているかわかればコメントを書く必要はない。そうでなければ、またはコメントで表現したほうがよければ、その空白行ブロックの1番上にコメントを貼る。

### データ型の制約

あるひとまとまりのデータの型を制約したい場合、基本的には pydantic か dataclass を使う。型チェックを厳密にする必要があって、パフォーマンスがそれほど重要でない場合は pydantic を使う。一方で、拘束性が必要になったり、何度も大量に繰り返し生成するような場合は namedtuple が適している。それぞれの速度差は10倍以上あるので、状況によって使い分ける。

### 返却値のフォーマット

返却値は、基本的にその場で JSON を定義するのではなく、定義された共通のフォーマットを使う。Flask の API レスポンスなら、共通の HTTP レスポンスフォーマッタで作られたクラスを使う。使い方は実際のハンドラの例を参照する。

Celery のタスクのように、シリアライズしたデータで返さなければいけないときもある。そうしたときは一般的に `success` というキーを設定し、そこに `True`/`False` を入れる。そして返却するデータを添える。これを Celery タスクで返す。

## JavaScript

### 変数名

変数名は平均して 1.5 語でつける。短く。

- 1語 — 良い
- 2語 — 普通
- 3語 — 少し長い
- 4語 — どうしても必要な場合だけ

### クラスの継承

クラスの継承は基本的に行わない。JavaScript は基本的にはスクリプト言語である。本格的にオブジェクト指向プログラミングをしようとしない。

### 引数は辞書で受ける

コンストラクターやヘルパー関数の引数は辞書（オブジェクト）で受ける。それによって、順番を間違える・不要な変数を省略する・名前を間違える、といったよくあるミスを避けることができる。また初期値もきれいに設定できる。

引数が1つ、または2つしかないときは辞書で囲まなくてもよい。3つ以上を入力するときは、基本的にこの表記(辞書)を使う。

### 画面の構成

画面を作るときは基本的に大きく3つの部分で構成する。

1. **画面の初期化**
2. **イベントのハンドリング**
3. **ヘルパー関数**

**1. 画面の初期化** — HTML にはマウントするエレメント要素を最小限記載しておき、ほとんど全てスクリプトでエレメントを生成する。ホーム等の重要な要素には ID をつける。それほど重要でなくアクセスされないものはクラス名だけつける。

明らかにタグで伝えたい・そのタグを指定する方が真剣である時だけ、クラス名を指定しなくてよい。例えば、5種類のボタンの中に `<button>` を埋め込み、それぞれのパターンが別のクラスを持つ、というとき、`button` にスタイルを適用すればよい。なぜなら `button` それ自体が「それが何であるか」を主張しているから。一方で `div` 要素は素では名前をつけなければそれが何だかわからないので、基本的にはクラスをつける。

### DOM 要素は `$` 接頭辞で表す

DOM エレメントを表す変数には最初に `$` をつける。これは jQuery というライブラリの時代に見られた習慣であり、DOM 要素は特別なのでそれと明示する価値がある。

### クリックアクション

何かの要素をクリックしたときのアクションは、基本的に `onclick` で指定する。

### View に関するクラスを書くとき（最小権限の原則）

View に関するクラスを書くときは注意する。最小権限の原則が適用される。特に HTTP 通信は、基本的に View のクラスの中では行わない。

クリック等の一般的なイベントでハンドルできないイベントでトリガーしたいときは、カスタムイベントを発行する。そして、その View を処理している改装（=その View を初期化して配下として持っている親側）の中でイベントを拾い、そこで HTTP 送信通信を行う。

### 共通ライブラリに切り出す判断

他のアプリケーションでも使われそうで、かつ行数をそれなりに必要とする一般的な処理は、共通のライブラリとして一発で呼び出せるようにしておきたい。

例えば、エンコードされた URL をデコードしてからリダイレクトするようなとき、相対 URL を取り出す処理を含めると数行を超えたルーチンを書かなければならない。これは実際に、ブラウザ関連のクラスに「リダイレクト」というメソッドとしてまとめられている。

### 401 / 403 のハンドリング

セッションが必要な API を呼び出して、セッションがなかったりユーザが見つからなかったりしたとき、401 / 403 が返却されてくる。JavaScript ではこれらのエラーコードを受け取ったら、ログイン画面にリダイレクトするようにする。

実際にはその画面がアクセスされたときにセッションを確認し、なければログイン画面にリダイレクトされているので、ほとんどの場合は起こらない。しかし、API を「その後、画面を生成するときに実行する」、具体的にはユーザオブジェクトを取ってくる処理を画面ロード後に行うようなときにセッションがない、ということはあまり起こらないが起こりうると想定して、この処理を書く。

### HTML への情報注入

HTML ページに注入するのは、基本的には言語識別子とロケールの辞書。ただし、ドロップダウンメニューのメニュータイトルのようにかなり一般的なものについては、ロケールオブジェクトを使って取り出さなくても、直接テンプレートに注入してもよい。

HTML に直接注入するべき情報として代表的なものは、他にリダイレクト URL。それ以外の情報、特にユーザに紐付く情報は、ほとんどはまず画面を JavaScript で初期化するときに API を呼び出して取ってくる。

ドキュメントがロードされてから、それらのユーザに紐付く情報を取ってくるまでの間に、画面の基本的な構成要素が描画されている。そして、ユーザに紐付くデータが取得できたタイミングで、それらを必要とする画面コンポーネントを生成し、配置する。これがセッションを必要とする画面生成の基本的なフローである。

ログアウトは単に、ドロップダウンメニューにログアウトのボタンを設置し、`<a>` タグで `href` リンクを設置すればよい。

### エラーページ

指定した URL が存在しなかったり、何らかの予期せぬエラーが起きたときのエラーページは、基本的に 404 と 500 の2種類を用意しておけばよい。これらは基本的にアプリケーションごとに独自のものと考えるので、共通化は特にしない。つまり、これらのファイルは独立性のある形で配置されている。関連するファイルは HTML テンプレートとスタイルシートとロケールである。

### 画像・アイコンは SVG で用意する

画像パーツは基本的に SVG で用意する。SVG はロードが速く、色の変更なども容易にでき、一部アニメーションさせることも容易にできるので、パフォーマンスと汎用性が高い。またディスプレイの解像度に合わせて別途用意する必要もない。ほとんどの部品は SVG で作れる。ランディングページに使う写真などはその例外である。

## 画面描画の全体フロー

各画面は大体次のような流れで描かれる。

1. **レンダー HTML** で HTML をブラウザに配信したとき、言語情報やロケール情報といった最低限の情報が注入されている。HTML には、起点となる DOM ツリーの根っこに相当する部分だけが書かれている。
2. `<script>` タグの中で、注入された言語情報やロケール情報が JavaScript のグローバルスコープにセットされる。そして、その画面を描画するための起点となるスクリプトがロード（import）されている。
3. その中では、DOM がロードされたときのイベントハンドラが1番上に書かれている。その中で、その View の1番親となるクラスが初期化される。例えばサインアップ画面だったら `SignUpView` というクラスが初期化される。
4. View クラスのコンストラクターの中では、必ず1つ「ビューを作るメソッド」が呼ばれている。その中でサブビュー要素を初期化していく。

1つの View のまとまりは、1つの View のクラスで表現される。それぞれの View のクラスの中には「画面を作るメソッド」があり、「イベントハンドリングを担うメソッド」があり、さらにいくつかのヘルパー関数もある。

つまり最も大きなフローは、「ドキュメントの DOM ツリーが最初にロードされたら、1番親の View クラスが初期化され、その中でサブビュークラスが初期化され、初期化される中で DOM エレメントが作られる」というものである。

### よく使うクラス

**PageView** — シンプルなクラス。1つの View のまとまりがいくつかのビューに分類できるとき（例: 設定画面ならば設定項目がいくつかに分類できる、サインアップならば各ページに分類できる）に使う。実際にページングさせないとしても、画面を作成した時点で分類できるのであれば、このクラスを使ってあらかじめ分類しておきたい。PageView の責任範囲は、単に View をいくつかのページに整理し、それぞれのページを表示・非表示する制御だけを行うことであり、その中で行われることには一切関与しない。

**TextField** — サーバーに送信したり何かを入力したりするのに必要な大抵のことが書かれているクラス。例えば、入力テキストの変更を追跡する、文字数や正規表現でバリデーションする、文字数を数える、バリデーションエラー時にアラートを表示する、入力文字数に応じてテキストフォームを引き延ばす、といったもの。ほとんどの入力フォームはこのクラスを使って書く。

TextField の HTML 構造はかなり細かいので、ほとんどの見た目はそのままの構造で実現できる。コンストラクターの設定項目の中には、アラートを格納する場所やカウンターを格納する場所などを調整できる項目もある。元の HTML 構造とこれらの設定を組み合わせればほとんど不自由がない。もし不自由なことがあれば、このクラスを拡張・修正するか、多くの場合は、さらに追加のボタンやインターフェイスをつけたいときにこのクラスを継承した専用のフォームクラスを書く。ただし、JavaScript での継承は最小限に抑えることが推奨されるので、継承クラスを作るかどうかは慎重に検討する。

### ページの配置 — ファイル分割の判断

PageView を使うとき、各ページをそれぞれ個別のファイルにすべきか、それとも親ビューのクラスの中で一気に書いてしまうか。これは、それぞれのページ・各画面がどれだけ大きいかで決まる。各画面がそれほど大きくない場合は、1つのファイルの中に書いてしまった方が見通しが良い。各画面がかなり行数が多くなるときにはファイルを分ける。

### コンポーネントへの Locale の持たせ方

大きな View のクラスにロケールオブジェクトを持たせることは許容されるが、細かなコンポーネント単位（例えばフォームなど）には基本的にロケールオブジェクトを持たせない。その代わりに、コンストラクターにテキストを受け取らせ、出力させたテキストを直接セットする。これは、モジュール同士の結合をなるべく疎結合にする原則によっている。

### ロケールキー・定数のハードコーディング

ロケールオブジェクトのキーはほとんどの場合1度しか使われないので、ハードコーディングしてよい。逆に、これらを定数化して一気にまとめて書いたりするのは煩雑になるので、使う場所でハードコーディングする方がコードはシンプルになることが多い。

独自のイベントも同様に、何回も使われそうであればどこかに定数で定義しておくのもよいが、ほとんどの場合は数箇所でしか使われないので、文字列でハードコードしてよい。

### メソッド名の統一

同じ役割を持ったメソッドには、なるべく他と同じメソッド名をつける。そのために、事前にサンプルコードを読んで、頻出するメソッド名を覚えておく。例えば DOM エレメントを作るメソッドは、ほとんどの場合 `createElements` として定義されている。他にも一定の名前のパターンがあるので、サンプルコードを見て覚える。

## エラーハンドリング

Flask の API レスポンス形式のフォーマットでは、基本的にレスポンスのトップレベルに必ず**コード**と**メッセージ**が入るように設計されている。これは成功した場合でもエラーの場合でもどちらでも同じ。したがって、これらがなければ何か予期せぬ不具合ということになる。

レスポンスは3種類に分類される。

### 1. 成功

成功の場合には、2xx 系のステータスコードと成功した旨のメッセージ、そしてその隣にデータが入っていることがある。例えばユーザ情報を更新したら、ユーザの辞書が入っているレスポンス。

### 2. 意図されたエラー

意図されたエラーには大きく2種類ある。

**複数エラー（`errors` キー）** — 複数のエラーが `errors` というキーに入っている場合。これは主にバリデーションエラーで使われる。入力値が複数あり、それらが複数エラーであるとき、各フィールド名とエラー内容をそれぞれ返す必要があるので、`errors` というリストの中にバリデーションエラーを所定の形式で入れて返す。この場合、各エラーは共通の形式であることが保証されている。必ずコードとメッセージが入っている。バリデーションエラーであるならば、フィールド名も入っている。

**単体エラー** — 単純にコードとメッセージが入っている。何か付随するデータがある場合はそれも入っている。

どのエラーオブジェクトにも、エラーコードの意味が書かれた大文字のテキストが入っているが、これは単に開発者が識別しやすくなるためのものであって、ほとんど使われることはない。

### 3. 意図しないエラー

3つ目は意図しないエラー。このエラーは所定の形式に従っていないので、単にレスポンスの中身をそのまま表示する以外にない。基本的にこれは起こってはならないので、見つけた場合にはそれが起きないように修正する。

### まとめ — ハンドリングの3パターン

つまり基本的には、**成功 / 単体エラー / 複数のバリデーションエラー**の3パターンをハンドリングすればよい。

- **成功時** — 勝手に成功のコールバック関数が呼ばれるので、その中でコードとメッセージを拾い、成功後の処理を書けばよい。
- **エラー時** — エラーのコールバックが呼ばれたら、単体エラーか複数エラーかを区別する必要がある。JavaScript の「辞書のフィールドを変数名に割り当てる（分割代入）」やり方を使えば、`errors` が入っているか、コードとメッセージが入っているかを1〜2行で区別できる。どちらの場合でもメッセージを拾って、メッセージを表示すべき場所に渡す。表示先は、TextField かその画面のメッセージテキストのおおむねいずれかになる。TextField の場合は、どのフィールドかを特定するためにフィールド名をエラーオブジェクトから拾って判別し、そのフィールドのアラートメソッドにメッセージを入力すれば、TextField クラスがフッターの中の所定の場所にメッセージを表示する。

## トラブルシュート

### スクリプトを編集してリロードしても変化がないとき

スクリプトを編集してブラウザをリロードしても変化がない場合、スクリプトのビルドが失敗している可能性がある。または JavaScript のコンパイル（transpile）が失敗している可能性がある。

1. まず gulp の自動ビルドプロセスが起動しているかを確認する。起動していなければ走らせる。
2. 起動しているのにスクリプトがビルドされていない可能性がある。dist フォルダにビルドされたファイルが入っているので、これらを手動で削除し、再度ビルドを実行してみる。
3. 特定のファイルがエラーになっていることがある。例えば権限エラーで dist フォルダに書き出されない。この場合は、そのファイルを手動で削除してから再度実行する。
4. 編集した内容が適用されているかは、そのファイルの中身を検索するか、ブラウザに落ちてきたファイルを DevTools で検索して確認する。編集が適用されていない場合は、ビルドが失敗している。

大抵の場合は、ビルド済みのファイルを dist フォルダから削除し、再ビルドすれば解決する。

## スタイルシート

スタイルシートを編集するとき、ベースのスタイルシートは共通ライブラリのデフォルトに書かれている。スタイルのリセットもここに書かれている。基本的にはこれを継承する。

汎用的なビューやコンポーネントのスタイルを新しく書いた場合は、共通側に記載する。

既に書かれているコンポーネントを使って画面を作るときは、アプリケーションのスタイルフォルダに該当するファイルを作り、その中に書く。例えば「ログイン」という識別子でグルーピングされる画面を作るなら、ログインで使われる特定のコンポーネントのスタイルを、そのログイン用ファイルの中に記述する。
