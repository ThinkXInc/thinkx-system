## Claude

push 先については **そのままだと失敗する場面がある**と回答。staging の checkout は `develop` に
居り、`monorepo` は他セッションが自由に push してよい枝。staging から `monorepo` へ push すると、
その間に誰かが push していたら non-fast-forward で弾かれ、サーバーの上で merge を解く羽目になる。

一手だけ変えれば解決する。staging は自分の追跡ブランチである `develop` に push し(素の
`git push` で必ず通る)、Mac 側が `git merge origin/develop` で取り込む。→ D-61

コンパイル配線は実測で解決した。懸念していた「追跡済みファイルを上書きして repo が恒久的に
dirty になる」は起きないことが分かった。

```
                tracked css   tracked js   babel/lessc の出力先との衝突
thinkx              0             0        なし
transformism        4            22        なし(追跡物は common.css / lib/jQuery.js 等の実ソース)
kazukiotsukacom     0             7        js/main.js のみ重なるが、babel の出力とバイト単位で一致
```

staging 上で `npx babel src/js --out-dir /tmp/...` して `cmp` した結果、両サイトとも一致。
site 側のファイル構成を変えずに3サイトとも配線できた。

キャッシュを直そうとしてヘッダを見たところ、**gzip も効いていなかった**。`gzip on` はあったが
`gzip_types` が無く、nginx の既定である `text/html` しか圧縮していなかった。`main.css` 130KB が
非圧縮で流れていた。`Cache-Control` の欠落と同じ場所なのでまとめて直した。

## この回で分かったこと

- **取りうる値が1つしかないものを、引数にも名前にも書かない**
- **デプロイを手元の git の状態に依存させない**(検査のつもりが反映を止める壁になった)
- **冒頭コメントの書き方も責務の所在を示す**(効果を端から端まで書くと、呼んでいるだけの
  スクリプトが自分でやっているように読める)
- **担当の境界を越えない**(状況が見えたからといって別セッションの仕事を引き取らない)
- **確認の対象は手で並べる限り漏れる**(今日2件目)
- **インストール済みのコピーは git の改名では消えない**(古い実装が動き続ける)
