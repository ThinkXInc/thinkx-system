# デプロイ手順書

サイトの変更を staging で確認し、本番へ反映する。

## branch

| branch | 保証していること | 動かす人 |
|---|---|---|
| `monorepo` | 作業線。どこにも反映されない | 全セッション(D-49) |
| `develop` | staging と一致していること。それだけ | オーナーの PR / staging 上の編集 |
| `release/<日付>` | 承認された一点を凍結していること | 承認の瞬間に切る。以後不変 |
| `production` | release と一致していること | オーナーの PR |

## 前提

- commit・push はいつしてもよい。揃える必要はない。
- 揃っているかを見るのは承認の一点だけ。承認とは、確認した SHA から `release` を切ること。
- staging へは `monorepo` を丸ごと上げる。サービスを選んで出す仕組みは持っていない。
- staging は直接編集してよい。
- `develop` / `production` へ直接 push しない。PR 経由。
- `gh` 未認証なら `! gh auth login`。
- timer は未実装(2026-07-21)。各節の「手動」を使う。

## 同期が止まったとき

`deploy.sh` は何も消さずに止まる。止まる理由は3つ。

| 表示 | 意味 | 対処 |
|---|---|---|
| `WRONG-BRANCH` | サーバーが対応 branch に居ない | 表示された `checkout -B` を実行して再実行 |
| `DIRTY` | 未コミットの変更がある | commit・push して対象 branch に取り込む。不要なら破棄。きれいにして再実行 |
| `NON-FF` | 対象 branch に無いコミットがある | push して対象 branch に取り込み、早送り可能にして再実行 |

どうするかはオーナーが決める。スクリプトは消さないし倒さない。

## 戻し方

一つ前の release を production に入れ直す。production を直接巻き戻さない。

```bash
cd ~/Sources/thinkx-system
git fetch origin
git branch -a --list 'origin/release/*'
```

```bash
cd ~/Sources/thinkx-system
gh pr create --base production --head release/<戻したい日付> --title "rollback to release/<戻したい日付>" --body ""
gh pr merge --merge --delete-branch=false
bash infra/scripts/deploy.sh prod thinkx
```

## 原則

- 承認 = 確認した ref から release を切る。承認してから後で切らない。
- キリを揃えるのは commit ではなく承認の一点。
- 全サービスを足並み揃えて出す。選んで出す仕組みは持っていない。
- サービス間に新しい依存を作らない。共通部分は各サービス内にベンダリングして閉じ込める。
  安全を支えているのは「テストが緑」ではなくこの独立性。
- サーバーは reset で無言上書きしない。明示 ref へ ff-only、消せない変更があれば止める。

経緯と、なぜサービスを選べないのかは `docs/archive/discussion-2026-07-21-deploy.md`。
