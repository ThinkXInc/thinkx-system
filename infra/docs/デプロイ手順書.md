# デプロイ手順書

サイトの変更を staging で確認し、本番へ反映する。

## 各 branch が保証していること

| branch | 保証していること | 誰が動かすか |
|---|---|---|
| `monorepo` | セッションの作業線。**どこにも反映されない** | 全セッションが直接 push(D-49) |
| `develop` | **staging の状態と一致していること。それだけ** | オーナーの PR / staging 上の編集 |
| `release/<日付>` | **承認された一点を凍結して保持していること** | 承認の瞬間に切る。以後不変 |
| `production` | **release と一致していること** | オーナーの PR |

`develop` は「安定した線」ではない。staging に今何が映っているかの鏡でしかない。
安定を担保しているのは `release` であって `develop` ではない。

## 前提

- **承認とは `release` を切ることである。** この2つを離さない。離した瞬間に隙間ができ、
  隙間に編集が入る。承認と cut が同一の瞬間である限り、保証は規律なしに成立する。
- **staging は直接編集してよい。** 編集はサービス内に閉じており、独立性により波及しない。
- `develop` に載せてよいのは「staging で検証すべき段階になったもの」。これは `develop` の
  保証ではなく、入口で守る約束。
- 反映は timer が行う。**サーバーに ssh しない。**
- `develop` / `production` へ直接 push しない。必ず PR 経由。
- `gh` の認証が要る。未認証なら `! gh auth login` を実行。
- **timer は未実装(2026-07-21 時点)。実装までは「手動デプロイ」節を使う。**

## 1. 作業を push する

```bash
cd ~/Sources/thinkx-system
git add <自分の持ち場のパス>
git commit -m "<種別>(<範囲>): <要約>"
git push origin monorepo
```

## 2. staging へ上げる

```bash
cd ~/Sources/thinkx-system
gh pr create --base develop --head monorepo --title "staging: $(date +%Y-%m-%d)" --body ""
gh pr merge --merge --delete-branch=false
```

## 3. staging で直接編集する

staging の checkout は `develop` を追っている。編集したらその場で commit + push する。

```bash
cd /src/thinkx-system
git add <編集したパス>
git commit -m "<種別>(<範囲>): <要約>"
git push origin develop
```

作業線に戻す。

```bash
cd ~/Sources/thinkx-system
gh pr create --base monorepo --head develop --title "staging の編集を作業線へ" --body ""
gh pr merge --merge --delete-branch=false
```

## 5. 承認する(= release を切る)

**全サービスが本番へ出してよい状態であることを確認したら、その場で切る。**

```bash
cd ~/Sources/thinkx-system
git fetch origin
git branch release/$(date +%Y-%m-%d) origin/develop
git push origin release/$(date +%Y-%m-%d)
git rev-parse --short origin/develop
```

最後に出た SHA が、このリリースの中身。**以後 develop がどう編集されても、このリリースは変わらない。**

## 6. 本番へ反映する

```bash
cd ~/Sources/thinkx-system
gh pr create --base production --head release/$(date +%Y-%m-%d) --title "release: $(date +%Y-%m-%d)" --body ""
gh pr merge --merge --delete-branch=false
```

マージした時点で prod の timer が拾う。1分以内に反映される。

## 原則

- **承認 = release を切る。** 承認してから後で切る運用を紛れ込ませない。隙間を作らないことが、
  この方式の保証を規律でなく構造にしている唯一の点。
- **全サービスを足並み揃えて出す。** サービスを選んで出す仕組みは持っていない。
- **サービス間に新しい依存を作らない。** 共通部分は各サービス内にベンダリングして閉じ込める。
  この独立性が「staging で A を編集しても綻びは A に閉じる」根拠であり、崩れると本方式の
  前提が崩れる。
