# デプロイ手順書

サイトの変更を staging で確認し、本番へ反映する。

## branch 構成

| branch | 誰が動かすか | 何が反映されるか |
|---|---|---|
| `monorepo` | 全セッションが直接 push(D-49) | どこにも反映されない |
| `develop` | オーナーが PR をマージしたときだけ | staging(timer が自動反映) |
| `release/<日付>` | オーナーが承認時に切る。以後不変 | — |
| `production` | オーナーが PR をマージしたときだけ | 本番(timer が自動反映) |

## 前提

- 反映は timer が行う。**サーバーに ssh しない。**
- `develop` / `production` へ直接 push しない。必ず PR 経由。
- `gh` の認証が要る。未認証なら `! gh auth login` を実行。
- **timer は未実装(2026-07-21 時点)。実装までは「手動デプロイ」節を使う。**

## 1. 作業を push する

```bash
cd ~/Sources/thinkx-system
git add <自分の持ち場のパス>
git commit -m "<種別>(<範囲>): <要約>"
git push origin monorepo
```

## 2. staging へ上げる

```bash
cd ~/Sources/thinkx-system
gh pr create --base develop --head monorepo --title "staging: $(date +%Y-%m-%d)" --body ""
gh pr merge --merge --delete-branch=false
```

## 4. リリース地点を固定する

```bash
cd ~/Sources/thinkx-system
git fetch origin
git branch release/$(date +%Y-%m-%d) origin/develop
git push origin release/$(date +%Y-%m-%d)
git rev-parse --short origin/develop
```

最後に出た SHA が、このリリースの中身。**以後 develop に何が積まれても、このリリースは変わらない。**

## 5. 本番へ反映する

```bash
cd ~/Sources/thinkx-system
gh pr create --base production --head release/$(date +%Y-%m-%d) --title "release: $(date +%Y-%m-%d)" --body ""
gh pr merge --merge --delete-branch=false
```

マージした時点で prod の timer が拾う。1分以内に反映される。

```bash

```

## 原則

- **全サービスを足並み揃えて出す。** サービスを選んで出す仕組みは持っていない。
- **release branch を切ったら、その中身は変わらない。** 承認から反映まで日が空いてよい。
- **サービス間に新しい依存を作らない。** 共通部分は各サービス内にベンダリングして閉じ込める。
  この独立性が「B の綻びが A を巻き込まない」根拠であり、崩れると本方式の前提が崩れる。
