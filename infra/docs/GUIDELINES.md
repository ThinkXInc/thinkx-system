# GUIDELINES — 一般規則(指示を2度繰り返さないための記録)

原文(「」)を維持する。各項目に 状況(何が起きてこの指示が出たか)と 適用(どうなったら同じケースか)を書く。
解釈を加える場合は「解釈:」に分離する。決定事項の蒸留は DECISIONS.md。

## ドキュメント化

- 「質問したことは解決策を適切な場所にドキュメント化しそのまま実行できる形式(過去の弊社のドキュメントを参照)としてのこせ　この指示も一般規則として繰り返さなくていいように残せ」
  - 状況: リハーサル冒頭、「グローバル IP を /32 で取る方法」を質問された。チャットで答えるだけで終わるところだった。
  - 適用: 作業中に kaz が「どうやるの?」と聞いたら、答えをチャットに書いて終わりにせず、該当手順書(step1-rehearsal.md 等)の該当箇所に copy-paste で実行できる形で追記する。

- 「気づいた点は随時findingsに書く　一般規則として覚えておいて」
  - 状況: 設計レビューで問題(F1 鍵・F2 証明書…)を発見し、私が「findings に残すこともできます」と提案の形で聞いた。聞くまでもなく書け、という指示。
  - 適用: レビュー・照合・デバッグ中に問題/穴/確定事実を見つけたら、確認を待たずその場で findings.md に追記する。

- 「私の書いたシンプルな記述を余計にごちゃごちゃ変えすぎだから　ほぼそのまま使うことを意図して書いて渡した文面はほぼそのまま使え」
  - 状況: kaz が deploy key の説明文を「なるべく維持しかつ不具合は直して」と渡したのに、私は見出し・前置き・補足注記・番号付き解説を足して原型を大きく変えた。
  - 適用: kaz が「ほぼそのまま使え」「なるべく維持」として文面を渡したら。体裁・言い回し・順序を変えない。
    やってよいのは (1) 空所(`...` や「以下のコマンド」等)を具体コマンド/パスで埋める (2) 明確な不具合(誤パス等)を直す、の2つだけ。見出し・前置き・解説・注記を足さない。

- 「私が書いたようなスタイルを維持しろ　わざわざ ...ならOKのようなシンプルな表現をしている　そうした私のスタイルを真似る一般規則をドキュメントに集約しろ」
  - 状況: kaz が step1-rehearsal.md の Prerequisites を「要件+完了条件(〜ならOK)」で簡潔に書いたのに、私が「完了条件:」等のラベル付き・段落調に**書き直して**提示した。二度却下された。
  - 適用: kaz が書いた文を触るとき。並べ替え・言い換え・ラベル付け・水増しをせず、頼まれた差分だけ。書く前に `docs/conventions/DOC_STYLE_GUIDES.md` と `doc_style_examples/` の近い実例を見る。

- OK/NG 集は「実際に記述の仕方を指摘されたとき以下に記載する．その際に解釈を加えないこと．単に直される前と後の文を書く」(DOC_STYLE_GUIDES.md より)
  - 状況: 私が OK/NG 例集に「→ 頼まれた差分だけ。並べ替えをしない」等の注釈・一般化を付けて作り、「全然だめだ　一般化しきれていないのでおかしなドキュメントへの制約になるだけだ」と却下された。
  - 適用: スタイル指摘を受けたら、直される前/後の文だけを DOC_STYLE_GUIDES.md の OK/NG 集に追記する。教訓めいた注釈を足さない。

- 「こういうのは必ずルールdocsにメモね」
  - 状況: 図の色ルール(追加=緑等)を私がチャット上の合意のままにしていて、後で私自身が思い出せなくなった。
  - 適用: 繰り返し使うルール(色・命名・フォーマット等)を口頭合意のままにしない。決めた瞬間に該当ルール doc(runbooks/ scripts/README 等)へ書く。

- 「私の指示をどこかのファイルに書き溜めているのか？」「このstatus.shをゼロから書こうと思ったらそれを見れば作れるようなものを」
  - 状況: plan-summary の仕様(図・色)を何度も言わせてしまい、指示がチャットに散逸してツールを作り直せる記録が無かった。
  - 適用: ツールへの指示を受けたら `scripts/README.md` に「ゼロから再実装できる粒度」の要件として追記する。実装だけ直して要件を書かないのは NG。

- 「私の指示の意図を勝手に拡大解釈して書き留めたりせず原文を維持して記録し，文脈を記録し，つまり勝手な解釈をなるべく加えないようにあるいは解釈は分離して書くように」
  - 状況: 本ファイルと DECISIONS.md の作成指示時。過去に私が指示を要約・言い換えて記録し、意味がずれた(例: D-3「リハは鍵不要」を「鍵方式はリハ/本番の区別と無関係」と誤って上書き)。
  - 適用: 指示を記録するときは常に。原文コピー+状況+適用。自分の言葉での要約を原文の代わりにしない。

- 「GUIDELINESの文脈が浅すぎて再現(同じケースを認識したり)がそれじゃ困難だろう」
  - 状況: 本ファイル初版で文脈を「(文脈: リハーサル開始時)」程度しか書かず、次のセッションが同じケースを認識できない形だった。
  - 適用: 記録には「何が起きてこの指示が出たか」「どうなったら同じケースか」まで書く。

- 「A liteとは？よくわからない用語を使うな」
  - 状況: quantz-web 切替の選択肢に「A-lite」という自作ラベルを付けて提示し、意味が通じなかった。
  - 適用: 選択肢・提案は自作の略語やラベルでなく、中身をそのまま短文で書く(例: 「quantz-web の conf.d 掃除を先に行い、切替を1回にする案」)。

## setup スクリプト(setup_*.sh)

- 「私が想定していたのはrawドキュメントの手順をそのまま実行するスクリプトを置いておき，将来的にほぼそのままdockerfileにも変換されるというものだ」
  「setup_...はこういうオリジナルのドキュメントをほぼそのまま実行ファイル化することを意図している」
  - 状況: 私が raw doc を無視して独自構成の setup(clone_or_update 関数・ガード・env-setup 抽象化)を書いた。「env-setup.shとか意味不明だから捨てて」と全却下。さらに見本として kaz が setup_supercom3.sh(doc ほぼそのままの sh)を書いて示した。
  - 適用: setup_ 系を書く/直すとき。まず対応する raw doc を開き、コマンドを上から並べる。独自の構成・抽象化を発明しない。

- 「要点は上からシンプルに実行するだけのシンプルな記述を書くこと　前にdockerfileにほぼそのままできるようにと言ったはず　bashの分岐などがあるとそれができない」
  - 状況: 上記の却下時。私のスクリプトには if/for/関数/set -euo pipefail が入っていた。
  - 解釈: setup_*.sh に if/for/関数/set -e を書かない(linear)。
  - 適用: setup_ 系に制御構文を書きそうになったら、このケース。書かずに済む形(コマンド列・コメントアウト)にする。

- 「setup_supercom3.sh はほぼそのままドキュメントをshにした　これは変えるなよ」
  - 状況: 私が見本の setup_supercom3.sh を「実行可能に整形」と称して勝手に書き換えた。kaz が原本に戻した。
  - 適用: kaz が「見本」「これは変えるな」と言ったファイルには一切手を入れない。参照のみ。

- 「私のドラフトから変更する場合は許可を仰ぐように」
  「もし変更したほうが良い箇所があればその変更の理由とともに尋ねてくれ」
  - 状況: kaz が setup_webserver.sh を quantz-web 完全環境として書き直した(ドラフト)。私はそれを完成させる役割で、勝手に編集しかけた。
  - 適用: kaz が書いた/書き直したファイルを変更する前。変更点を列挙して許可を得てから編集する。

- 「全体的に理由が日本語として完全でなく意味がわからないというか解釈が特定できない　もう少し丁寧に書け」
  - 状況: 上記の許可伺いで「`vim` → heredoc に(bashrc に永続化)」のような略記で理由を書き、意味が特定できないと差し戻された。
  - 適用: 修正の許可を求めるとき。各項目を「現状 / 何が問題で動かないか / どう直すか / なぜそう直すか」の完全な文で書く。

- 「最上部に余計な記述を追加したりするな　Keep it simple please」
  - 状況: 私が setup_webserver.sh の冒頭に長い banner コメント(===== 枠・役割説明・制約の列挙)を付けた。kaz の見本は 1 行の見出しだけ。
  - 適用: ファイル冒頭に説明を書くとき。1 行(多くて 2-3 行)に収める。banner 枠・箇条書きの前置きを付けない。

- 「実行不可能なものは明らかに直すべきものは直してくれ」
  - 状況: raw doc 由来の `vim 〜`・ssh-keygen の対話プロンプト表示行・`newgrp`(新シェルで停止)・watcher(常駐)・`{version}` リテラル等が sh に残っていた。
  - 適用: doc→sh 化で、流すと止まる/エラーになる行を見つけたら。直すが、その変更は上記の許可制に従い報告する。

## run スクリプト(デーモン制御)

- 「/src/quantz-web/web-server/etc/restart.shをみに行くのでなくここに実行するコマンドを直接書くんだよ　なぜならデーモンの起動などはこのinfraレベルが握っているのであってquantz-web側でないだろ」
  - 状況: infra/run/ の restart_quantz.sh 等を、repo 内の restart.sh を source する委譲方式で作って却下された。
  - 適用: infra/run/ の run_/stop_/restart_ は、repo のスクリプトを呼ばず systemctl 等の実コマンドを直接書く(linear)。repo 側スクリプトは参照ノウハウであって実行経路にしない。

- 「restartの生コマンドでなくrun/restart_ スクリプトを使おう　このスクリプトにナレッジを蓄えられるかもしれないから」「restart_webserverってなんでまとめてrestartしようとする？そんなケースはほぼない　サイトごとだよ　だから混じっていてわかりにくかった」
  - 状況: restart_webserver.sh が全サイトの uwsgi をまとめて restart し、未セットアップの kazukiotsukacom が混じって分かりにくかった。また私は restart を生の ssh コマンドで案内していた。
  - 適用: run/stop/restart は**サイト/サービス単位**で持つ(host まとめ版を作らない)。命名は deployable unit(setup_/repo 名)に一致。日常操作は生コマンドでなく run/ スクリプト経由にし、順序・journal・色 verify 等のナレッジをスクリプトに蓄える(D-41)。

- 「loadbalancerは今本番で動いているがmasterにpush? 2026refactorでなく？ もうpushしてしまったが 実機は自動で変わらない」
  - 状況: AWS 用の LB 設定変更(web1.supercom.internal)を loadbalancer repo に入れる際、私が「master に push」と案内した。master はオンプレ本番 LB の生きた設定で、そこに AWS 用を載せるとオンプレが pull 時に壊れる。
  - 適用: 他リポジトリ(loadbalancer / 各サイト)の変更は infra から push しない。**私が workspace clone で編集して diff を見せ、commit/push はオーナー**。AWS 用は master でなく **2026refactor**(master=本番不変)。全 repo 2026refactor 規約に従う(D-42)。

- 「実運用のためのstaging.でありそのために実装する 確認だけできればいいのではない」
  - 状況: 私が他サイトの staging 確認に /etc/hosts の一時的な方法を勧めた。オーナーは共有できる恒久 staging URL を実装したい。
  - 適用: staging.<domain> は実運用の共有 URL として実装(Route53 A 手動 + ワイルドカード証明書 + LB vhost)。「確認だけ」の /etc/hosts で済ませない(D-43)。

- 「bashスクリプトを格納する命名規則はquantz-webを踏襲せよ scriptsはpyにしばしばつかわれる」
  - 状況: health/trace スクリプトの置き場所を `scripts/` にしようとした時。quantz-web の慣例は
    bash はコンポーネント直下(`web-server/etc/*.sh`・`vectordb_server/*.sh`・loadbalancer は repo 直下)で、
    `scripts/` は python 用。
  - 適用: 新しい運用 bash は component 直下 or `etc/`(infra なら `infra/etc/`)に置く。`scripts/` に bash を足さない。

- 「分岐は必要あるのか　もしプログラム的なものが必要ならbashでなくpythonにすべき bashは読みにくくエラーを頻繁に出すからだ これは一般規則に書くに値する」
  - 状況: setup_user.sh に if/grep ガードの分岐が3つ入っており linear 原則に反していた(かつ silent failure の温床になった)。
  - 適用: bash に分岐・ループ・状態管理を書きたくなったら、それは python(`scripts/`)にするか、
    「上書き=冪等」(tee + config.d/Include のような構造)で分岐自体を消す。bash は linear コマンド列に限る。

- 「Deploy Keyが新たにレポジトリを追加するたびに人間が設定したかどうか忘れるとハマるのでは困る　しかも追加のたびにsetup user.shの実行が必要になるのはおかしい　例えばkeyは一度出したらどこかに保管しておき，setup_{service}で検出して"Deploy key {}を追加してください"の警告を出すべきだ　ここでkeyを吐き出せれば完璧だ」
  - 状況: nginx-web-root 新設時に Deploy key 未登録で clone が silent に失敗した。鍵管理が setup_user.sh の REPOS ループに同居しており、repo 追加のたびに人間の記憶に依存していた。
  - 適用: 各 setup_{service} の冒頭で **check_deploykey.py <repo>** を呼ぶ(preflight)。
    鍵の真実は Mac の infra/deploykeys/、setup 前に certs と同梱の tgz で配る。
    未整備なら公開鍵と手順を表示して**戻り値で停止**(bash の exit は使わない=ssh を切るため)。
    ライフサイクル(user=マシン1回 / key=repo ごと)を混ぜない。別名 = repo 名。

- 「exitはsshが切れるから使うな」
  - 状況: preflight を bash の exit で止める案を出した。ssh 'bash -s' < script では exit がセッションごと殺し、
    「鍵を見せて同一セッションで続きを案内」ができない。
  - 適用: リモートで流す script では終了に exit を使わない。Python は `sys.exit(main())`(自プロセスのみ)、
    bash 呼び出し側は `|| { …; false; }` で戻り値判定。

- 「secretsはここに秘密があると自ら告知しているようなもの　階層が深いのは見つけにくい」
  - 状況: 鍵の保管を infra/secrets/deploykeys/ に置く案を出した。
  - 解釈: ディレクトリ名を変えても秘匿効果はない(security by obscurity)。守りは .gitignore と read-only 鍵。
  - 適用: 保管は浅く見つけやすい場所(infra/deploykeys/・infra/certs/)。名前を「隠す」目的にしない。

## 手順書(そのまま実行できる形)

- 「そうやって追加で説明するんでなく macから ssh -i ~/...   # web のようにはじめから書けよ」
  - 状況: terraform output の ssh コマンドに -i が無く Permission denied になり、私が後から「-i を付けてください」と会話で補足した。
  - 適用: 手順書・output に書くコマンドは、初見で copy-paste して通る完全形(鍵・env 変数・cd 込み)で書く。会話での後出し補足が要る時点で手順書側の不備。

- 「こういう書き方でなく上からそのまま実行していけばできるように書け」
  - 状況: 手順2の冒頭に「# 前提: user_setup.md の前処理を先に済ませる」という注記を書いた。前提を注記で示すのではなく、前処理コマンド自体を手順の中に順番に置くべきだった。
  - 適用: 手順書に「先に〜しておくこと」と書きそうになったら。その前処理を実行行として手順に組み込む。

- 「アナタノ.envのpass ?そのままコピーして動くコードをいつも貼れ　必要な情報は聞け」
  - 状況: curl コマンドに `-u thinkx:<あなたの.envのpass>` とプレースホルダを書いて渡した。
  - 適用: 貼るコマンドはプレースホルダ禁止・そのまま実行して動く形にする。値が要るなら
    (1) その場でファイルから読む(例: `set -a; . infra/env/loadbalancer/.env; set +a` して `$VAR` を使う)
    (2) 読めない/不明なら**ユーザに聞く**。`<...>` を残して丸投げしない。

- 「ssh supercom-web に飛んでから実行する必要があるのにsshが書かれてないじゃん　上からそのまま実行していくだけにして　一般規則化して」
  - 状況: 鍵回収の手順に「# web マシンから回収」という地の文の見出しだけ書き、そのブロックを実際にどこで実行するか(Mac か web か)がコマンド上に現れていなかった。
  - 解釈: 実行場所は地の文の見出しで示してはならない。場所の切り替えは `cd` / `ssh` という**コマンドそのもの**で示す。
  - 適用: 手順は上から順にそのまま貼って実行できる形にする。実行マシン・ディレクトリが変わる箇所は、その切り替えを実行行(`cd …` / `ssh host '…'`)として明示する。「〜マシンから」「〜で実行」のようなコメントで代替しない。先頭に必ず起点(`cd <path>` または `ssh <host>`)を書く。

## アセット配布・フロー組込

- 「動画は thinkx/web-server/views/video に置かれているはず　これが所定のディレクトリ　他のサイトも基本的に同じ　ローカルに置いてある　転送するスクリプトが必要だがこれを忘れると動画がないというのでなくec2立ち上げ->setup->runの流れに自然に組み込まれているのがいいだろう」
  - 状況: clone しても views/video は空(git 管理外)で staging に動画が出なかった。
  - 適用: git 管理外の実アセット(動画等)は `etc/push_assets.sh` で配り、setup_<site> が展開する。
    配り忘れても silent に欠落させず **setup で黄 WARN** を出す。ec2→setup→run の標準フローに組み込む(D-40)。

## 図・料金(plan-summary)

- 「毎回AWSでインフラの設定を変更するたびに料金見積もりが返却されるようにしたい」「明らかに停止する時間が長くそれにより料金が変わる場合標準的な使用を想定し考慮する」
  - 状況: 機能追加依頼(リハーサル中)。curl 不可のためネット料金 API は使えず、静的料金表方式にした。
  - 適用: terraform を変更する作業では、apply 前に料金(cost-estimate)を出す。

- 「terraform applyで実際に適用するとしたらこの時点でどうインフラが作られたり変更されるのか明確に把握する必要がある　そのための図を料金の前に出してくれ」「変更分や削除分を緑や赤で表示できると最高だ」「いちいち指示しなくても自動で描くようにしてと言ってる」
  - 状況: plan の生出力だけでは全体像が掴めない、図は毎回頼まずとも出てほしい、という要望。私が「図は LLM に頼む」運用にして却下された。
  - 適用: apply 前の確認は plan-summary.sh(図+変更色+料金が自動で出る)を使う。人に図を描かせる/描くのを省く運用にしない。

- 「図は参考であり terraformの出力から構成するんだろ　そして変更があったらそれを検出して色分するんだろ」
  - 状況: 図が静的テンプレの env 置換だけで、plan と無関係だと発覚した時。
  - 解釈: 変更検出は terraform plan(config と実 state の差)。git 差分ではない。
  - 適用: 図の色は必ず plan の resource_changes から取る。

- 「図が模範から変わってるだろ　変更なしは単に普通に出すだけだよ　追加と変更だけ色づけしろといっただろ」
  - 状況: 私が模範を捨てて自作の箱レイアウトを生成し、さらに変更なしを淡色にした。二重に指示違反。
  - 適用: 図の見た目は runbooks/diagram.md の模範のまま。色づけは追加/変更/削除だけ。変更なしに色や淡色を付けない。

## 完了報告の帰属と偽緑の禁止(オーナー指摘 2026-07-17)

- **原文**: 「一つのタスクだけが終わったということを意味しているのか、それともこの全体が終わったのかがよくわからない。」「一個一個のスクリプトに完了報告を緑で書くと、複数のスクリプトを同時に実行した時に、どれがどれだかわからなくなる問題を本質的に解決することは無理なんだろうか。」
- **実事故**: $LB 未設定で push_env の引数がずれ「サイト0件」となり、0件転送を「OK: 全件完了」と緑報告(偽緑)。
- **運用**: (1) 判定行には**スクリプト名・対象ホスト・件数**を必ず含める(例 `OK: push_env -> supercom-lb 全件完了(1 件)`)。行単体でどの処理の結論か判別できること。(2) **0件成功は成功と報告しない**(usage 赤で落とす)。(3) 手順書の各ブロックに変数ガード `: "${VAR:?手順0の変数を先に貼る}"` を置き、前提欠落は先頭で赤停止。

### 訂正(オーナー指示 2026-07-17): 変数ガードは廃止
- **原文**: 「その他のセッションで変数がない時に引っ張ってくるのは、コマンドが複雑になるからやめろ。ステップ0と書いてあるのが分かりにくいので、それをプリリクイズイットにして、必ず必須の処理にすればいいんだよ。」
- **運用**: ブロック内ガード(`: "${VAR:?...}"`)は削除。代わりに冒頭を **prerequisites(必須)** と命名し、新しいターミナルでは必ずそこから。コマンドは素朴に保つ。

### 訂正2(オーナー指示 2026-07-17): prerequisites 方式に一本化
- **原文**: 「ssh $WEB 'bash -s' < これをやめろと言ってる。ごちゃごちゃしすぎてる。プリークイズって書いたんだから、これは必ずしも必要ない。むしろさっきの変数がなかったら結局(エラー)を出す方がよかった。」
- **運用**: prerequisites に cd・変数・`run()`(= ssh 'bash -s' の包み)を定義し、各ステップは `run $WEB setup_thinkx.sh` のような素の1行に。ブロック内の cd 繰り返しは手順書では不要(prerequisites が必須のため)。prerequisites を飛ばすと `run: command not found` で即赤く落ちる=前提欠落の検出はこれで足りる。

## worktree とデプロイに関する恒久指示(オーナー指示 2026-07-20)

- **原文**: 「ローカルのGitの履歴とは全く独立してデプロイができる必要がある」
- **運用**: monorepo の並行作業は track ごとの専用 Git worktree で行い、同一 working tree を
  複数セッションで共有しない。通常のデプロイは origin 上の承認済み `DEPLOY_REF` を staging で
  確認した後、同一 ref を production に適用する。ローカル Mac の現在の Git 状態(branch・HEAD・
  未コミット変更)をデプロイ元にしない。サーバーで自動起動する Claude/Codex は専用編集 worktree を
  使用し、clean に保つ deploy checkout では起動しない。
- **文書の分担**: 決定理由=`docs/DECISIONS.md`(D-58) / 拘束規則=`infra/CLAUDE.md` /
  worktree の割当と手順=`docs/WORKTREES.md` / インフラ固有操作=`infra/docs` 配下 /
  Codex 固有の停止判断=`.codex/GUIDELINES.md`
