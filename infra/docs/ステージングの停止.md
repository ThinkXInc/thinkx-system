# ステージングの停止（スマホの Claude から staging EC2 を止める仕組み）

staging サーバー（web1-stg）の tmux では Claude Code が常駐している。オーナーはスマホの
Remote Control からこの Claude に指示できるので、**「停止して」と言うだけで PC を触らずに
staging EC2 を止められる**ようにする。それがこの仕組み。

インスタンスは **stop**（terminate ではない）なのでディスクは残り、次に AWS コンソール等から
start すればそのまま復帰する。止まっている間は EC2 の課金が止まる（EBS は残る）。

## 現状: 稼働中（2026-07-24 検証済み）

準備完了。ロール `staging-web1-stop-self` がアタッチされ、aws CLI v2 が
`~/.local/bin/aws` に導入済み。`stop-instances --dry-run` で
"Request would have succeeded" を確認した。

**スマホの Claude に「ステージングを停止して」と言えば止まる。**

方式は IAM ロール（自分自身しか止められない最小権限）。shutdown 案は sudo が
要パスワードで Claude から実行できず、`InstanceInitiatedShutdownBehavior` が
terminate の場合インスタンスごと消えるため棄却した。

## 対象の事実（実測値）

| 項目 | 値 |
|---|---|
| ホスト名 | `web1-stg` |
| インスタンス ID | `i-09d3675f4e1a61e28` |
| リージョン | `ap-northeast-1` |

インスタンス ID はインスタンスを**作り直すと変わる**（terraform destroy/apply で再作成した
場合など）。作り直したら本書のポリシー JSON と下の停止コマンドの ID を更新すること。

## 準備手順（オーナーが AWS コンソールで行う・初回のみ）

Claude からは AWS の認証情報が無いためできない。コンソールで3ステップ。

### 1. IAM ポリシーを作る

IAM → ポリシー → ポリシーの作成 → JSON タブに以下を貼り付け。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "StopSelfOnly",
      "Effect": "Allow",
      "Action": "ec2:StopInstances",
      "Resource": "arn:aws:ec2:ap-northeast-1:*:instance/i-09d3675f4e1a61e28"
    },
    {
      "Sid": "DescribeForStatusCheck",
      "Effect": "Allow",
      "Action": "ec2:DescribeInstances",
      "Resource": "*"
    }
  ]
}
```

- 名前: `staging-stop-self`（任意だが分かるものに）
- 1つ目の Statement が本体。**このインスタンス1台の stop だけ**を許す。start も terminate も
  他のインスタンスも許さない。乗っ取られても「staging が止まる」以上のことはできない。
- 2つ目は停止前後の状態確認用（`DescribeInstances` はリソース単位の制限が効かない API
  なので `*`。読み取り専用）。不要なら削ってもよい（stop 自体は1つ目だけで動く）。

### 2. IAM ロールを作ってインスタンスにアタッチ

1. IAM → ロール → ロールの作成 → 信頼されたエンティティ: **AWS のサービス** → ユースケース: **EC2**
2. 上で作った `staging-stop-self` ポリシーを選択
3. ロール名: `staging-web1-stop-self`（任意）で作成
4. EC2 → インスタンス → `i-09d3675f4e1a61e28`（web1-stg）を選択 →
   アクション → セキュリティ → **IAM ロールを変更** → 作成したロールを選択 → 保存

インスタンスの再起動は不要。アタッチした瞬間から IMDS 経由で資格情報が取れるようになる。

### 3. Claude に「aws CLI を入れて停止を検証して」と指示する

ここから先は staging の Claude ができる。aws CLI v2 を導入し、
`aws ec2 stop-instances --dry-run` で権限が通ることを確認する（dry-run は実際には
止めずに権限だけ検証する）。検証まで通ったら本書の「現状」節を「稼働中」に書き換える。

## 使い方（準備完了後）

スマホの Claude（この tmux セッション）に「ステージングを停止して」と言う。Claude が
実行するのは:

```bash
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
IID=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/instance-id)
aws ec2 stop-instances --region ap-northeast-1 --instance-ids "$IID"
```

- インスタンス ID は決め打ちせず IMDS から取る（作り直しに強い）。ポリシー側の ID だけ
  合わせておけばよい。
- 実行すると**この Claude セッションも道連れで落ちる**。返事は途中で途切れるが正常。
  tmux セッションはインスタンス stop で消えるため、次回 start 後は tmux / Claude を
  起動し直す（サービス群は systemd で自動起動する）。
- 停止の確認はスマホの AWS コンソールアプリか、start し直したあとの `uptime` で。

## 再開（start）の定型ルーチン

**start はこの仕組みの対象外**（止まっているサーバーの中の Claude は動いていないので
自明に不可能）。ローカル（Mac）から次の2コマンドを叩く。これが staging の実行ルーチン:

```bash
cd ~/Sources/thinkx-system
bash infra/scripts/start_staging.sh
bash infra/scripts/attach_claude.sh
```

- `start_staging.sh` は停止中でなければ何もしない（「既に稼働中」で正常終了）ので、
  常にこの2つを叩いてよい。EIP 保持(D-53)のため IP・DNS・ssh 設定は不変。
  nginx / uwsgi 等のサービスは systemd で自動起動し、スクリプトが active まで確認する。
- `attach_claude.sh` は tmux セッションが無ければ作成・あればアタッチ(`tmux new -As`)。
  再起動後はセッションが消えているので新規作成になる。中で Claude Code を起動すれば
  スマホから指示できる状態に戻る。
- Claude Code の起動時自動化(systemd unit で tmux + Claude を自動起動)は採らない。
  無人で AI が走り続ける構成になるため、起動はオーナーの明示操作に残す。
