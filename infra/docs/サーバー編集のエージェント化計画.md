## 1. 配置先: supercom-web1-stg(staging の web)1台のみ

理由:
- 編集対象(/src/thinkx-system と各サイト)と実行環境(node v24 / python / uwsgi)が既に揃っている
- 編集 → ビルド → https://staging.<domain>/ での即時確認が同一マシンで完結する(サイト編集フローの想定と一致)
- **prod には置かない**: 本番は「git pull + run スクリプトで反映するだけの箱」を維持する。対話ツールと認証情報を本番に置かない
- lb は編集対象を持たないため対象外

懸念: t3.small(2GB RAM)。Claude Code + フロントビルドの並走でメモリが逼迫したら t3.medium 化(terraform 1行の in-place 変更・承認制)。

## 2. インストール: setup_claude_code.sh を別立て新設

- setup_webserver.sh には入れない(全 web 箱の必須要件ではなく、認証という手作業を含むため)
- `infra/setup/setup_claude_code.sh`(冪等・末尾に色つき verdict):
  前提確認(node v18+ / tmux)→ `npm install -g @anthropic-ai/claude-code` → verify(`claude --version`)
- 構築手順.md には載せない(必須工程でないため)。接続手順は 運用.md に追記する

## 3. 認証

- 初回のみ tmux 内で `claude` を起動して対話ログイン(オーナー実行)。認証情報は /home/kaz/.claude/ に永続
- 認証ファイルは **git にも secrets.tgz にも入れない**(このマシン固有・失われても再ログインで再生成可能)

## 3.5 認証スコープ(v1.2・個人 Max アカウント運用の露出範囲)

- このトークンで**できない**こと: オーナーの claude.ai 過去対話の閲覧・他マシンの Claude Code セッションの閲覧
  (履歴と記憶はマシンごとにローカル)
- **できる**こと(共有時の前提): ①オーナーの Max 枠を消費しオーナー名義で動く
  ②このサーバー上に蓄積したセッション履歴・記憶は tmux に入る全員が読める
  ③バージョンにより claude.ai 連携(セッション同期・Artifacts 一覧/更新)がオーナーアカウント配下で動く
  → 気になる連携は claude の /config で無効化
- 運用原則: **サーバー上の Claude と個人的な内容の対話をしない**(チーム共有前提の場)
- v2: サーバー専用アカウント(Team プラン1席 or API キー課金)で個人と構造分離(コスト増・オーナー判断)

## 4. tmux 運用

- セッション名は固定で `claude`
- どのマシンからも1コマンドで入る(無ければ作成・あればアタッチ。複数マシン同時アタッチ可):

```
ssh -t supercom-web1-stg 'tmux new -As claude'
```

- 抜けるのはデタッチ(Ctrl-b d)。セッションと Claude Code は残り続ける

## 5. git push の扱い(承認点)

- 現在の deploy key は読み取り専用のため、サーバー上で作った commit を push できない
- **案A(推奨)**: thinkx-system にのみ**書き込み可**の deploy key を新設し、staging web だけに配布する
  (gen_deploy_key.sh で生成 → GitHub 登録時に Allow write access を有効化)
- 案B: サーバーでは commit まで・push は Mac から — 体制の目的(サーバー完結の編集)と矛盾するため非推奨

## 6. 規約との整合

- /src/thinkx-system で起動するため、リポジトリ内の CLAUDE.md / AGENTS.md / .claude/settings.json がそのまま効く
- **サーバー上の Claude Code から terraform は実行しない**: tfvars / state は Mac にのみ存在し、インフラ変更は Mac 側セッションの管轄。破壊操作・secrets のゲートは従来どおり
- Claude Code のメモリ(~/.claude/)はマシン固有で Mac 側と共有されない。共有すべき知見は従来どおり
  リポジトリの GUIDELINES / DECISIONS / findings に書く(それが正本)

## 7. 実行手順(承認後)

1. setup_claude_code.sh を書いて push(Claude)
2. `run $WEB setup_claude_code.sh`(オーナー・staging prerequisites 下で)→ 緑 verdict
3. 案A 承認時: 書き込み deploy key を生成・GitHub 登録・配布(オーナー)
4. tmux 内で claude 初回ログイン(オーナー)
5. 運用.md に接続手順を追記(Claude)

## 8. 本番への反映フロー(v1)

- staging(サーバー上)で編集 → ビルド/restart → https://staging.<domain>/ で確認
- OK なら commit + push(monorepo ブランチ)
- **本番反映は手動ゲート**: `bash infra/scripts/deploy.sh prod <サイト...>` を実行した瞬間だけ本番が変わる
  (prod の /src/thinkx-system を pull し、指定サービスを restart スクリプト経由で再起動・色つき verdict)
- CI は使わない(v1)。push 型 CI は SSH を GitHub に開放する必要があり SG 設計(22 はオフィス IP のみ)と衝突。
  自動化するなら pull 型(prod の systemd timer)が正解だが、承認ゲートを手放すため当面不採用
- **prod 側に Claude Code を置いて pull+restart を実行させる案は不採用**(検討 2026-07-19):
  ①この操作は固定2コマンドで判断が不要 = エージェントは価値を足さずリスクだけ足す
  ②「prod は pull して動かすだけの箱・対話ツールと認証情報を置かない」(1章)に反する
  ③人間が deploy.sh を打つこと自体が承認記録であり、エージェント経由は決定と実行の間に解釈層を挟む。
  staging 箱の Claude Code も prod への SSH 鍵を持たない(持たせない)ため、deploy は操作者のマシンからのみ

## 9. 複数参加者と役割別応答(v1.1)

- tmux 共有セッションは1枚の共有ターミナルで、**誰が打鍵したかは Claude から見えない** →
  発言の冒頭に**名乗り**(名前または役割)を付ける運用にする。例: 「kaz:」「(広報・非エンジニア):」
- 役割ごとの応答プロファイルは `docs/ROLES.md`(新設・v1.1 実行時)に定義し、サーバー上の Claude が参照する:
  - 開発者: 通常どおり(diff・コード・技術用語可)
  - 非エンジニア: 専門用語を避ける・コードや diff を見せない・staging.<domain> の見え方と UI/使い勝手の言葉で対話・
    変更は「どのページのどこがどう変わるか」で説明
- **名乗りは応答の仕方だけを変える。権限は変えない**: 破壊操作・secrets・本番反映(deploy.sh prod)の
  承認ゲートは役割宣言と無関係に維持する
- 文脈を混ぜたくない場合は人ごとの別セッション(tmux new -As claude-<名前>)も可。ただし記憶は共有されないため
  共同作業は共有1本 + 名乗りを推奨

## 9.5 ROLES.md の配線(残作業・オーナー1行)

docs/ROLES.md は作成済みだが、サーバー上の Claude が読む CLAUDE.md から参照されていない。
CLAUDE.md はワークスペース制御文書のため Claude は書き換えない — **オーナーが次の1行を CLAUDE.md に追加する**:

「**サーバー共有セッションの応答規約**: tmux 共有セッションでは `docs/ROLES.md` の名乗り運用に従う。」

## v2 検討事項

- ブランチ分離: staging ブランチで作業 → 検証後に本番ブランチへ昇格(merge)→ prod は本番ブランチのみ pull。
  v1 は単一ブランチ + 手動ゲートで開始し、運用してみて昇格レビューが欲しくなったら導入
- pull 型自動反映(staging 箱のみ): 編集が Mac 側からも行われる場合の staging 即時反映
- サーバー専用の Anthropic アカウント(個人 Max との構造分離。3.5 章)
- バックアップリポジトリへの push(deploy.sh に1行。GitHub アカウント侵害まで守る層)
