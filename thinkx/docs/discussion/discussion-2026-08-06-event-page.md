## 1. ページ追加の方法確認と素材要求

サイト構造を調査して報告。thinkxinc.com は静的 HTML ではなく Flask アプリで、ページ追加は
①main.py にルート追加 ②テンプレート新設 ③less を書いて main.less に登録 ④画像配置
⑤route_sweep ゴールデン追記、のセットになる。前例は truetechjapan 受賞企業ページ（2158fa4）。
反映は確立済みのデプロイ手順（monorepo → PR → develop → staging → 本番）に乗る。
必要素材として、イベント名・日時・会場・申込方法・プロフィール文・共演者情報・各画像の
サイズ要件を列挙して要求。

## 8. 【事故】add_current_office_ip.sh による本番・staging の全損

staging へのアセット配布が `Operation timed out` で失敗。原因を手元 IP の変化と判断し、
`add_current_office_ip.sh` の実行を案内した。

> **bash infra/scripts/deploy_production_from_staging.sh これを実行したら、今サーバーが完全に止まったんだが、何が起きてる？ありえないんだ。**

外形確認すると全サイト connection refused。ログを精査して機序を特定:
`add_current_office_ip.sh` が **-auto-approve で terraform apply を実行**する実装だったところへ、
IP 追加とは無関係の **AMI 追従差分**（data.aws_ami most_recent が新しい Ubuntu 22.04 ビルドを検出 →
ami 変更は ForceNew）が同乗し、**prod/staging の web/LB 計4台が破壊・再作成**された。
EIP は台帳（D-53）により保持されたため IP・DNS は不変。ホスト鍵の変更警告は
「同じ IP に別マシンがいる」＝入れ替わりの証拠だった。

> **どうしてホストの鍵が変わってるんだ。ホストの鍵というのは、SSHするための鍵か。なぜそんなことが起きてる。**

SSH の鍵は2種類あり、pem は「自分を証明する鍵」、ホスト鍵は「サーバーが自分を証明する鍵」で
OS 初回起動時に生成される。新品に置き換わったので変わった、と説明。

> **Ubuntuのバージョンは固定しているはずだが、supercomのバージョンと一緒だよ。明示的に変えようとしない限り変えてはいけないんだよ。**

メジャーバージョン（22.04）は固定されていたが、同じ 22.04 内の**ビルド（AMI ID）**が
most_recent で追従していたことが地雷だった。オーナーの原則に沿って
`lifecycle { ignore_changes = [ami] }` を両インスタンスに入れ、AMI 差分では再作成しないようにした（D-71）。

> **本番が停止しているが、Discordからは何の通知もない。ダウンしたら知らせる仕組みがないので、これはドゥードゥにしておかなければいけない。TODO**

外形監視+Discord 通知の不在を TODO として起票。

## 9. 復旧

`infra/docs/構築手順.md` に沿って prod → staging の順で再構築。途中の躓き:

- **apt ロック**: 新品初回ブートの unattended-upgrades がロックを保持し、setup_webserver が
  2回失敗（python3.9 と mongod が入らない）。うち1回は Claude とオーナーの**二重実行**が原因。
- **携帯回線（CGNAT）からの ssh 不達**: checkip の出口 IP を /32 許可しても通らず、
  復旧作業の間だけ 1.73.0.0/16 を一時許可（完了後に撤去済み）。

> **やるときはやるって言えよ**

宣言と実行を同一メッセージで行っていたことへの指摘。以後、状態を変える操作は実行前に宣言する
ルールを GUIDELINES に記録した。

> **サーバー立てられるまで勝手にやってくれ。すぐに出かけたいので。承認とかやらないので、勝手にやってくれよ。**

以降は自律実行。prod は全サイト 200・check_request_path 全ホップ green・acceptance 全サイト green。
staging も同一手順で再構築し、pr_and_merge_to_develop → deploy_staging → acceptance green。
一時許可した SG ルールは削除し、許可リストが terraform 管理の3件に戻ったことを実測確認。

> **作ったスクリプトを実行していけばいいようになっているはずだがなぜ色々複雑なコマンドを叩いている？必要なコマンドはすべてスクリプト化して再利用できるようにするはずだが**

（pr_and_merge_to_develop.sh / deploy_staging.sh / acceptance-sweep.sh 等）を使う形に戻した。
