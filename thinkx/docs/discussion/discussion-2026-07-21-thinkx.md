## 1. 遅延の申告と原因の特定 — 表示開始が `load` に縛られていた

**kaz:**

> 最近作ったTrueTechのサイトが異常に読み込みが遅い気がするんだが、チェックしてくれないか。

**kaz:**

> 最近作ったというのは、最近企業ページをいくつか作ったんだよ。その企業ページを新しくブラウザでロードしようとしたら異常に遅くて、だいたい6000ミリ秒ぐらい表示までかかっている。

オーナーの論点:

- TrueTech のサイトの読み込みが異常に遅い。
- 対象はトップではなく、最近作った企業ページ。
- 表示までおよそ6000ms かかっている。

初期調査では的を外した。トップページは 93ms・22KB で応答しており速い。企業ページ
（`/ja/award/<key>`）は本番で 404 を返した — まだデプロイされていなかった。テンプレートは
4KB・外部埋め込みゼロ・画像2枚と軽く、6秒を説明できる要素がコード上に無かった。

kaz が staging の DevTools 波形を提示して決着した。**個々のリクエストは全て速い**
（最大でも `bez6hty.js` の 353ms）のに、波形は前半約500msで一度静止し、6,000ms 付近で再び
動いていた。ネットワークが何もしていない5秒間は、転送ではなくメインスレッドかタイマー待ちを示す。

自前 JS を追って原因が確定した。

```js
// main.js
window.addEventListener('load', function (e) { f.initializeLayout(); });  // → showSite()
// main.css:4102
body       { opacity: 0; }
body.show  { opacity: 1; }
```

**サイト全体が `opacity: 0` で伏せられ、`.show` の付与が `window.load` に紐付いていた。**
`load` は全サブリソースの完了まで発火しないため、表示開始が GTM・GA4・Typekit の和文フォント
1.9MB・各種ビーコンのうち**最も遅い一つ**に人質に取られていた。document は 61ms、CSS は 32ms で
届いている。

途中で立てた仮説は2つとも外れた。277KB のロゴ PNG（計測されたのは revorn でロゴ 7.5KB、無関係）と、
Typekit の `wf-loading` による FOIT（該当 CSS が `main.css` に1件も存在しない）。

Claudeの回答要点:

- 初動は的外れ。トップは 93ms で速く、企業ページは本番未デプロイで 404 だった。
- 波形の決め手は「個々のリクエストは全て速いのに約5秒の無活動がある」こと。転送ではない。
- 原因は自前コード。`body{opacity:0}` を `.show` で解除するが、その付与が `window.load` 依存。
- 表示が third-party の最も遅い一つに律速される構造。仮説2つ（PNG・FOIT）は実測で棄却。

## 2. フェードインを維持した修正と、thinkx 読み取り専用の例外承認

**kaz:**

> 原因はわかったが、そのロードトリガーの要点というのは、ページを表示するときにフェードインするという効果を実装しようとしているが、それを維持して改善できるか。そしてThinkXは読み取り専用だが、今回は例外なので修正してくれ。どの計画でもない、今回のはただ単に修正である。緊急修正と呼んでもいい。

オーナーの論点:

- フェードイン演出は意図的なものなので、維持したまま改善できるか。
- thinkx は読み取り専用だが今回は例外。修正してよい。
- どの計画書の管轄でもない、単なる緊急修正である。

演出は無傷で維持できる。`.show` の付与を `load` から `DOMContentLoaded` へ移すだけで、
0.2s の transition はそのまま、開始タイミングだけが変わる。

```js
document.addEventListener('DOMContentLoaded', function() {
    requestAnimationFrame(function() {
        requestAnimationFrame(function() {
            document.body.classList.add('show');
        });
    });
});
```

二重 `requestAnimationFrame` は必須。`opacity:0` の状態で1フレーム描画させないと遷移の
開始値が確定せず、フェードが飛んで瞬間表示になる。

`.show` はヘッダとトップのヒーロー演出のトリガも兼ねていたが、全て CSS transition なので
前倒ししても壊れず、演出開始が早まるだけで意図通りだった。あわせて未使用の `windowHeight` と
`f` オブジェクト経由の二段間接を畳んだ。

Claudeの回答要点:

- 演出は維持できる。`.show` の付与を `load` → `DOMContentLoaded` へ移すだけ。
- 二重 `requestAnimationFrame` は必須。1フレーム描画しないと遷移の開始値が定まらずフェードが飛ぶ。
- `.show` が兼ねる他の演出も CSS transition のみで、前倒しは安全。

## 3. ビルド生成物を編集した事故 — ドキュメントは「あったが読まれなかった」

修正の直後、`git status` に何も出ないことで事故が露見した。編集した

`src/js/main.js` を直し、babel で焼き直した。

**kaz:**

>
> それはドキュメントがないからなのか、それともドキュメントがあって読んでいなかったからなのか、またはドキュメントへの配線が悪いのか、チェックする必要があるだろう。

オーナーの論点:

- 実装手順を把握していなかったということだ。
- 原因は3つのどれか。①ドキュメントが無い ②あったが読まなかった ③ドキュメントへの配線が悪い。
- どれなのかチェックする必要がある。

**三つとも該当したが、主因は②だった。**

必要な事実を持つ文書が2つ実在した。`thinkx/docs/受賞企業ページの作り方.md` は今回いじった
受賞企業ページそのものの手順書で、§2-4 に「`css/main.css` は `.gitignore` 済み（ビルド生成物）」と
明記されている。`docs/SITE_REQUIREMENTS.md` L17-19 には「`views/src/js` … babel/lessc で
書き出される」「gitignore に実生成物 `views/js`, `views/css`」とそのものが書かれていた。
`thinkx/docs/` を一度も `ls` しなかったのが実態で、弁解の余地はない。

③も実在したが、効いた箇所は想定と違った。ルート CLAUDE.md L30 が指す
`thinkx-system/SITE_EDIT_WORKFLOW.md` は存在せず（実体は `docs/` 配下）、これは配線不備では
あるが、同文書はビルド詳細を持たず「カットオーバー前は未発効」のため今回の直接原因ではない。

**実際に効いたのは別の穴。** ルート CLAUDE.md は「`<project>/CLAUDE.md` を都度読め」と規定し、
指示通り読んだ。だがそこには views ビルドの記載も `thinkx/docs/` への言及も無かった。
**規定どおり読んだ唯一の文書が、必要な事実を持っていなかった。**

①も部分的に該当。作り方 §2-4 は lessc（CSS）しか書いておらず、babel（JS）の記載が無い。
踏み抜いたのはまさに JS 側だった。

再発防止として最も安いのは、編集前に `git check-ignore <path>` を打つこと。ignore されていれば
生成物を疑う。今回それ一発で気づけた。

Claudeの回答要点:

- 三つとも該当。ただし主因は②「あったが読まなかった」で、これは自分の落ち度。
- 必要な事実は `受賞企業ページの作り方.md` §2-4 と `SITE_REQUIREMENTS.md` L17-19 に既存だった。
- 効いた配線不備は「規定どおり読んだ `thinkx/CLAUDE.md` が必要な事実を持っていない」こと。
- ①も部分該当。作り方は lessc のみ記載で babel が無く、踏んだのは JS 側。

## 到達点

出発点は「企業ページが異常に遅い」という体感だった。原因は企業ページには無く、TrueTech 全ページ
共通の構造 — `body { opacity: 0 }` を解除する `.show` の付与が `window.load` に紐付いており、
表示開始が third-party の最も遅い一つに律速されていた。`DOMContentLoaded` へ移すことで
約6000ms が 144ms になり、以後は末尾が何秒かかろうと表示は動かない。この修正は thinkxinc.com と
NNTM にも同時に効き、transformism にのみ同じ地雷が未修正で残っている。

そこから派生して、ページ重量の実体が順に明らかになった。Typekit の和文フォント 1.9MB は
`features=ALL`（縦書き・OpenType 機能の全要求）が原因で、動的サブセットもウェイト削減も既に
最適だった。`main.css` は 117KB が無圧縮で飛んでおり、`gzip_types` と `gzip_proxied` の不在が
原因だった。そして最大の資産は 54MB の autoplay 背景動画で、13.5MB へ圧縮した。

技術的発見と同じ重みを持つのが、**ドキュメント配線の穴**だった。ビルド生成物を直接編集する事故は、
必要な事実が2つの文書に既存でありながら、規定どおり読んだ `thinkx/CLAUDE.md` がそれを持たない
という構造から生まれた。同型の3サイトすべてで同じ事故が起きうる。役割別の必読配線が提案され、
オーナー承認待ちで残っている。

この日の Claude 側の誤りは4回（ビルド生成物の直接編集／`font-display: optional` の推奨／
「78MB を先読み」の断定／監視スクリプトの誤検出）。共通するのは**測っていないことを断定形で
書く癖**で、4回とも実測が覆した。逆に言えば、実物を確認する前に手順を書かなかったこと
